# Runtime

**Status:** Reviewed draft. This chapter defines the common execution protocol and identifies the inspected implementation subset. It does not claim that all concurrency or embedding facilities in the language specification are implemented.

## Responsibility and Boundary

The runtime executes operations whose meaning was established by checking and [Mid preparation](mid.md). It supplies storage mechanisms, reference-count primitives, dynamic access enforcement, scheduling, and native service integration. It does not select overloads, infer source types, resolve conformance, or decide which source paths own a value.

The [language specification](https://github.com/plew-lang/spec/blob/main/spec/04-execution/14-concurrency.md) owns observable concurrency and lifetime rules. [Ownership and Access](ownership-and-access.md) owns the compiler's proof and elaboration obligations; [Representation and ABI](representation-and-abi.md) owns physical value and call mapping. The runtime implements their agreed operations. The driver owns compilation requests, publication, process integration, and the lifetime of executable resources.

| Operation | Compiler responsibility | Runtime responsibility |
|---|---|---|
| Copy, move, and destruction | Select the operation and finalized type-specific behavior; place it on the correct path | Execute reference-count/storage primitives and invoked destruction helpers |
| CoW mutation | Preserve value semantics, select the typed element operations, and establish the mutation boundary | Provide allocation, uniqueness observation, and storage operations required by that plan |
| Dynamic exclusivity | Identify the logical root/path, access extent, and forwarding authority | Check actual active accesses and maintain balanced dynamic records |
| Async suspension | Produce a prepared state machine, live frame contents, and cleanup paths | Retain completion state, register waiters, and schedule resumption |
| Lazy call | Preserve one calling contract and request a prepared callable through the execution bridge | Resume ordinary execution after publication; use the same runtime operations as AOT |

These are conceptual responsibilities, not a requirement to place each column in one source file. A type-specific helper generated by the backend can implement part of the execution protocol without transferring semantic decision authority to the runtime.

## One Execution Implementation

Build and run use the same runtime implementation, ABI, and semantic rules. Separate ARC, CoW, access-check, destruction, or async implementations for AOT and JIT are prohibited. Different link arrangements, compiler services, and callable-availability mechanisms do not justify duplicate execution logic. If a design requires splitting those implementations, stop for an architectural decision.

Common implementation means shared execution code and protocols, not unconditional sharing of compiler/application scheduler globals. Every state variable still needs an intended owner. Process arguments, diagnostics, module storage, scheduling state, and compilation state need explicit owners and lifetimes when compiler and application coexist. A saved/restored argument view is state management within the common runtime, not a second runtime. Native symbol resolution must bind each service to its intended state owner; an unrestricted same-name process lookup must not accidentally attach application operations to compiler-private globals. The driver owns that symbol-admission protocol.

Plew-managed application execution is stopped during synchronous lazy compilation. This includes every application worker, event delivery, continuation execution, callback entry and user destruction. An external C call already entered through a registered native boundary may continue; its return or callback into Plew waits at the common entry gate. External C effects and OS activity are not stopped or cancelled by this guarantee. The [driver's worker-demand protocol](driver-and-execution.md#worker-demand-coordination) owns request arbitration, compiler affinity and publication; the runtime owns the participant states below. This is an adopted design, not a claim that the inspected implementation already supports spawn quiescence.

A pending code-generation request is not an asynchronous task exposed to application scheduling. Terminal compilation failure must not return a fabricated value through an arbitrary callee ABI. The process execution boundary terminates on such failure; surviving-host recovery, Hot Restart orchestration, and multiple independently restartable environments are not promised here.

### Managed Pause and Native Boundaries

The execution owner maintains an application participant registry and a pause generation. Registration, native transitions, blocking/wakeup and retirement synchronize with this same authority; independently sampled flags are not a proof that the application is stopped. The compiler service is outside the application participant set and uses compiler-owned state under the common runtime protocol.

| Participant state | Obligation during a pause |
|---|---|
| Running managed application code | Cooperatively reach a safe stopping point and acknowledge the requested generation |
| Waiting for preparation or a runtime blocking operation | Publish a stable suspended state; wakeup cannot enter managed code until the gate opens |
| Inside a registered external native call | Publish retained roots/access/code dependencies before departure; C can continue, but managed reentry remains gated |
| Starting or retiring a worker | Serialize membership with the pause; no unregistered execution or premature resource removal |

Generated demand-mode code checks for pause requests at managed entry/call boundaries and loop backedges. Compiler-generated helpers with potentially unbounded managed work must also cooperate, including typed element copy/drop loops at committed ownership boundaries. A helper can use a registered native transition only for work outside managed application execution: stable retained inputs alone do not permit typed application operations, user deinit or managed state updates to continue. Any such transition back to managed work passes the gate, regardless of whether the helper was written in C or emitted by the backend. A finite non-interruptible helper may finish before acknowledging. Stopping cannot expose half-initialized ownership transfers, unbalanced access records or incomplete storage transactions. These are code-generation obligations consumed by executable admission, not a runtime attempt to discover safe instruction addresses. Arbitrary OS-thread suspension is not used. AOT execution without a demand service need not carry JIT pause polling; this does not change its ARC, access or scheduling implementation.

A stopped frame retains its already evaluated arguments, live owned values, access scopes and executable resources. Logical user lock ownership, including a MutexGuard, remains held; suspension neither unlocks it nor ends a borrow. Other workers waiting for that lock can acknowledge as blocked, without acquiring it. Runtime/coordinator locks needed to acknowledge or publish must not be held across a wait. Brief state commits complete before parking; a wakeup that has acquired an application lock still passes the gate before exposing the guard to managed execution. Thus a paused lock owner does not itself prevent quiescence.

Native entry commits a stable boundary record before external execution begins, ordered against pause admission by the same authority. If pause admission wins, the caller parks before starting a new external call; an entered boundary record is the departure linearization point. Return and callback entry test the gate before any application code, including generated wrappers, runs. Nested callbacks retain their enclosing native-call dependencies; a callback that later requests preparation uses the same worker-demand protocol. A callback from an external thread must first attach to the intended execution owner and participate in this admission protocol. This is an internal requirement, not permission for arbitrary foreign threads to enter Plew. Native-thread release of a managed handle must not bypass the gate to run user deinit; defer such managed work with its ownership retained. The usual explicit FFI responsibility for raw memory, external synchronization and lifetime still applies; pausing does not make unsafe foreign access safe.

I/O completion and cross-worker notifications may accumulate while paused, but only synchronized transport bookkeeping and wakeup can proceed. They do not resolve destination-local Promises, run continuations or perform application destruction until resumption. Pending work and loop/resource lifetime remain accounted for. Once every participant is stopped, safely blocked or outside managed execution, the coordinator can grant the compiler service permission to prepare and publish; mere event-loop inactivity is insufficient.

This boundary follows the distinction in [Dart's generated/native transitions](https://github.com/dart-lang/sdk/blob/main/runtime/vm/heap/safepoint.h) and [HotSpot's native reentry checks](https://github.com/openjdk/jdk/blob/master/src/hotspot/share/runtime/interfaceSupport.inline.hpp). Their safepoint machinery is a comparison for safe stopping, not evidence that those languages stop all application execution for every compilation. Plew adopts the stronger compilation pause to keep compiler-session mutation independent of application execution, while excluding already entered external C work from that pause guarantee.

### Startup Readiness

Runtime executes the [driver's closed initialization plan](driver-and-execution.md#static-initialization-plan); it does not discover dependencies on a global read. It starts only prerequisite-ready bodies, uses the ordinary async machinery for their explicit awaits, and publishes each completed owner once before admitting dependent bodies. A synchronous call or borrow/inout access never waits for another global initializer. Storage readiness and one-time publication states remain separate from JIT entry registration/materialization and the managed-pause gate. Workers share these initialized roots rather than initiating root-side forcing. General native callback/embedding eligibility remains within its existing ABI boundary. An acyclic startup plan does not establish termination of arbitrary lock, channel or I/O waits.

## Storage, ARC, and CoW

Logical value ownership is distinct from storage reference counts. One semantic copy may share a backing allocation under CoW; a move transfers responsibility without creating another logical owner. A byte copy of an ABI argument or relocated element is not by itself a semantic Copy operation. The backend and runtime must agree on when a retain, element copy, payload destruction, and allocation release occur, with no independently added second ownership operation.

Opaque buffer/cell handles hide headers, capacity, live count, and allocation addresses from ordinary value semantics. Typed compiler-generated operations supply element behavior that an untyped allocator cannot infer. Relocation transfers existing initialized slots; it must not copy ownership into two live slots. The live-count and initialized-region invariants determine which elements are available for reads and eventual destruction. Uninitialized capacity is not a set of values to destroy.

CoW must establish private writable storage before mutation becomes observable. Detaching storage containing reference-bearing elements must preserve each element's ownership; a scalar byte-copy helper alone is not a generic element-copy implementation. Uniqueness tests may remove unnecessary work only under the proven ownership/access contract. Shared identity through Ref/MutableRef is not value-semantic CoW mutation.

Strong and weak references have different obligations. Losing the last strong owner destroys the payload according to finalized destruction behavior; weak observers can keep the control allocation alive without keeping the payload alive. Upgrade must not resurrect a destroyed payload. Deallocation follows the final relevant ownership release, not merely the first counter reaching zero.

The language sharing contract fixes RC mode at allocation and uses one runtime protocol with non-atomic and atomic operations. For AOT, execution preparation produces a conservative may-share plan, the session retains its decisions and dependencies, and the driver requires its closure before executable publication. The analysis covers the required whole-program dependency graph, including weak upgrade, globals, closure/environment operations, indirect witnesses and destruction. Propagate requirements to allocation origins and aliases; a mixed join requires atomic origins. Store allocation-mode decisions, argument/result alias relationships, typed operation dependencies and reverse invalidation edges in the execution preparation result. AOT without a sharing boundary uses non-atomic ordinary managed allocations; no spawn-time promotion or per-retain mode guessing is adopted.

Demand execution instead uses conservative atomic RC for ordinary managed allocations as its baseline, including application library-generated value operations and weak control state. Immortal roots remain a separate storage policy. This mode is fixed before execution and is not downgraded by a partial graph that has not seen future demands. A later lazy body can therefore share an existing managed value without rewriting its allocation mode. Proven confinement can support a later optimization only if its publication and dependency validity cover every permitted future use. The conservative baseline does not require that optimization or a second runtime implementation. The [language execution contract](https://github.com/plew-lang/spec/blob/main/spec/04-execution/14-concurrency.md) owns these AOT/JIT guarantees.

The driver admits a body only when its allocation, copy/drop, weak-promotion and called-entry modes agree with its execution environment. Physical RC specializations are keyed by that frozen mode/alias plan as well as source instance, target and ABI. They do not change semantic type identity or authorize different overload selection. AOT invalidation precedes execution; demand publication cannot silently invalidate a mode already used by live allocations. Foreign-memory safety remains at the explicit FFI boundary. The existing non-atomic primitives do not prove spawn support. Cycle reporting/reclamation described as future work in the specification is not an implemented collector or a reason to weaken normal-path destruction guarantees.

Generate only required mode combinations, not every possible specialization in advance. Potentially combinatorial code growth and propagation across distant callers are accepted costs of retaining non-atomic operations where safe. Argument count alone is not a general bound: result and internal-buffer modes and their alias relationships also constrain a specialization. Programs without a sharing boundary should bypass unnecessary sharing analysis; measure dependency collection, analysis and generated-code costs rather than assuming the fast path is free.

The exact raw-buffer header and immortal-storage encoding are private representation choices. Any change must update generated operations, native helpers, constants, and relevant validation together. It must not expose allocation identity as ordinary value equality.

The [concurrency specification](https://github.com/plew-lang/spec/blob/main/spec/04-execution/14-concurrency.md)
describes future additive cycle reporting/reclamation limited to the shared
reference graph. Value trees do not require shared identity merely for recursive
shape. Detected garbage cycles are reported and reclaimed without executing
cyclic members' user deinit; ordinary ARC destruction remains deterministic.
Per-thread idle collection requires a safe-point and sharing protocol, not an
assumed existing collector. [Cycle management](../issues/com-2z5l.md) and
[concurrency analysis](../issues/com-qzpm.md) retain these implementation
boundaries separately.

Collection-specific finite operations, initialized-extent invariants, reentrant
commit-before-release and library-layer responsibilities are defined in the
[Buffer floor supplement](collections-and-buffer.md).

## Dynamic Access Enforcement

The runtime consumes normalized storage identity and path information from [Access elaboration](ownership-and-access.md). It checks executed accesses against active records, rather than executing a conservative interprocedural effect summary as if every possible branch occurred. Scope entry/exit, alias checks, and proven forwarding permissions must describe the same access lifetime.

The record's address and path storage must remain valid until scope exit. Pinning the underlying allocation preserves storage lifetime; it does not grant exclusivity. Ending a dynamic record must balance the record actually begun, including nested calls and compiler-generated destruction. Borrowing cannot silently persist across an async boundary by leaving a stack record registered.

FFI beyond the checked boundary is the programmer's responsibility under the specification. Native calls do not become pure merely because no Plew body is available. Callback entry, thread eligibility, and retained context lifetime remain subject to the [foreign boundary](representation-and-abi.md); this chapter adds no automatic context capture or arbitrary-thread callback support.

## Async Activations and Completion

The compiler produces the state machine and frame layout from prepared Mid. The runtime owns queue and waiter mechanics, not a second AST interpreter. A suspended activation preserves its owned values and resume state; a callback reentry reloads frame contents rather than relying on SSA values from an earlier invocation. Source cleanup remains on the Mid paths that discharge those values. Completion code separately releases the activation's own completion-handle count and frame storage.

Entry must establish the returned Promise owner's count before an initial resume that can complete synchronously. Otherwise completion could free the cell before entry returns its handle. Pending operations, timers, and awaited handles need independent ownership obligations so dropping a user-visible handle does not leave a dangling scheduled callback or imply cancellation.

A Promise belongs to one event loop. For a copyable result it is a shared completion handle: multiple waiters may register without replacing one another, completion transfers their continuations to scheduling, and each waiter receives an owned logical copy. For a unique result, the consuming protocol in [Typed Outcomes and Worker Results](#typed-outcomes-and-worker-results) applies; private cell ownership does not permit multiple public result consumers. The runtime/typed generated support must preserve a compound result and destroy it when its last owner disappears. A scalar completion slot is only an implementation subset, not the representation contract for every Promise[T].

Completion is published once per operation. A continuation has one registration/queueing responsibility at each suspension and must not be resumed twice for the same completion. Queue ownership must make the frame and callable valid until execution. These are required protocols; the inspected low-level resolve helper does not itself establish all of them for arbitrary callers.

Before any reentrant application continuation, callback, or payload destructor can run, commit the operation's observable state: remove or finalize its registration, fix the payload owner and terminal outcome, and establish any queued completion ownership. Release internal transport locks before invoking application code. Publishing a completion cannot expose an intermediate state merely because the callback runs on the correct loop. Inline completion and scheduled completion must obey this same boundary; a channel must not invent its own await or continuation-order semantics. The common async contract continues inline when an awaited Promise is already complete; await is a possible suspension point, not an unconditional yield. An incomplete Promise registers a waiter and suspends, then resumes on its owning loop. Channels follow this same rule rather than supplying their own continuation-order semantics.

An event-loop scheduler is an execution service, not a VM or a compiler. It can call already published native functions regardless of whether those functions were generated ahead of time or on demand. No bytecode interpreter, speculative tier, or independent language evaluator is required by this architecture.

### Typed Outcomes and Worker Results

A completion operation carries one finalized logical outcome type and its permitted typed operations. The generated producer owns the outcome before publication; completion storage owns it after the transfer. For copyable results, repeated awaits acquire ordinary owned copies of the same result. For unique results, the unique public Promise exposes one consuming await; its outcome is moved exactly once and cannot acquire a copy path merely because the private cell has internal scheduling owners. A consuming await transfers its result-receipt right to the suspended consumer before releasing the public Promise handle. That consumer is not an abandoned result merely because no public handle remains. Destroy the result on its designated completion path only when neither a public result owner nor an entitled waiting consumer remains. Internal RC ownership is not permission to duplicate the public typed result.

JoinHandle's join-or-drop transition chooses the completion destination exactly once. Join registers the calling worker's event loop, which need not be the handle's creation loop, and transfers the right to receive a result to its Promise; dropping an unjoined handle registers disposal on the dropping worker's loop. Register that destination's pending delivery ownership before exposing it to a finishing worker. The worker's synchronized completion cell owns a result produced before destination registration. Worker completion is published only after its body has returned and its own loop has drained; it is not the first return instruction.

A completed worker transfers its outcome to the already selected destination, where receive or abandoned-result destruction follows the same local completion protocol as other cross-worker deliveries. Keep destination resources and typed code valid until that transfer/disposal obligation ends. Last release of a shared reference contained in the outcome follows the shared cell's own final-release rule; it is not a second destruction of the worker result. Normal shutdown needs an application protocol that discharges outstanding receives and processing tasks. Cyclic waits, including waiting for one's own completion, are not automatically made productive by retaining resources; memory safety is not a deadlock-freedom promise.

## Cross-Worker Completion Delivery

A cross-worker transport does not transfer ownership of an event loop's local completion state. A Promise, receive registration, activation, and continuation remain associated with their destination loop. Making the transport queue thread-safe, using atomic allocation counts, or releasing its lock does not authorize a sending worker to resolve another worker's Promise or update that worker's local reference counts directly.

| State or operation | Responsible owner |
|---|---|
| Accepted payload, admission/closure state, and cross-worker notification state | Common synchronized transport; payload copy/move/drop behavior is supplied by the compiler's checked type contract |
| Pending receive registration, Promise result, and application continuation | Destination event loop; foreign workers may signal it through the transport, not operate on its local completion objects |
| Pending-work registration and delivery-resource lifetime | Runtime protocol spanning registration through local completion and release |
| Value transfer, discarded results, and cleanup | The one path that owns the value after admission/delivery; generated typed operations execute on the authorized path, outside transport locks |

The protocol must close registration, notification, and final use together:

1. Establish the destination's pending operation and ownership before making its wakeup route available to a producer. A message or closure event can arrive immediately; registration cannot leave a window in which the destination is already eligible to terminate.
2. A sender or closure producer commits the shared state and payload ownership under the transport's synchronization protocol. Successful admission and returned failure must never both own the same payload. Publish a safe notification after that state is visible; do not run destination application code on the producer's thread.
3. The destination observes the committed state on its own loop, associates values or terminal completion with its registrations, and completes each operation once. Repeated or coalesced wakeups must not repeat delivery, and a wakeup arriving between an empty check and parking must not be lost. This does not require one physical notification per message.
4. Commit the local completion and transfer ownership to the result, scheduled continuation, or discarded-result cleanup before releasing the operation's pending-work and delivery obligations. A queued continuation has its own ownership until execution. User callbacks and deinit must not observe intermediate transport state or run under its internal lock.

Shared transport state must not own unrestricted access to a destination-local Promise. Destination identities, registration tokens, inboxes, wakeup handles, and their physical storage are implementation choices, but their lifetime and publication must obey the protocol above. A late notification must not access a destroyed or reused destination registration. No new source-level lifetime, cross-worker borrow, or second AOT/JIT runtime is implied.

Dropping a public completion handle is not cancellation. An outstanding receive can therefore remain pending, accept a value later, and destroy its result if no public owner remains. A producer-disconnection or explicit channel-closure event must reach the destination and finish registrations that can no longer receive a value; these are completion paths rather than an implicit cancellation mechanism. Payload already transferred into a completed result is not reclaimed by a later transport close.

Explicit receive cancellation uses the same terminal-completion protocol. Cancellation control belongs to the receiving loop and identifies one registration; it is separate from the Promise that owns the result. Cancellation of an unassigned registration and payload assignment compete for one terminal transition. If cancellation wins, unlink the registration without consuming a payload and complete its cancellation outcome once. If assignment wins, retain the original result ownership and reject cancellation; do not requeue a value already transferred to a result. Closure completion is another terminal outcome, not a reason to resolve an operation twice. Preserve the relative order of surviving registrations.

Cancellation must transfer ownership to the terminal result or completion-delivery path before releasing the receive's pending-work obligation. A control handle retained after termination is not a pending receive and cannot keep the result payload alive solely for future cancellation attempts. Late/coalesced notifications must recognize terminated registrations. Dropping either public handle alone does not request cancellation. Public types and signatures are library contracts; these obligations do not add generic Promise cancellation or a second scheduler.

Closing admission or observing an empty-and-closed receive does not establish completion of application work that already owns delivered results. Those values may be held by Promise owners or processing activations. The application keeps explicit processing/acknowledgement responsibilities where it needs such a barrier; transport closure does not infer them.

The compiler/driver must preserve destination queues, runtime state, and executable code until these obligations are discharged. Dispatch during application suspension for lazy compilation follows the [managed-pause protocol](#managed-pause-and-native-boundaries); transport bookkeeping can proceed, while destination-local completion and application dispatch wait. Channels do not have a separate pause mechanism. This section supplies the internal ownership protocol; it does not choose channel capacity, receive ordering, exact library signatures, or certify an implemented worker transport.

## Pending Work and Process Lifetime

Loop completion depends on owned pending work, not simply whether main returned or the ready queue is momentarily empty. Timer, I/O, worker completion, and detached-result disposal need explicit registration, completion, and release rules as those facilities are implemented. The specification's spawn/join semantics include worker-loop completion and processing at the registered destination; queue exhaustion in the current timer-only runtime does not implement that contract.

Count a cross-worker receive from registration through its terminal local completion, including in-flight notification and completion delivery. Releasing a public handle or returning from a worker body does not remove that obligation. Successful explicit cancellation ends the receive through terminal local completion; any separately queued delivery or continuation still retains its own obligation. Conversely, a stored channel handle or buffered value is not by itself a registered receive operation, and its reference count is not a substitute for pending-work accounting. A service that keeps a loop alive must have an explicit owned obligation. Normal owner loss can still destroy buffered values according to the transport contract without first delivering them to application code.

Code, global storage, callback contexts, process-argument views, and runtime support must outlive every permitted callback, including native process-exit callbacks. Returning from a main invocation alone is not permission to unload JIT code. The [driver chapter](driver-and-execution.md) owns the execution-resource lifecycle; this chapter defines what execution participants require from that owner.

Normal-path value destruction is distinct from process/runtime teardown. Panic aborts without unwinding or a deinit guarantee. Process exit and immortal top-level roots likewise do not create a universal destructor pass. Restoring a borrowed host argument view is resource bookkeeping, not a promise to destroy all application values or safely restart an embedded host.

## Native Services and Contract Changes

Runtime symbols use explicit physical signatures consistent with ABI lowering. Declaration registration must reject incompatible same-symbol types; a guessed external declaration is not an acceptable missing implementation. OS services, C allocation, and process operations are platform integration dependencies, while their Plew-facing value/error/termination contracts remain governed by the specification and checked library APIs.

To change an operation, identify its checked/intrinsic contract, Mid representation or access plan, typed generated support, native helper, and both AOT/JIT consumers. Update the protocol as one change. Validation should compare observable output, failure, destruction, ownership, and scheduling behavior across execution modes, including early completion and dropped handles. A sanitizer pass does not prove semantic equivalence, and one working scalar async example does not establish general payload or scheduler coverage.

## Reference Designs and Plew's Choices

Plew exposes one sendability property rather than separate movement and shared-read traits. Its sendable values must also tolerate the admitted FrozenRef sharing path; this is not a renaming of [Rust Send and Sync](https://doc.rust-lang.org/std/marker/trait.Sync.html). Ref/MutableRef remain worker-local, and wrapping a nonsendable payload in FrozenRef or MutexRef does not repair it. This deliberately excludes some independently owned graphs and unsynchronized interior-mutability types that a richer movement-only capability could admit. Build such state in the destination worker or use values/IDs and admitted synchronization. Reconsider a separate sharing capability only for demonstrated use cases or costs, rather than speculatively adding another public rule. Atomic RC protects lifetime, never unsynchronized payload access.

[Swift's runtime design](https://github.com/swiftlang/swift/blob/main/docs/Runtime.md) documents execution support for generated code, including memory management and dynamic type operations. Plew likewise treats runtime helpers as contracts with generated code. Swift's broader runtime facilities do not require Plew to repeat type selection at runtime or adopt Swift's executor model.

[Dart's VM overview](https://github.com/dart-lang/sdk/blob/main/runtime/docs/README.md) distinguishes compilation components from the execution environment shared by JIT and AOT modes. Dart also has a precompiled runtime variant without compiler/dynamic-loading facilities. Plew's prohibition on separately maintained execution implementations is its own stronger constraint, not a claim that Dart ships one identical binary configuration. Plew does not adopt Dart's collector, background compilation, isolate heap model, or Hot Reload. [Dart's event-loop model](https://dart.dev/language/concurrency) is a useful scheduling reference, while Plew's explicit ARC and shared-reference rules remain different.

[Rust's Rc](https://doc.rust-lang.org/std/rc/index.html) illustrates non-atomic shared ownership confined to one thread and the role of weak references. It supports separating payload lifetime from weak observation; it does not make a general runtime primitive sufficient proof of Plew's allocation-specific threading safety. The compiler still owns the conditions for using each mechanism.

## Implementation Evidence and Open Boundaries

The following is a source inspection at compiler revision `6fe09bc7c0e75260b3f773643921478b5020b94f`, not a runtime correctness test or a full concurrency audit:

- `src/Backend.pw::emitLlvmRuntime` emits common C support: raw-buffer allocation/count/capacity/reference primitives, strong/weak operations, dynamic access records, checked arithmetic, native I/O/process helpers, and Promise/queue/timer support. Generated source location inside Backend is an implementation arrangement, not ownership of source semantics.
- Its ready queue is drained before selecting the earliest timer. Timers advance a virtual clock; the inspected loop does not perform wall-clock waiting or general OS event polling. The Promise payload is scalar i64, waiter registration is a list, and resolve queues continuations. The helper overwrites the completion slot without a double-resolution guard, so one-shot completion needs a caller protocol and is not independently enforced by this primitive. These facts limit implementation claims; they do not change the language's general async contract.
- `Backend/Llvm/Async.pw` establishes an activation and retains the non-main returned Promise before the initial resume. `MidAsync.pw` consumes prepared Mid and frame analysis, reloads completion state after reentry, and separates source Drop from Promise/frame release at completion.
- `native/compiler_execution.cpp` owns copied argument strings and a pointer view, installs the application view, and restores the previous view on destruction. Its main-call boundary explicitly retains execution-lifetime obligations beyond main return. This does not establish a general multi-environment API. `native/llvm_backend.cpp` disables default process-symbol lookup for source modules and provides selected memory-service fallbacks separately; this inspected separation is not a complete runtime-symbol ownership audit.

Compound Promise payload ownership, actual I/O waiting, spawn/channel execution and atomic allocation selection, collector support, allocation failure/overflow handling, full intrinsic coverage, and every reentrant/native callback path are not verified by this inspection. Existing known implementation restrictions remain restrictions rather than adopted language prohibitions. Compiler/application shared scheduling-state isolation and safe reusable embedding also need a separate lifecycle audit before stronger claims are made.

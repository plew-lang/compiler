# 設計判断と未決事項

> 会話は時系列で設計が変遷している。古い案が後で覆されている箇所が多い。本書は後発の結論を優先して記述するが、最終的な正典は `grammer/Plew.g4` と `SPEC.md`。

## 言語の目的（全制約の出発点）

- モノレポでサーバー（Go 的）とフロント（React 的）を 1 言語で書き、モデル層を共有する。
- **コンテナのコールドスタートが速い**ことが第一目的 → AOT ネイティブ / WASM、軽量ランタイム志向。
- 「Rust から所有権を引いた書き味」が理想。所有権・借用・ライフタイムは**明確に不採用**。
- この「参照の値渡し + GC + 所有権なし」が、並行性・拡張・ロック周りの議論すべての根本にある。

## 主要な判断と根拠

### 参照の値渡し + `inout`（→ [spec/03](../spec/01-basics/03-values.md)）
- 「全部参照渡し」は副作用がシグネチャから見えない/競合/不変性を強制できない、として却下。可変性と `inout` を構文で明示する方向に。
- 引数の `mut` は「関数内ローカルの再代入可能性（副作用なし）」と誤解されるため不採用。Swift の `inout`（呼び出し元を書き換える意図が明確）を採用。Ada / C++ `&` / Nim `var` / D `ref` も比較。

### 並行性: spawn キャプチャ問題（大きな方針転換・→ [spec/14](../spec/04-execution/14-concurrency.md)）
- 初期案は変数宣言種別（`let` / `let mut` / `let sync` / `atomic`）でスレッド安全性を制御するものだった。
- **破綻例**（`examples/main.pw` の元ネタ）:
  ```plew
  mut val a = <T s=<S x=42 /> />
  sync val b = a            // 参照の値渡しで a をコピー
  spawn { b.lock().s.x += 1 }
  a.s.x += 1                 // a と b は参照先を共有 → 競合
  ```
  参照の値渡しゆえ、`sync` でラップしても元の参照経由で競合可能。さらに `Mutex.lock()` は内部可変性で不変参照から呼べるため、構文・型レベルで `mut` を禁止しても競合は防げない、と判明。
- **最終結論（Go 寄り）**: spawn キャプチャは全 immutable（例外なし）、`Mutex` / `sync val` は標準で提供しない（or `@unsafe` 限定で非推奨）。スレッド間は immutable な `Sender` の `send` で**値を送る**（"share memory by communicating"）。**Mutex を入れない理由**：参照の値渡しゆえロックでラップしても元参照経由で競合し得る／**GC では `Drop` による自動 unlock が使えない**（スコープ脱出≠即時破棄）。
- **モデル確定（async/spawn）**: 基盤は JS と同じ単一プロセス・単一スレッド + イベントループ。重い処理は `spawn`（「プロセス」ではなく**スレッド**・立てたスレッド自身も単一ループ）。
- **spawn の戻り＝ハンドル構造体（決定）**: `join() -> Promise[T]`。**footgun 回避の理由**：detached でもブロックは完走（投げっぱなしでも結果を捨てるだけ）／ハンドルはスレッドを所有しない（寿命を GC 到達可能性に紐づけると突然死＝不可）／**ランタイムは全スレッド完了まで生存**（Go の「main 終了で goroutine kill」footgun を避ける。将来 daemon 指定の余地）。
- チャネル方針: **複数 Sender**。ただし所有権が無いので Rust の「Receiver は単一所有」を強制できない（`Receiver` も参照の値渡しで複数箇所が持て、`receive()` も複数回呼べる）。マルチコンシューマの意味論（競合 vs ファンアウト）は未確定＝**具体 API はコアライブラリ実装の課題**（言語コアの構文要素ではない）。
- **`Send`/`Clone` を制約に使わない**: Rust の `Send` は所有権・move 前提のマーカーで、所有権が無い Plew では不要。スレッド安全性は「spawn キャプチャ全 immutable」で担保し、多重 Sender も `Clone` 制約でなく型固有の操作で与える。
- **並行安全性の保証範囲＝書き込み隔離のみ・データ競合自由は非提供（決定・今セッション）**: 機構は [spec/14](../spec/04-execution/14-concurrency.md)。**経緯**：(i) clone スナップショット案 → spawn は競合自由を狙わない方針と判明し撤回、(ii) Java 流 no-UB を検討 → no-UB の"無料"は「全複合型を恒久的に参照表現に縛る（安いアンボックス Slice 不可）」標準コストで、enum 等は今でも裂け得るため**毎表現決定にかかる税**と判明、ユーザーの「ほぼ単スレッド・コンパイラ/ランタイムを頑張りたくない」と逆行 → **約束しない**に決定。idiomatic（immutable キャプチャ＋チャネル送信）は競合しないので破壊は非推奨経路限定。**理想は「クラッシュはしても UB なし」（Go の concurrent map 検出型）だが、実装/ランタイムコスト次第で各機能の実装時に判断**（現時点で保証なし）。
- **トップレベル変数を持つ（決定・今セッション）**: モジュールのトップレベルに `val`（定数）・`mut val`（可変）を置ける（`export val` で公開も）。**ユーザーはグローバル（ambient）な定義を作れない**が「グローバル変数/関数が無い」わけではない＝モジュールレベルには在る。正確には「**グローバル名前空間が無い**」ではなく「**ユーザーが ambient 定義を作れない**」（唯一の ambient＝言語提供 lang item は実在する）。
- **言語アイテム（lang item）は常にスコープ・それ以外は明示 import（決定・今セッション）**: 機構は [spec/15](../spec/04-execution/15-modules.md)。**経緯**：毎ファイル `import Foundation with *`（#include 風）も暗黙 ambient（Swift 風・コア境界が曖昧で「Random は要 import？」が起きる）も嫌い、の板挟みを「ambient なのは"言語の語彙"＝固定小集合だけ、ライブラリは全部明示」で割って解消。**位置づけ＝唯一の ambient は言語提供 lang item でユーザーは足せない**（"グローバル名前空間なし" とは言い切らない＝lang item は実際 ambient）。**保留：マニフェスト既定 import（write-once で全ファイルに撒く）** ── ユーザーが「許せる」とした案だが当面不採用（additive で後付け可）。

### 拡張システム（記法が最も二転三転した・→ [spec/09](../spec/02-type-system/09-extensions.md)）
- 解決したかった Rust の DX 課題: (1) 1 メソッドのために trait+impl は冗長、(2) 呼び出し側がファイル頭の `use` を見ないと由来が分からない。
- 核心アイデア: **拡張元を呼び出し位置で明示**する（import スコープに依存させない）。
- **外部型への実装は拡張に強制**: 無名 impl は「**型を所有**」が必須（Rust の「型 or トレイト」より厳格）。理由：外部型への無名トレイト impl は呼び出しで `#` 修飾が要り「実質拡張」になる上、明示拡張と並存すると経路が二重化するため、一律 `#Ext` に一本化。`#Ext` は型の一部でジェネリックにも決定論的に流れ、別実装は別型として区別（禁止でなく型で区別）。
- **記法変遷**: `[..].average#crate()` → 区切りを `@` に（メアド連想）→ 演算子・引数渡しで明示できない問題で `value@Ext.call()` を断念 → レシーバ後置 `value@Extension.call()` → スコープを `namespace { … }` で区切る → 広すぎるので **`extension`** キーワードに。**最終文法では区切りは `#`**（`@` は会話上の議論）。
- **Single Dispatch Resolution Rule**: `#Ext` を必須にすることで C++ 的ダイアモンド曖昧性は原理的に起きない。危険が出るのは `#Ext` 省略糖衣 / extension の継承・ネスト / 暗黙 trait dispatch を入れたとき → これらは禁止/制限する。**拡張の再エクスポートは安全で許可**（`#Ext` は各ファイルでスコープ内の一意名に解決＝一般シンボルと同じ扱い。当初 re-export を危険リストに入れていたのは誤りで撤回）。
- **拡張ビューは暗黙キャストなし・ビュー変更は明示（決定・今セッション）**: 機構（`A#P`＝ゼロコストビュー・型検査では `A` の不変な型細別・コンテナ非伝播・拡張違いオーバーロード共存）は [spec/09](../spec/02-type-system/09-extensions.md)。**経緯**：一旦「双方向の暗黙キャスト（ターゲット指向）＋拡張違いオーバーロード禁止」を採ったが、(a) スカラは暗黙・コンテナは不可という**非対称が分かりにくい**、(b) Plew は他に暗黙変換を持たず**全ビュー変更を明示する方が一貫**（orphan の `f(x#Ext)` 必須と統一）、の 2 点で**暗黙キャスト全廃に再転換**。明示の冗長は `default_extension`（既定拡張はベア表面に載る）が大半を吸収。暗黙キャストを外した結果、オーバーロード禁止の特別規則も不要になった（exact 一致で曖昧消滅）。

### トレイトのフィールド + `via`、トレイト準拠モデル（→ [spec/08](../spec/02-type-system/08-traits.md)）
- computed property（getter 地獄）が嫌い、という動機でトレイトにフィールド定義を許す（構造的制約として機能）。Rust が避ける理由（メモリレイアウト/衝突）は理解の上で採用。
- 代償: フィールド要求トレイトは外部型に実装できない（Rust の orphan rule より強い制限）。妥協策が `via` フィールドエイリアス。`via`/`<-`/`=:` を比較し `via` 採用。
- **準拠モデル（方針確定）**: 準拠は `impl Type as Trait` を**明示宣言**し、全要求を `via` で実体メンバに束ねる（or メソッドは本体定義）。当初の「単一フラット名前空間」は後述のオーバーロード許容で緩和。
  - **却下**: ① Swift 方式（同名・同シグネチャの既存メソッドが暗黙に witness）→「うっかり準拠」が怖い。② Rust 方式（inherent と trait で別名前空間、`fn baz() { return self.baz() }` の自己委譲が意味不明）。`via` 束縛は両者の中間で、**ベアの呼び名を保ったまま明示**でき、自己委譲の奇習も消える。
  - **別名はベアでも可視**（決定）: 要求名と実体名が違う `via` は要求名をベアの呼び名として追加。トレイトとして呼べてベアで呼べないのは不合理、という理由。
  - **`via` 左辺は常に完全シグネチャ**（決定）: 本体定義形と対称で、トレイト未参照でも各行の意味が分かり、同名要求が複数（要求のオーバーロード）でも一意に witness できる。「名前だけ／稀にシグネチャ」の特例を避けた（ルールは 1 つ）。
- **派生メソッドは拡張＋`default_extension` に一本化・ベア提供メソッドは廃止（決定・今セッションで再転換）**: 「デフォルト実装」の 2 役割のうち ① 派生メソッド採用・② 上書き可能な既定は不採用、は前回と同じ。機構（置き場＝名前付き拡張の `impl Trait`・型が `default_extension` で取り込む）は [spec/08](../spec/02-type-system/08-traits.md)・[spec/09](../spec/02-type-system/09-extensions.md)。**動機**：ベア提供メソッドは ambient で、別トレイト由来の同名・同シグネチャが暗黙に流れ込んで衝突し得る（検出時点も「偶発＝準拠時／継承強制＝トレイト定義時」に分岐して複雑）。拡張に閉じれば衝突は構造的に起きず、`default_extension` で冗長性を消せる。**経緯**：blanket 要望 `impl[T] T as A where T: B`（Rust 流）→ 頭なし Self は型所有が錨を持てず却下 → 主語をトレイトにする `impl B as A` → 同じ衝突が提供メソッドにもある指摘 → 「トレイト主語 impl はすべて拡張内のみ＋`default_extension` で opt-in」に収束。**効果**：どの派生メソッドがベアに見えるかの決定権が**トレイト作者→型作者**へ移り、列挙可能性が強化、衝突は**型の `default_extension` 宣言地点**に局所化（旧「衝突検出の時点分岐」は不要になり撤回）。`impl Foo` の種別曖昧（無名 impl か提供メソッドか）も解消＝ベア `impl Name` は常に型主語の無名 impl。**対価**：型ごとに `default_extension` 一行／ジェネリック境界 `T: Trait` は要求しか運ばず派生メソッドは流れない（`x#Ext` 明示）。
- **トレイト継承 `trait Sub: Super`（決定）**: Sub 準拠に Super 準拠を要求（`:` は `where` 制約と同記法）。**複数指定は `+`**（今セッションで `,` から変更＝`where T: A + B` と区切り統一。`+` は同一主語 `Self` への制約重ね、`,` は別主語の並びで supertrait では使わない）。**制約であって自動実装ではない** — `impl T as Sub` には別途 `impl T as Super` が要る（暗黙準拠を持たない方針の一貫）。**派生メソッドが拡張へ移った帰結**：トレイト由来の同名・同シグネチャ派生メソッド衝突は「型が両方をデフォルトに含めたとき」だけ＝その型の `default_extension` 宣言地点で報告（旧「継承強制 (1)／偶発 (2) の検出時点分岐」は撤回）。
- **オーバーロード許容（決定・Path 2／旧「演算子の多重実装は拡張で」「型引数廃止」を撤回）**: 同名メソッドを引数型で区別して複数定義可（inherent でも trait witness でも）。**根拠＝無名 impl が型のモジュールに閉じる**ので、衝突検出はモジュール単体ビルドでローカルに完結（Rust のグローバルコヒーレンス不要）。重なり得るジェネリック impl は保守的拒否（specialization 無し）。**Path 1（演算子だけ特別カテゴリ＋暗黙の構文トレイト）は却下** — 「演算子は本来メソッドの糖衣なのに特別扱いする根拠が無い／特別 trait が暗黙」。Rust が trait 必須なのは Rust の trait スコープ解決＋コヒーレンスゆえで、モジュール閉包の Plew には当てはまらない（cargo-cult 回避）→ Swift 流の inherent オーバーロードを採用。「うっかり準拠」は `impl as`＋`via` の明示準拠で別途防止（オーバーロードとは直交）。
- **関連型 associated type（決定）**: `type Name` で要求宣言、impl は `type Name = ConcreteType` で束ねる（`via` 不使用＝関連型はメソッド/フィールドのフラット名前空間とは別の**型の名前空間**）。外部射影は `T.Item`（`.`＝値メンバアクセスと同区切り）、制約束縛は `Trait[Item = Foo]`。Rust 実証済みモデルに合わせ、記号だけ Plew 流（`<>`→`[]`、`::`→`.`）。
- **トレイト型引数は維持（決定・一時「廃止」と判断したが撤回）**: オーバーロード許容＋モジュール閉包で多重 impl が安全に書けるので `Add[Rhs]` 等の型引数を残す。**入力（複数 conformance）＝型引数、出力（impl が一意に決める）＝関連型、両方持てる**。演算子はトレイト経由継続。
  - **変換は `As`→`From[Source]` に置換（決定）**: `as()`（引数なし・戻り型だけ違う）は引数オーバーロード規則に乗らないため、ターゲット側 `From[Source]` にする。`x as T`⟺`T.from(x: x)`、`try` のエラー変換も `From`。これで多変換先・多 source・`try` が自然に解決（旧「多重オペランド／多重変換」未決を解消）。`Coalesce` の 2 重 impl も復活＝valid。
  - **集約エラー enum の boilerplate はメタプログラミングで消す（決定）**: variant ラップの `From` は**コンパイラ特例の自動ラップにはせず、`Derive` 系メタプログラミングで生成**（Rust の `thiserror` 相当）。`try` の暗黙 `From` 機構は 1 つに保ち、手書き boilerplate だけ生成で消す（→ [spec/16](../spec/04-execution/16-metaprogramming.md)）。
- **数値リテラルは多相・文脈で確定・既定型なし（決定）**: 型は文脈（注釈・引数型・戻り型・被演算子型）で一意に定まったもの。**一意でなければエラー**（`val x = 42` も文脈ゼロ＝エラー）。Rust 的既定型は持たない（明示優先・幅安全）。**型付けは双方向（期待型を式に下ろす）のみで、変数の後続使用から宣言型を逆算する推論はしない**（コンパイラ負荷と可読性のため）。
  - **等価・順序・論理の演算子設計を確定（決定・今セッション）**: 当初の `Eq[Rhs]`/`Ne`/`Lt..Ge`（型引数つき比較）案を見直し、**等価＝`Eq`／順序＝`Ord: Eq` に統合し型引数を持たせない**。理由：等価/順序は同一型上の同値関係/全順序で、`impl A as Eq[B]`（異種）は対称律・反射律を型で守れず不健全。型引数を残すのは**両辺が別型になり得る**演算（`Add..[Rhs]`・`Index[Key]`・`Coalesce[Rhs]`・`From[Source]`）だけ、と境界を整理。
  - **浮動小数の NaN は比較時 panic（決定）**: `F32`/`F64` を全順序 `Ord`・全等価 `Eq` に準拠させ、NaN を比較した瞬間に **panic**。算術は IEEE 据え置き。**却下案**：(a) IEEE 忠実に黙って `false`（Swift 寄り・静かな footgun）、(b) `compare -> Optional[Ordering]` の部分順序（普通の型にまで `Optional` の儀式を強いる）、(c) 生成時 panic（**WASM に FP トラップが無く**全演算へソフトチェックが必要＋FFI で NaN 注入され不変条件が漏れる）。比較時 panic は移植可・低コストで、バグの瞬間にだけ大きく落ちる＝「隠れた footgun を嫌う」方針に最も合致。inf は全順序を壊さないので通常値。
  - **整数オーバーフローは常に panic・wrap は明示・意味論を変えるリリースビルドは持たない（決定・今セッション）**: 桁あふれは**全ビルドで panic**（Swift のトラップに合わせる）。ラップは明示（`&+`／`wrapping_add` 等・暫定）。整数 0 除算も panic（剰余符号は被除数＝truncated・→ [spec/12](../spec/03-expressions/12-operators.md)）。**却下：Go の silent wrap**（「静かな嘘を返さない」＝ NaN/暗黙変換と同方針に反する）。**却下：Rust の debug=panic/release=wrap**＝**意味論を変えるビルドモードを持たない**（`debug`/`release` は最適化レベル＝速度だけ・観測挙動は不変＝リリース限定バグを作らない＝開発しやすさ最優先）。Go にそもそも debug/release 区別が無い（常に最適化・overflow は常に wrap）ことも確認、Plew は「1 意味論＋最適化レベルのみ」を採る。**別腹（未決）**：`assert` の debug 除去（Swift `assert` vs `precondition` 型）は重い不変条件チェック向けに別途検討（オーバーフロー検査はこの枠ではなく常時 on）。
  - **`&&` / `||` は短絡する制御フロー（決定・トレイト化しない）**: `a && b ≡ if a { give b } else { give false }` の **`if` 糖衣**（Bool 専用・オーバーロード不可）。`And`/`Or` トレイトは廃止。**却下案**：(a) eager トレイト＝範囲チェック後の添字などガード idiom が壊れる/panic、(b) Swift の `@autoclosure` で lazy トレイト＝暗黙ラップ機構が要り「明示>暗黙」に反する。根拠：`&&`/`||` は右辺を評価するか左で決める＝`+` と評価戦略が違う**別カテゴリ（制御フロー）**なので特別扱いに筋が通る。`!`（`Not`）は eager なのでトレイトのまま。
  - **`panic` はキーワード（決定）**: `panic "メッセージ"` は発散する**文**（式ではないので `x ?? panic` は不可→`guard`/`match`）。メッセージは診断用 String のみ。回復不能用で catch 不可。**「`Never` を返す普通の関数を魔法で発散扱い」を却下**（見た目が関数なのに特別扱い＝暗黙を嫌う）。ユーザー可視の `Never` 型も導入せず、発散はフロー解析で扱う。**`spawn` 内 panic はプロセス全体を停止**。
  - **match アームのベア式形（決定）**: アーム右辺は ①ベア式 `=> expr` ②ブロック ③発散ブロックの 3 形式。`give` を毎回書かせず軽量にする。
  - **条件チェーン：if-let/while-let も束縛可・連結は `&&`（Rust let-chains 流／決定）**: `if`/`elif`/`while`/`guard` の条件を**条件チェーン**に統一。**却下案**：Swift の `,` 区切り＝`&&` を値レベル Bool 専用に保てるが新しい区切り意味を増やす＋既存 guard 例の書き換えコスト。**`&&` 採用の根拠**：(1) spec の guard が既に `&&` で一貫、(2) Plew は構造体生成が JSX 限定なので Rust 流の「条件位置で構造体リテラル禁止」制限が不要、(3) 値レベル `&&` はこの条件チェーンの〈全節 Bool〉特殊形と説明でき概念は一つ。**`&&`/`||` を制御フローにした判断との整合**：trait メソッドは引数が正格評価済みで届くので短絡は表現不能、ゆえに短絡は制御フロー側に置くのが必然。**by-name 引数（Scala `=> T`）も同根拠で却下**：呼び出し側に痕跡が残らない暗黙の非評価で「明示>暗黙」に反する（遅延が要ればクロージャか `<Lazy />` で明示）。

### トレイトを値型にする存在型（`any`・決定・→ [spec/08](../spec/02-type-system/08-traits.md)）
- **`any P` を導入**：トレイトを値の型として使える（型消去・動的ディスパッチ・異種混在）。動機は **Plew = Programming Language for Everyday Wizard**＝トレイトの配列を Swift のように素直に書けるべき、という根幹思想。`children: Array[any Component]` のような React 風ツリーが第一の用途（ジェネリック `[T]` は同種しか持てず不適、手書き型消去ラッパは構築側 boilerplate が重い）。**実装順は最後でよいが必ず実装する**。
- **マーカーは `any` のみ・`some`（opaque）は持たない**：`dyn`（Rust）でなく `any`（Swift）採用＝「動的ディスパッチ」という実装語でなく「準拠する任意の型」という概念を指し everyday wizard に自然。`some`/opaque を入れないのは、ユーザーが「`any`/`some` の使い分けはややこしい」と評したため＝マーカーは 1 つに絞る。**marker 必須の実利**：ジェネリック `where T: P` と存在型 `any P` が見た目で別物になり「横着して `n: P`」問題が解け、object-safety 違反の診断が `any` に紐づく。
- **形成は全型引数・全関連型を束縛必須**（決定）：**理由＝この縛りで `any P` 内に残る消去が `Self` ただ一つ**になり、呼び出し規則が単純化（関連型の共変再消去のような曖昧さを排除）。Rust の `dyn Trait<Assoc = …>` と同趣旨。
- **object-safety は型レベルの一律禁止でなくメンバ単位・使用箇所診断**（決定・modern Swift SE-0309 と同方向）：**却下＝旧 Swift 流の型レベル一律禁止**（「Eq は Self 要求があるので型にできない」は抽象的で分かりにくい、とユーザー評）。エラーを使用箇所に局所化し「2 つの `any Eq` は別型かもしれず比較不可」と具体的に出せる。
- **前回の雑な括りを訂正**：「Add/関係系は存在型にできない」は**完全適用すれば呼べる**（`any Add[I32,Output=I32]` で `+` 可）に訂正。本当に詰まるのは `Self` 入力と関連関数だけ。

### 文字列とコレクション（String / Array / Slice・→ [spec/02](../spec/01-basics/02-basic-types.md)）
- **`String` は不変・UTF-8 常に妥当・`==` はバイト等価（決定・今セッション）**: Swift/Rust/Go を比較した結論。**不変にした地金＝意味論からの帰結**：Plew は参照の値渡しで文字列は共有される＝「参照＋可変＋共有」は古典的エイリアス footgun（Ruby が抱える）。参照意味論なら不変が安全側で、`spawn` の「キャプチャ全 immutable」とも噛み合う。**却下：Swift の `==` 正準等価**（正規化コストが隠れる）＝明示原則に反する（要れば明示正規化、API 未決）。**却下：Go の「妥当性不変条件なし」**（保証が緩すぎ）＝「静かな嘘を返さない」方針。
- **`String = struct { pub(get) bytes: Array[U8] }`**: 内部表現がそのままバイト配列なので getter を生やさず**フィールドで公開**（方針：**stored は `pub(get)` フィールド、computed だけメソッド**）。不変条件は `pub(get)`（write 内部）＋任意バイトの公開 factory を持たない（生成はリテラルと検証 factory `from_bytes -> Result` のみ）で守る。
- **要素ビューは明示選択・型がコストを語る（決定）**: `bytes`（`Array[U8]`・`count` O(1)）／`scalars()`／`graphemes()`（イテレータ・`count()` O(n)）。`*_count()` を生やさず「配列 count=O(1)／イテレータ count()=O(n)」で自明にする（ユーザー発案）。**整数添字 `s[i]` は持たない**（可変長 UTF-8 で O(1) 添字は嘘。Swift/Rust も拒否）。Rust の `char`/Go の `rune` は**スカラ＝書記素でない**ので絵文字・結合列を割る罠があり、書記素を第一級で出せる Swift の長所だけ取り込む。
- **`Array[T]` 一本・`[E; N]`（const generics）は持たない（決定）**: 日常配列は動的・伸長・連続・プリミティブ unboxed（Java `int[]`／C# 配列モデル＝WASM ゼロコピーの前提）。**根拠**：`[E; N]` を実用にする＝const generics 必須で**型システムが一段重く紛らわしい**大物、しかも GC＋参照値の Plew では「インライン格納でスタック確保」という Rust の主動機が弱い。需要が固まれば**非破壊で後付け**できる（C#・Swift も後から InlineArray を足した前例）。
- **C 固定長配列はタプルでなく同型 `Array` に写す（決定）**: **C 配列は定義上ホモジニアス**なので、Swift が異種タプルに落としたのは「固定同型型が無かった」苦肉策。Plew は**同型は `Array[T]` へ（境界でコピー）**写す。
- **位置タプル廃止 → ラベル付きタプル（無名・構造的レコード）（決定・今セッション）**: **動機**＝「位置指向のタプルが、全部名前付きの言語で唯一の例外だった」を解消（構造体・enum バリアントは既に名前付きのみ＝`Some(T)` 不可）。**経緯（却下案）**：①無名 struct を JSX `<x=1/>` で生成する案は、分解パターンが bare `{…}` でブロックと衝突（JS の `({a,b}=o)` 問題）。②`${}` 記号は Perl 臭く型/生成/分解の 3 面がバラバラ。→ **タプル廃止で空いた `()` に置く**のが新記号ゼロ・`{}`（ブロック）と非衝突・「全部名前付き」と地続きで最良。
- **変数束縛は `val`＝新規・bare＝既存（決定・今セッション。分解・for へ拡張）**: スカラの「`val x` 宣言／`x =` 代入」を分解・`for` にも一般化（→ [spec/03](../spec/01-basics/03-values.md)）。**未初期化宣言は持たない**（Swift の `let x: T` 後分岐代入は `val x = if c { give 1 } else { give 2 }` で代替＝確定代入解析を持ち込まない）。文頭 bare `{` はブロックのまま（無名レコードが `()` なので衝突せずスコープ用独立ブロック文を温存）。
- **Slice / Substring は当面持たない（保留・additive）**: ゼロコピーのビュー型 `Slice[T]` と String の substring API は**入れない**。**手詰まりにならない根拠**：いずれも純粋に additive（Array 意味論も既存シグネチャも壊さず後付け可）。**マネージド言語の前例**：性能の答えは `[E; N]` でなく「連続バッファ＋ビュー」＝.NET `Span`／Java Panama `MemorySegment`／JS `TypedArray`／Python `memoryview`。スライス取得は（入れるなら）`[]` でなく**メソッド `arr.slice(...)`**（`[]` は要素値専用、view は名前付き操作で可視化）。**スライスを入れるなら 2 型**（所有伸長 `Array` ＋固定ビュー `Slice`＝C#/.NET 流）で Go の append-aliasing footgun を避ける案を本命とする。
- **文字列構築はビルダ（不変＋ビルダがワンセット）**: 逐次連結の O(n²) を避けるため、伸長可能ビルダで溜め確定時に不変 String へ封じる（Java `StringBuilder`／Go `strings.Builder`／Python join 型）。型名・API は未決。

### モジュールと無名 impl の配置（`part`・→ [spec/15](../spec/04-execution/15-modules.md)）
- **無名 impl の配置単位＝モジュール**と決定（impl 権はモジュールに紐づく）。無名 `impl T as Tr` は **T を定義したモジュール内にのみ**置ける（Rust の「型 or トレイト所有」より厳格な型所有版）。
- **却下した代替**: ① file = module（明示的だが impl を型と同一ファイルに強制＝窮屈）② directory = module（楽だが境界が暗黙）。「明示・非窮屈・新機構なしは2つまで」というトリレンマと認識し、明示最優先の方針に従って「新機構（`part`）を足して明示＋非窮屈」を選択。「impl は trait か struct を定義したモジュール内のみ」を厳格にすると単一ディレクトリでは狭すぎる、というのが directory 却下の決め手。
- **モジュール内はスコープ共有、外部 import はファイル単位**。暗黙の可視性を「明示的に綴じた part ツリー」の内側に限定することで、拒否したディレクトリ境界の暗黙性と区別する。
- **ディレクトリパスの解決＝`_.pw`**: 固定英単語（`Mod`/`Index`）や同名重複（`Foo/Foo.pw`）を避け、`_` は「ディレクトリ名をそのまま継ぐ代表ファイル」の意。**`_.pw` はディレクトリを集約せず単なる単一ファイルモジュール**。検索性低下は軽微（エディタで吸収）と判断して許容。
- **再エクスポート**: `export <path> with {...}`（`import` を付けず・ローカル非束縛＝JS の `export...from` 相当）。全取り込みは `with *`（`all` は snake_case メンバ名と衝突しうるため `*` を採用）。1ファイル1モジュールゆえ再エクスポートは必須で、公開 API の「バレル」構築に使う。

### パッケージ（分散・TOML マニフェスト・→ [spec/15](../spec/04-execution/15-modules.md)）
- **中央レジストリ無し**（Go modules / SwiftPM 思想）。各パッケージは **TOML マニフェスト**（暫定名 `Plew.toml`）を持ち、依存を **git / ローカルパス**で指定。
- **依存はローカル名に束縛**し `import @Name` で使う。上流のパッケージ名衝突は**消費側のローカル名**で解決（Cargo の rename / Go の replace 相当）。
- **公開エントリ＝`src/_.pw`**（マニフェストで上書き可）。`lib/` 案（Dart 風）も検討したが、Go のような lib/bin のソース分割を嫌い、Rust の `src/` に寄せて全ソースを `src/` に置く方針を採用。外部からは**エントリの公開物だけ**到達可（内部ファイル直接 import 不可＝カプセル化）。
- **実行エントリの規約は持たない**。ビルドはエントリを明示（`plew build ./src/entry.pw`）。
- **同一パッケージの複数バージョンは共存を許す方針**（依存解決ツールの詳細は実装時に別途）。

### メンバの可視性（型スコープ・2 段・→ [spec/05](../spec/02-type-system/05-structs-enums.md)）
- `pub` は**型のカプセル化のみ**を制御し、モジュール/パッケージ境界（`export`）とは直交する別軸。非公開（修飾なし）＝**その型の無名 impl からのみ**可視。
- **段階は 2 つだけ**（`pub(crate)` / `pub(super)` は「正しく使えた試しがない」として不採用）。兄弟モジュールが触りたいメンバは `pub` にする（＝外部にも見える）か、密結合コードを型のモジュールに `part` で同居させ無名 impl から触る。
- **非公開を見られるのは無名 impl だけ**。理由：拡張から非公開が見えると誰でも extension 経由で内部に到達でき `pub` が無力化する。外部に隠す必要は普遍的（不変条件の保証・リファクタ自由度）。Python の慣習 private 等「内部露出」は理想でなく弱点。

### `impl Type as Trait`（→ [spec/07](../spec/02-type-system/07-methods-impl.md)）
- `impl Trait for Struct`（Rust）は直後が trait か struct か文脈依存で気持ち悪い → **型主語**に統一。`as` は一度キャスト用途と衝突を懸念して `with` を検討したが、最終的に `impl Type as Trait` に回帰。
- ジェネリック実装は **`impl[...]` で型パラメータを前置宣言**。`impl[T]`（束縛）と `Struct[T]`（使用）を分けるので `impl Struct[I32]`（具体型への実装）と曖昧にならず、トレイト引数だけに現れる型変数（`impl[T] Vector as Mul[T]`）の置き場にもなる。当初案「型側ブラケットで暗黙束縛」は、トレイト引数限定の変数を書けず・具体型と曖昧で却下。

### ジェネリクスの記法（型パラメータ・制約・impl・→ [spec/06](../spec/02-type-system/06-generics.md)）
- **型パラメータの `[...]` は名前のみ**。**インライン制約 `[T: Trait]` は廃止**し、制約はすべて `where` に集約。理由：`[...]` が全宣言箇所で「名前だけ」に揃い `impl[T]` バインダと一貫、制約の置き場が一意（単純・明示）。代償＝単一制約が冗長（明示税）。supertrait `trait Sub: Super` と関連型宣言 `type Item: Format` の `:` は別構文なので残す。
- **`where` の述語は `型: 制約` のみ。型等価述語 `where T = I32` は持たない**。特定具体型への実装は型の位置に直接書く（`impl MyStruct[I32] as Trait`）。
- **「トレイト境界」→「トレイト制約」と呼ぶ**（`境界` は boundary の語に温存：モジュール／パッケージ境界・区間の境界条件 `i<b`・FFI 境界変換/境界コピー）。
- **デフォルト型引数（`[T = …]` / `Add[Rhs = Self]`）は持たない**（後付け additive）。Rust の実需は①演算子 `Rhs = Self`②末尾 policy 引数に集約されるが、Plew は①を明示 `Add[Self]` で書き、②は GC でアロケータ引数が無くハッシャ型も surface しないため不要。Rust の既定型引数は推論に参加しない狭い糖衣でもある。

### `assoc`（static 相当・→ [spec/07](../spec/02-type-system/07-methods-impl.md)）
- Plew の static メソッド/変数は **`assoc fn` / `assoc val`**（名前が違うだけで static と同等機能）。命名は `static`（不変と誤読）/ `class` / `ass` を却下し `assoc`（associated）に。
- **経緯（翻意）**：当初は「static は概念ごと不要（インスタンス非依存ならグローバル関数で足りる）」としたが、`Struct.new()` 等のニーズから `assoc` を採用＝**実質 static を持つ**方向に翻意。型に属さないトップレベル関数も別途存在するが、それは static の代替ではない（両方ある）。なお「グローバル**名前空間**」は無い（全定義はモジュールスコープ）。

### `@[...]` ディレクティブとメタプログラミング（方針転換・→ [spec/16](../spec/04-execution/16-metaprogramming.md)）
- **当初は閉じたメタプログラミング**: Rust の `derive` 相当の組み込みディレクティブのみで、ユーザーマクロは非公開（安全性・予測可能性・実装コストが理由だった）。
- **転換後**: ユーザー定義のメタプログラミングを可能にする。ビルドと独立した別コマンドで別ファイルへコード生成（go generate / build_runner 型）＋ マクロは `TokenStream` を入出力する構造体（`Derive` トレイト実装）として定義（Rust の手続きマクロ寄り）。
- 組み込みディレクティブは引き続き言語提供。命名は型由来で **PascalCase**（`Eq`/`Hash`/`Clone`/`Encode`/`Decode`/`DefaultFactory`/`All`）。理想は組み込みも `Derive` 実装構造体として同じ仕組みで提供すること。enum の `All`（生成メソッドは `Enum.all()`）は `@enumerable`/`@all_cases`/`@variants` を比較し `Enum.all` 直結案を採用。

### その他
- **キャスト `as`** は `From[Source]` の糖衣（`x as T`⟺`T.from(x: x)`）。暗黙変換は持たず、幅変更も明示 `as`（例外は `try` の `From` と数値リテラル多相）。唯一 newtype と元型間の `as` は From でなくゼロコスト再タグ（→ [spec/10](../spec/02-type-system/10-newtype.md)）。
- **ローカル変数の再宣言（shadowing）は Rust 流に無制限（決定）**: **却下案**：(B) 再利用はパターン束縛のみ・プレーン val はフレッシュ必須＝「パターンだけ同名可」という線引き自体が分かりにくい、(C) 全面禁止＝guard が窮屈。Rust 流は規則が単一（`name` は直近の宣言を指す）で、guard/match の絞り込みも特別扱いなしに導ける。「同名で別物を指す」恐怖は未使用束縛の lint で緩和。
- **コレクション名 `Array`**: `Vec` は日本語話者に数学のベクトル連想で直感的でないとして却下。
- **辞書リテラル**: Swift 風 `[k: v]`、空辞書は型推論不能を避けるため明示トークン `[:]`。
- **レンジ構文 `a..<b`／`a..=b`（決定・今セッション）**: 半開／閉を**両端とも記号で明示**し素の `..` を持たない（機構→ [spec/02](../spec/01-basics/02-basic-types.md)）。**却下**：Rust の bare `..`=半開（どちらが開かを覚える要）／Swift の `...`=閉（一目で分からない）／Kotlin の `..`=閉デフォルト（後から `..<` を足す羽目）。採用根拠＝`<`/`=` が境界条件 `i<b`/`i<=b` に対応する mnemonic で「開区間の記憶」footgun が消える（代償：`..`=半開の世界標準から外れる＝黙って半開より良い、半開ループが 1 文字長い＝明示税）。
- **JSX 属性に `{}` 不要**: 属性値は常に式として扱うため（JSX の `{}` は HTML 曖昧性回避という歴史的都合）。
- **`extern`**: 設計会話では `declare fn … from "libc"` 案を検討したが、最終文法は Rust 式の `extern "C" { … }` ブロックを採用。
- **`lazy`（遅延初期化）**: 専用構文は設けない。`<Lazy />` 構造体で表現する（言語仕様に載せなくても自然に実装できる単なる構造体）。
- **数値リテラルの基数・サフィックス**: 16/8/2 進（`0x`/`0o`/`0b`）・`_` 桁区切り・e 表記・型サフィックスを採用。Rust とほぼ同様だが型サフィックスは型名（PascalCase）なので `10U32` / `3.14F64`。
- **force-unwrap 演算子は無し**: 後置 `!` のような強制取り出しは持たない（文法に残る `UNARY_POSTFIX_OP` は遺物で再構築時に削除）。取り出しは `Optional`/`Result` の `unwrap` メソッドに留め、基本は非推奨。
- **冪乗演算子 `**` は導入しない**: `pow` で代替。Rust/Go/Swift と同様、右結合・優先順位の事故（`-2**2`）、戻り型/コストの不透明さ、演算子経済の観点から。冪乗は単一 CPU 命令でなく実体は関数呼び出しのため、安価な演算子の見た目を与えない。
- **演算子の優先順位・結合性（決定・今セッション）**: 14 段ラダーを規定（機構→ [spec/12](../spec/03-expressions/12-operators.md)）。**`as`・算術・ビット・比較・`&&`/`||` の相対順は Rust と一致**（一次資料 The Rust Reference で照合）。Plew 固有の判断：
  - **`??` は Swift 位置**（算術・ビット・`as` より弱く、比較・`&&`・`||` より強い・右結合）。**経緯**：当初「算術より強く（`(count??0)+1`）静かな嘘を防ぐ」を推したが、調査で **`??` を算術より上に置く主要言語は無い**（Swift/Kotlin/JS/C# すべて算術より下＝`count ?? 0 + 1`＝`count ?? (0+1)` は共通挙動）と判明し撤回。比較との上下は二陣営に割れる（Swift/Kotlin＝比較より上、JS/C#＝比較より下）が、`x ?? 0 == y`＝`(x??0)==y` と素直に読める Swift/Kotlin 陣営を採用。**却下**：JS の「`??` と `&&`/`||` の無括弧混在を構文エラー」＝Swift 流の一貫順序なら曖昧さが出ず、規則を増やす割に得が薄い。
  - **レンジは Rust 位置（最下位・非結合）**。Swift はレンジを `??` より強く置くが、Plew は最下位にした（`a ?? b ..< c`＝`(a??b)..<c`）。実用上レンジは限定文脈（`for … in`・`[]`・括弧内）にしか現れず端点に算術が先に結合するので害なし。
  - **ビット演算子は演算子として採用するが実装は後回し**＝今回は優先順位スロットのみ予約。「能力は不要では？」を再検討した結論：Lua(5.3 前)・OCaml・Scheme 等シンボル無しの前例はあるが、Plew は systems 言語かつ**自前 stdlib（UTF-8 の `scalars`/`graphemes`・ハッシュ・FFI）がビット演算を要求**するので能力は必須、論点は演算子 vs メソッドで演算子採用。C の罠（`x & 1 == 0`）回避のため Rust 同様「シフト>&>^>|・全部比較より上」。**`!`（論理 Not・`Bool` 専用）と `~`（`BitNot`・整数）を分離**（Rust の `!` は両用で紛らわしい）。
  - **`as` は算術より強い**＝暗黙数値変換が無く `a as I64 + b as I64` を多用するため。当初「Rust と違い Plew は `as` を書く頻度が高い」と差別化したが、**Rust も暗黙拡幅が無い点で同じ**と判明し差別化は撤回（位置の結論は Rust と同一）。
  - **前置 `try`/`await` の帰結**：後置チェーン全体に掛かる（`try a.b()`＝`try (a.b())`）。Rust の後置 `?` と逆で途中取り出しは `(try a).b()`。前置 `try` 採用（既決）の必然。
  - **比較・等価は非結合**（`a==b==c` が `Bool` の `Eq` で静かに通る誤読を防ぐ・Rust の "Require parentheses" と同じ）。
- **`Display` 廃止・`Format` 一本化（決定）**: 表示も文字列補間も `Format`（`fn format(format: String) -> String`）に統一。`{x}`⟺`x.format(format: "")`、`{x:.2}`⟺`x.format(format: ".2")`。役割重複を解消。
- **文字列補間は任意の値式・`:` 境界は括弧深さ 0（決定・今セッション）**: `{ 式 }` の中身は**任意の値式**（Rust のインライン捕捉が識別子限定なのと異なる）。**フォーマット境界の `:` 規則**＝補間内で**括弧入れ子深さ 0 のコロンだけ**が spec 開始（ラベル引数・レコードの `:` は必ず `()`/`[]` 内なので衝突せず、Plew は型注釈を式位置に持たない）。**却下した区切り**：`;`/`@`（規約性・可読性で劣る）・`|`（将来 `BitOr` と深さ 0 で衝突）。**補間内はブロック式・`match` 式を禁止**（閉じ `}` 対応を単純に保つ）。**波括弧リテラルは `{{`/`}}` 二重化**（Rust 同）。**複数行**：生改行はそのまま含み、**行末 `\` は改行＋次行先頭空白を除去**して折り返し（Rust 同）。
- **添字代入トレイト `IndexSet`（決定）**: `a[i] = x` ⟺ `mut fn index_set(key:, value:)`。Rust の `IndexMut` 相当だが、参照/借用が無く可変な場所を返せないので**可変参照ではなくセッター**。複合代入 `a[i] += x` は `Index`＋演算＋`IndexSet`。
- **`inout` の呼び出し側は `&`（決定）**: `f(param: &x)`。`mut` 束縛にのみ付けられ、「この呼び出しで変更され得る」ことを明示。
- **`async fn` は TypeScript 流（決定）**: 戻り型は `-> Promise[T]` と明示し、本体の `return e`（`e: T`）はコンパイラが `Promise[T]` に自動 wrap。`await` が開く。
- **Iterator / Iterable 分離（決定・今セッション）**: `Iterator`＝`mut fn next() -> Optional[Item]` の消費カーソル、`Iterable`＝`iterator()` で毎回新カーソルを産む。`for` は Iterable を回し（`Array`/辞書/レンジが準拠）、`Iterator` 自身も Iterable。**却下**：単一 Iterator（コレクション自身が `next`）＝値意味論で「自分のカーソル」を持てず多重走査不可。正確なシグネチャは未決。
- **ユニット型＝`()`（決定・今セッション）**: 名目 `Void` も `Void` エイリアスも作らず、ユニットは 0 要素ラベル付きタプル `()`。**根拠**：Java の「void は型でない」失敗（総称に乗らない）を避ける／0 フィールドなのでフィールドを畳むメタプログラミングで「0 個の基底ケース」として一様に扱え、別名・別型を設けない方が書き方が一通りで済む。

## 未決 / 今後決定すべき事項

実装を進める前に確認・確定が必要な点：

1. **チャネルの最終構文・型** — 方向（複数 Sender・`receive() -> Result[T, ChannelClosed]`・`Send`/`Clone` 境界不使用・`send` は immutable メソッド）は固まっているが、**所有権が無いため Receiver の単一所有は強制できない**（複数参照・複数 `receive` 可）。マルチコンシューマの意味論を含め **具体 API はコアライブラリ実装の課題**（言語コアの構文要素ではない）として stdlib 設計時に詰める。
2. **spawn/async の意味論実装** — モデルは確定（`spawn` はスレッド起動・ハンドル `join() -> Promise[T]`・キャプチャ全 immutable・立てたスレッドも単一ループ・全スレッド完了までランタイム生存）。実装課題は「キャプチャ全 immutable」の型チェック（セマンティクス層）。文法には `block_modifier: ASYNC | SPAWN` のみ。
3. **Mutex/sync/atomic の扱い** — 標準で提供しない（or `@unsafe` 限定）。旧文法の修飾子は削除済み。
4. **（解決済み）extension の継承・ネスト** — **両方とも禁止**（呼び出し位置での由来一意性＝Single Dispatch Resolution を保つため）。再利用は `self#A.foo()`、組み合わせは `value#A#B` で代替。複数拡張を 1 名にまとめる別名（`alias Web = Json + Http`）は**将来の非破壊追加候補として保留**。再エクスポートは一般シンボルと同じく許可で決着済み。
5. **（解決済み）オーバーロード解決** — 暗黙変換は**無し**（完全一致＋リテラル多相のみ、例外は `as` 明示と `try` の `From`。拡張ビュー変更 `A`↔`A#P` も `#`/`#!` 明示）、`via` 左辺は**常に完全シグネチャ**で要求を特定、逆方向推論なし、モジュール閉包でローカル判定。骨子確定。※残る検討は実装着手時の細部のみ。
6. **GC アルゴリズム** — GC 採用のみ決定、方式は未定。
7. **メタプログラミング / ディレクティブ詳細** — `Derive` トレイトのシグネチャ、`TokenStream` API、組み込みを `Derive` 実装で提供するか等（→ [spec/16](../spec/04-execution/16-metaprogramming.md)）。
8. **文法の細かい穴** — `@[...]` 内の空行・末尾カンマ、`match_case` 前の改行、`where_clauses` 末尾カンマなど（書き味レベル）。
9. **FFI の型マッピング** — `extern "c"` / `extern "javascript"` ブロックの構文は採用済みだが、Plew 型 ↔ C/JS 型の対応（数値・ポインタ/バッファ・文字列の境界変換、外部由来の `NaN` 流入の扱いなど）は未策定。C 固定長配列は当面**境界コピーで `Array[T]`** に写す方針（→ [spec/15](../spec/04-execution/15-modules.md)）。
10. **文字列・配列の保留 API（すべて additive）** — 骨子（不変 String・`bytes` 公開・`Array[T]` 一本・`==` バイト等価・`scalars`/`graphemes` イテレータ・FFI はコピー）は確定。以下は後から非破壊で足す：(a) **文字列ビルダ**の型名・API、(b) **正規化 API**、(c) **`Slice[T]`（ビュー型）とゼロコピー部分文字列／FFI**（入れるなら所有 `Array`＋固定ビュー `Slice` の 2 型・取得は `arr.slice(...)`）、(d) **String の substring API**（まずはコピー版）、(e) **片側レンジ**（`a..`/`..<b`）・`step`・**レンジパターン**・スライス糖衣 `arr[..<n]`・**`Step` trait の定義と反復プロトコルの正確なシグネチャ**（`Iterator`（`mut next`）と `Iterable`（`iterator()`）の 2 層分離は決定済み＝上記「その他」。残るは各メソッドの厳密な型）、(f) **固定長配列 `[E; N]` / const generics**。
11. **言語アイテム（lang item）の正確な一覧** — 「構文が意味として参照する型/トレイトは import 不要で常にスコープ・それ以外は明示 import」は決定。残るは**正確な一覧の確定**（数値型・`Bool`・`String`・`Array`・`Optional`・`Result`・レンジ 2 型・`Promise`/スレッドハンドル・`Add`/`Eq`/`Ord`/`From`/`Iterator`/`Step` … をどこまで含めるか）と、コンパイラの lang-item スロットとコアライブラリ定義の対応付け（実装フェーズ）。マニフェスト既定 import は当面不採用＝additive で後付け可。
12. **`assert` の debug 除去とビルドプロファイル** — 整数オーバーフロー/0 除算/NaN 比較は**常時 panic**（最適化レベルで意味論不変・リリース限定バグなし）で決着。残るは「重い不変条件チェックを最適化ビルドで外す」需要への対応＝`assert`（debug のみ）vs 常時チェック（`precondition` 相当）の二段を用意するか、名称、ビルドプロファイルの定義。**ラップ演算子/メソッドの正式名**（`&+`/`wrapping_add` 暫定）もここで確定する。
13. **複合代入 `+= -= *= /=` の脱糖規則** — 優先順位は確定（代入は文で優先順位に乗らない・[spec/12](../spec/03-expressions/12-operators.md)）。**文章化はするが詳細は後回し**（ユーザー指示）：脱糖を `a OP= b` ⟺ `a = a OP b` の純粋糖衣にするか（`AddAssign` 相当の専用トレイトを持たない案・参照値意味論＝`IndexSet` と同方針）、成立条件（`mut val` 等の代入可能な場所＋演算子トレイト実装＋`Output` が左辺型と一致）、場所の 1 回評価（`a[f()] += x` の `f()` を二重評価しない）、`%=` を提供するか（現行 `ASSIGN_OP` は `= += -= *= /=` で `%=` 無し）、ビット演算追加時の `&= ^= |= <<= >>=`。`a[k] += x` の Index＋演算＋IndexSet 展開は [spec/12](../spec/03-expressions/12-operators.md) に既出。

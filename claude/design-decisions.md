## 言語の目的（全制約の出発点）

- モノレポでサーバー（Go 的）とフロント（React 的）を 1 言語で書き、モデル層を共有する。
- **コンテナのコールドスタートが速い**ことが第一目的 → AOT ネイティブ / WASM、軽量ランタイム志向。
- 「Rust から所有権を引いた書き味」が理想。所有権・借用・ライフタイムは**明確に不採用**。
- この「参照の値渡し + GC + 所有権なし」が、並行性・拡張・ロック周りの議論すべての根本にある。

## 主要な判断と根拠

### 参照の値渡し + `inout`
- 「全部参照渡し」は副作用がシグネチャから見えない/競合/不変性を強制できない、として却下。可変性と `inout` を構文で明示する方向に。
- 引数の `mut` は「関数内ローカルの再代入可能性（副作用なし）」と誤解されるため不採用。Swift の `inout`（呼び出し元を書き換える意図が明確）を採用。Ada / C++ `&` / Nim `var` / D `ref` も比較。

### 並行性: spawn キャプチャ問題（大きな方針転換）
- 初期案は変数宣言種別（`let` / `let mut` / `let sync` / `atomic`）でスレッド安全性を制御するものだった。
- **破綻例**（`examples/main.pw` の元ネタ）:
  ```plew
  mut val a = <T s=<S x=42 /> />
  sync val b = a            // 参照の値渡しで a をコピー
  spawn { b.lock().s.x += 1 }
  a.s.x += 1                 // a と b は参照先を共有 → 競合
  ```
  参照の値渡しゆえ、`sync` でラップしても元の参照経由で競合可能。さらに `Mutex.lock()` は内部可変性で不変参照から呼べるため、構文・型レベルで `mut` を禁止しても競合は防げない、と判明。
- **最終結論（Go 寄り）**: spawn キャプチャは全 immutable（**例外なし**）、`Mutex`/`sync val` は標準で提供しない（あるいは `@unsafe` 限定で非推奨）。「可変共有」はしない ── スレッド間は immutable な `Sender` の `send`（immutable メソッド）で**値を送る**（"share memory by communicating"）。チャネルの `Sender` も他と同じく immutable にキャプチャされる＝免除ではない。実バッファ操作はチャネル内部（コア）が担い、公開面は immutable に保つ。
- **モデル確定（async/spawn）**: 基盤は JS と同じ単一プロセス・単一スレッド + イベントループ（`async`/`await` = Promise）。重い処理は `spawn { … }` で**スレッド**を起動（「プロセス」ではない）。**立てたスレッド自身も単一スレッド + イベントループ**（Web Worker 的に内部で async 可）。
- **spawn の戻り＝ハンドル構造体（決定）**: `spawn { give … }` は **`join() -> Promise[T]`** を持つ構造体（暫定 `Thread[T]`）を返す。`await handle.join()` で join ── イベントループを素朴にブロックせず譲る（async/await と同じ機構でスレッド完了を観測）。別スレッドからの値取得はこの `join` が標準。**detached**（ハンドル未束縛）でもスレッドはブロックを完走（スレッド側から detached は不可視・結果は捨てられる）。**ハンドルはスレッドを所有しない**（未束縛/GC でも死なない。寿命をハンドル到達可能性に紐づけると GC タイミングで突然死＝不可）。**プログラム終了はランタイムが全スレッド完了を待ってから**（(i)。Go の「main 終了で goroutine kill」footgun を避ける。将来 daemon 指定の余地）。
- チャネル方針: **複数 Sender**。ただし **Plew は所有権が無いので Rust の「Receiver は単一所有」を強制できない** ── `Receiver` も参照の値渡しで複数箇所が持て、`receive()` も複数回呼べる。マルチコンシューマの意味論（競合 vs ファンアウト）は未確定。`recv()` は `Result[T, ChannelClosed]` 方向。**具体 API はコアライブラリ実装で詰める**（言語コアの構文要素ではない）。`send` は immutable メソッド（上記）。
- **`Send`/`Clone` を境界に使わない**: Rust の `Send` は所有権・move 前提のマーカートレイトで、所有権が無く「spawn キャプチャ全 immutable」で割り切る Plew では不要。スレッド安全性はその割り切りで担保し、多重 Sender も `Clone` 境界ではなく型固有の操作として与える（`Clone` トレイト自体は値の複製用として別途存在するが、チャネルの方向制御の手段にはしない）。
- GC では `Drop` による自動 unlock が使えない（スコープ脱出 ≠ 即時破棄）ことも Mutex を標準に入れない判断を後押しした。

### 拡張システム（記法が最も二転三転した）
- 解決したかった Rust の DX 課題: (1) 1 メソッドのために trait+impl は冗長、(2) 呼び出し側がファイル頭の `use` を見ないと由来が分からない。
- 核心アイデア: **拡張元を呼び出し位置で明示**する（import スコープに依存させない）。
- **外部型への実装は拡張に強制**: 無名 impl は「**型を所有**」が必須（Rust の「型 or トレイト」より厳格）。外部型への実装はトレイト所有を問わず（外部×外部も、自分のトレイト×外部型も）すべて拡張。理由：外部型への無名トレイト impl は呼び出しで `#` 修飾が要り「実質拡張」になる上、明示拡張と並存すると経路が二重化するため、一律拡張に寄せて `#Ext` に一本化。`#Ext` は**型の一部**（`ImportedStruct#Ext`）でジェネリックにも決定論的に流れ、別実装は別型として区別（禁止でなく型で区別）。素の外部型は当該トレイトを満たさず、使用箇所で `#Ext` 適用が要る。
- 記法変遷: `[..].average#crate()` → 区切りを `@` に（メアド連想）→ 演算子・引数渡しで明示できない問題で `value@Ext.call()` を断念 → レシーバ後置 `value@Extension.call()` → スコープを `namespace { … }` で区切る → 広すぎるので **`extension`** キーワードに。**最終文法では区切りは `#`**（`@` は会話上の議論）。
- **Single Dispatch Resolution Rule**: `#Ext` を必須にすることで C++ 的ダイアモンド曖昧性は原理的に起きない。危険が出るのは `#Ext` 省略糖衣 / extension の継承・ネスト / 暗黙 trait dispatch を入れたとき → これらは禁止/制限する。**拡張の再エクスポートは安全で許可**（拡張も import 必須で、`#Ext` は各ファイルでスコープ内の一意な名前に解決される＝一般シンボルと同じ扱い。当初 re-export を危険リストに入れていたのは誤りで撤回）。

### トレイトのフィールド + `via`、トレイト準拠モデル
- computed property（getter 地獄）が嫌い、という動機でトレイトにフィールド定義を許す（構造的制約として機能）。Rust が避ける理由（メモリレイアウト/衝突）は理解の上で採用。
- 代償: フィールド要求トレイトは外部型に実装できない（Rust の orphan rule より強い制限）。妥協策が `via` フィールドエイリアス。`via`/`<-`/`=:` を比較し `via` 採用。
- **準拠モデル（方針確定）**: 型はセレクタ（名前＋ラベル）ごとの**オーバーロード集合**を持つ（同一シグネチャは一意・引数型で区別。当初の「単一フラット名前空間」は後述のオーバーロード許容で緩和）。準拠は `impl Type as Trait` を**明示宣言**し、フィールド・メソッドを問わず **全要求を `via` で実体メンバに束ねる**（名前一致でも省略不可）か、メソッドは impl 内で本体定義する。
  - **却下**: ① Swift 方式（同名・同シグネチャの既存メソッドが暗黙に witness）→「うっかり準拠」が怖い。② Rust 方式（inherent と trait で別名前空間、`fn baz() { return self.baz() }` の自己委譲が意味不明）。`via` 束縛は両者の中間で、**ベアの呼び名を保ったまま明示**でき、自己委譲の奇習も消える。
  - **別名はベアでも可視**（決定）: 要求名と実体名が違う `via` は要求名をベアの呼び名として追加。トレイトとして呼べてベアで呼べないのは不合理、という理由。同セレクタ・同シグネチャの衝突はエラー（引数違いは共存）。
  - **`via` 左辺は常に完全シグネチャ（決定）**: `fn write(data: Bytes) -> Result[I32, Error] via write_bytes` のように、要求の完全シグネチャ（メソッドは引数ラベル・型・戻り型、フィールドは型）を毎回書く。本体定義形（`fn f() -> T { … }`）と対称で、トレイト未参照でも各行の意味が分かり、同名要求が複数（要求のオーバーロード）でも一意に witness できる。「名前だけ／稀にシグネチャ」の特例を避けた（ルールは 1 つ）。target がオーバーロードなら左辺シグネチャで一致する overload を選ぶ。
  - **define-once**（本体定義は一箇所、他は `via`）、**シグネチャ一致必須**、**1 メンバで複数トレイト witness 可**。**同名・同シグネチャ**で別挙動が要るときは名前付き `extension` + `#Ext`。同名でも**引数型が違えばオーバーロードとして共存**（→ 後述「オーバーロード許容」）。拡張は同一シグネチャの同名も `#Ext` で曖昧化できる。
- **提供メソッド（本体あり）は許可、ただし上書き不可（決定）**: 「デフォルト実装」が束ねる2役割を分離した。① 派生メソッド（`Iterator` の `map`/`filter` を `next` の上に組む類）＝実需の9割、`.map().filter()` チェーンに必須 → **採用**。② 上書き可能な既定（フック/性能特殊化）→ **不採用**。理由：唯一の実需が性能特殊化だが Plew は性能より開発容易性を優先、かつ Swift の protocol extension（静的 vs 動的ディスパッチの食い違い）の罠そのもの。本体の有無で「抽象な要求」か「固定の提供メソッド」かをトレイト作者が明示選択し、中間の「既定だが上書き可」を消す。提供メソッドはオーバーロード集合に加わり、同セレクタ・同シグネチャで衝突→`#Ext`（引数違いは共存）。準拠側 impl が witness するのは要求のみ（上書きは不可、変えたければ `extension`+`#Ext`）。`via` ルールはむしろ純化（"既定に頼る" 抜け道が消え全要求が明示 witness）。
- **トレイト継承 `trait Sub: Super`（決定）**: Sub 準拠に Super 準拠を要求（`:` は `where` 境界と同記法）。**制約であって自動実装ではない** — `impl T as Sub` には別途 `impl T as Super` が必要で、親準拠は暗黙生成しない（暗黙準拠を持たない方針の一貫）。Sub の提供メソッドは self 経由で Super のメンバを呼べる。ダイヤモンドの同名要求はオーバーロード集合に入り同シグネチャなら畳まれ（不一致は共存）、同一シグネチャの別トレイト由来提供メソッド衝突はエラー→`#Ext`。
- **オーバーロード許容（決定・Path 2／旧「演算子の多重実装は拡張で」「型引数廃止」を撤回）**: 同名メソッドを引数型で区別して複数定義可（inherent でも trait witness でも）。**根拠＝無名 impl が型のモジュールに閉じる**ので、衝突検出はモジュール単体ビルドでローカルに完結（Rust のグローバルコヒーレンス不要）。解決規則：セレクタ（名前＋順序付きラベル）でまず分け、同セレクタ内は ①型引数の形が全員一致 ②具体位置でのみ区別 ③境界は曖昧化に使わない。重なり得るジェネリック impl は保守的拒否（specialization 無し）。これで開世界の重なり問題を回避（境界・型引数で曖昧化しないため）。**Path 1（演算子だけ特別カテゴリ＋暗黙の構文トレイト）は却下** — 「演算子は本来メソッドの糖衣なのに特別扱いする根拠が無い／特別 trait が暗黙」が理由。Rust が trait 必須なのは Rust の trait スコープ解決＋コヒーレンスゆえで、モジュール閉包の Plew には当てはまらない（cargo-cult 回避）→ Swift 流の inherent オーバーロードを採用。「うっかり準拠」は `impl as`＋`via` の明示準拠で別途防止（オーバーロードとは直交）。
- **関連型 associated type（決定）**: `type Name` で要求宣言、シグネチャ中はベア参照、impl は `type Name = ConcreteType` で束ねる（`via` 不使用＝関連型はメソッド/フィールドのフラット名前空間とは別の**型の名前空間**）。**境界可** `type Item: Display`（ベアは境界なし）。**外部射影は `T.Item`**（`.` ＝値のメンバアクセスと同じ区切り、文法 `type_use` も `.` 連結なので素直）。**境界での束縛は `Trait[Item = Foo]`**（Rust の `<Item = Foo>` 相当。supertrait/`where`/引数境界で共通）。Rust 実証済みモデルに合わせ、記号だけ Plew 流（`<>`→`[]`、`::`→`.`）。
- **トレイト型引数は維持（決定・一時「廃止」と判断したが撤回）**: オーバーロード許容＋モジュール閉包で多重 impl が安全に書けるので、`Add[Rhs]` 等の型引数を残す。**入力（複数 conformance）＝型引数、出力（impl が一意に決める）＝関連型、両方持てる**（`Add[Rhs] { type Output }`）。トレイト名の `[...]` は位置型引数＋関連型束縛（`Iterator[Item=Foo]`）の混在（Rust の `Trait<Arg, Assoc=T>` 同形）。演算子はトレイト経由継続（`a+b`⟺`a.add(rhs:b)`、`Add[Rhs]` を rhs 型でオーバーロード解決）。`Coalesce[Rhs]`・`Index[Key]` も型引数で多重 impl（`?? T`/`?? Optional`、複数キー型）。
  - **変換は `As`→`From[Source]` に置換（決定）**: `as()`（引数なし・戻り型だけ違う）は引数オーバーロード規則に乗らないため、ターゲット側 `From[Source] { assoc fn from(x: Source) -> Self }` にする。`x as T`⟺`T.from(x: x)`、`try` のエラー変換も `From`（ターゲットは `as` の `T`／関数戻りエラー型で常に明示、ソース型でオーバーロード解決）。これで多変換先・多 source・`try` が自然に解決（旧「多重オペランド／多重変換」未決を解消）。`Coalesce` の 2 重 impl も復活＝valid。
  - **集約エラー enum の boilerplate はメタプログラミングで消す（決定）**: `enum AppError { Parse{e:ParseError} Io{e:IoError} }` に対する `From[ParseError]`/`From[IoError]`（variant ラップ）は、**コンパイラ特例の自動ラップにはせず、`Derive` 系メタプログラミングで `From` 実装を生成**する（Rust の `thiserror` 相当）。`try` の暗黙 `From` 機構は 1 つに保ち、手書き boilerplate だけ生成で消す。実装はメタプログラミング章＝最後（→ [spec/12](../spec/12-metaprogramming.md)）。
- **数値リテラルは多相・文脈で確定・既定型なし（決定）**: リテラルは組み込み数値型（整数 `I8…U64`／小数 `F32`/`F64`）に多相で、型は文脈（注釈・引数型・戻り型・被演算子型）で一意に定まったもの。**一意でなければエラー**（`val x = 42` も文脈ゼロ＝エラー、`val x: I32 = 42`/`42I32` を要求）。Rust 的既定型は持たない（明示優先・幅安全）。オーバーロード解決ではリテラルを数値互換な候補に絞り、2 つ以上残れば曖昧エラー＝健全性維持。ユーザー定義型は対象外。サフィックスは型名直後付け（`42I32`/`3.14F64`）。**型付けは「期待型を式に下ろす」双方向型付けのみ**（注釈・引数型・戻り位置・被演算子から）。**変数の後続使用から宣言型を逆算する推論はしない**（コンパイラ負荷と可読性のため）＝ `mut val count = 0` は後で `return count` されても宣言時点で文脈ゼロ＝エラー（`count: I32 = 0` と書く）。
  - **等価・順序・論理の演算子設計を確定（決定・今セッション）**: 当初の `Eq[Rhs]`/`Ne`/`Lt..Ge`（型引数つき比較）案を見直し、**等価＝`Eq { fn eq(rhs: Self) -> Bool }`（`!=`は`!(==)`）／順序＝`Ord: Eq { fn compare(rhs: Self) -> Ordering }`（`< <= > >=`は`compare`に展開）に統合し、型引数を持たせない**。理由：等価/順序は同一型上の同値関係/全順序で、`impl A as Eq[B]`（異種）は対称律（`B as Eq[A]`が要る）・反射律を型で守れず不健全。型引数を残すのは**両辺が別型になり得る**演算（`Add/Sub/Mul/Div[Rhs]`・`Index[Key]`・`Coalesce[Rhs]`・`From[Source]`）だけ、と境界を整理。`@[Eq]` は `impl T as Eq` を合成。
  - **浮動小数の NaN は比較時 panic（決定）**: `F32`/`F64` を全順序 `Ord`・全等価 `Eq` に準拠させ、NaN を比較（`==`・`<` 等＝`eq`/`compare`）した瞬間に **panic**。算術は IEEE 据え置きで NaN/inf を生成、判定は `is_nan()`。**却下案**：(a) IEEE 忠実に黙って `false`（Swift 寄り・静かな footgun）、(b) `compare -> Optional[Ordering]` の部分順序（普通の型にまで `Optional` の儀式を強いる）、(c) 生成時 panic（**WASM に FP トラップが無く**全演算へソフトチェックが必要＋FFI で NaN 注入され不変条件が漏れる）。比較時 panic は移植可・低コストで、NaN 比較というバグの瞬間にだけ大きく落ちる＝「隠れた footgun を嫌う」方針に最も合致。inf は全順序を壊さないので通常値。
  - **`&&` / `||` は短絡する制御フロー（決定・トレイト化しない）**: `a && b ≡ if a { give b } else { give false }` の **`if` 糖衣**（Bool 専用・オーバーロード不可）。`And`/`Or` トレイトは廃止。**却下案**：(a) eager トレイト＝`while i<n && p(arr[i])`・範囲チェック後の添字などガード idiom が壊れる/panic、(b) Swift の `@autoclosure` で lazy トレイト＝暗黙ラップ機構が要り「明示>暗黙」に反する。根拠：`&&`/`||` は右辺を評価するか左で決める＝`+` と評価戦略が違う**別カテゴリ（制御フロー）**なので特別扱いに筋が通る。`!`（`Not`）は eager なのでトレイトのまま。ビット演算は将来 `BitAnd`/`BitOr` を `&`/`|` に（未提供）。
  - **`panic` はキーワード（決定）**: `panic "メッセージ"` は発散する**文**（`return`/`break` と同じ制御フロー。式ではないので `x ?? panic` は不可→`guard`/`match`）。メッセージは診断用 String のみ・型付き値は運ばない。回復不能用で catch 不可（回復可能な失敗は `Result`/`try`）。**「`Never` を返す普通の関数を魔法で発散扱い」を却下**（見た目が関数なのに特別扱い＝暗黙を嫌う）。ユーザー可視の `Never` 型も導入せず、発散はフロー解析で扱う。**発散規則**：全経路が `panic`/`return`/`break`/`continue` で抜けるブロックは値を生まず `give` 不要で任意の期待型と適合（`if`/`match` の発散アーム）。**`spawn` 内 panic はプロセス全体を停止**（スレッド単位の失敗は `Result`+`join()`）。
  - **match アームのベア式形（決定）**: アーム右辺は ①ベア式 `=> expr` ②ブロック `=> { …; give x }` ③発散ブロック `=> { … panic … }` の 3 形式。`give` を毎回書かせず軽量にする。
  - **条件チェーン：if-let/while-let も束縛可・連結は `&&`（Rust let-chains 流／決定）**: `if`/`elif`/`while`/`guard` の条件を**条件チェーン**に統一。`&&` で Bool 節と反証可能束縛 `PATTERN = expr` を連結、左→右短絡、先行束縛は後続節と本体で有効、束縛節は `||` 不可（Bool 節内の `||` は自由）。**却下案**：Swift の `,` 区切り＝`&&` を値レベル Bool 専用に保てるが新しい区切り意味を増やす＋既存 guard 例の書き換えコスト。**`&&` 採用の根拠**：(1) spec の guard が既に `&&` で採用済みで一貫、(2) Plew は構造体生成が JSX 限定なので Rust 流の「条件位置で構造体リテラル禁止」制限が不要で素直に入る（`if foo {` の `{` が常に本体）、(3) 値レベル `&&` はこの条件チェーンの〈全節 Bool〉特殊形と説明でき概念は一つ（脱糖は別）。**`&&`/`||` を非トレイト＝制御フローにした判断との整合**：trait メソッドは引数が正格評価済みで届くので短絡は表現不能（短絡には by-name 引数が要る）、ゆえに短絡は制御フロー側に置くのが必然。**by-name 引数（Scala `=> T`）も同根拠で却下**：呼び出し側に痕跡が残らない暗黙の非評価で「明示>暗黙」に反する。遅延が要るならクロージャ `() -> T` か `<Lazy />` で明示する。

### モジュールと無名 impl の配置（`part`）
- **無名 impl の配置単位＝モジュール**と決定（impl 権はモジュールに紐づく）。無名 `impl T as Tr` は **T を定義したモジュール内にのみ**置ける（Rust の「型 or トレイト所有」より厳格な型所有版。外部型への実装はトレイト所有を問わず拡張 `#Ext`）。import するとモジュールの型とその無名 impl が同伴（impl 単独 import は無い）。
- **モジュール = ルート + `part` で推移的に綴じたファイル群**（片側宣言・ネスト可・forest・ディレクトリ跨ぎ可・part 先は独立 import 不可）。`import`=別モジュール参照、`part`=同一モジュールに綴じ込む。
- **却下した代替**: ① file = module（明示的だが impl を型と同一ファイルに強制＝窮屈）② directory = module（楽だが境界が暗黙）。「明示・非窮屈・新機構なしは2つまで」というトリレンマと認識し、明示最優先の方針に従って「新機構（`part`）を足して明示＋非窮屈」を選択。「impl は trait か struct を定義したモジュール内のみ」を厳格にすると単一ディレクトリでは狭すぎる、というのが directory 却下の決め手。
- **モジュール内はスコープ共有、外部 import はファイル単位**。暗黙の可視性を「明示的に綴じた part ツリー」の内側に限定することで、拒否したディレクトリ境界の暗黙性と区別する。
- **ディレクトリパスの解決＝`_.pw`**: ディレクトリを指す `import`/`part` はその中の `_.pw` に解決される。固定英単語（`Mod`/`Index`）や同名重複（`Foo/Foo.pw`）を避け、`_` は「ディレクトリ名をそのまま継ぐ代表ファイル」の意。**`_.pw` はディレクトリを集約せず単なる単一ファイルモジュール**（`Models/_.pw` と `Models/User.pw` は別物）。検索性低下は軽微（エディタで吸収でき、移動はパス／シンボル基準）と判断して許容。拡張子は `.pw`。
- **再エクスポート**: `export <path> with {...}`（`import` を付けず・ローカル非束縛＝JS の `export...from` 相当）。全取り込みは `with *`（`all` は snake_case メンバ名と衝突しうるため `*` を採用）。1ファイル1モジュールゆえ再エクスポートは必須で、公開 API の「バレル」構築に使う。拡張も一般シンボルと同様に再エクスポート可（SDR 上も安全）。

### パッケージ（分散・TOML マニフェスト）
- **中央レジストリ無し**（Go modules / SwiftPM 思想）。各パッケージは **TOML マニフェスト**（暫定名 `Plew.toml`）を持ち、依存を **git / ローカルパス**で指定。
- **依存はローカル名に束縛**し `import @Name` で使う。上流のパッケージ名衝突は**消費側のローカル名**で解決（Cargo の rename / Go の replace 相当）。
- **公開エントリ＝`src/_.pw`**（マニフェストで上書き可）。`lib/` 案（Dart 風で「lib = 公開面」）も検討したが、Go のような lib/bin のソース分割を嫌い、Rust の `src/` に寄せて全ソースを `src/` に置く方針を採用。外部からは**エントリの公開物だけ**到達可（内部ファイル直接 import 不可＝カプセル化）。
- **実行エントリの規約は持たない**。ビルドはエントリを明示（`plew build ./src/entry.pw`）。
- **同一パッケージの複数バージョンは共存を許す方針**（依存解決ツールの詳細は実装時に別途）。

### メンバの可視性（型スコープ・2 段）
- `pub` は**型のカプセル化のみ**を制御し、モジュール/パッケージ境界（`export`）とは直交する別軸。`pub`＝型を見られる所から可視、`pub(get)`＝読み取りのみ公開（書き込みは内部）、非公開（修飾なし）＝**その型の無名 impl からのみ**可視。
- **段階は 2 つだけ**（`pub(crate)` / `pub(super)` は「正しく使えた試しがない」として不採用）。兄弟モジュールが触りたいメンバは `pub` にする（＝外部にも見える）か、密結合コードを型のモジュールに `part` で同居させ無名 impl から触る。
- **非公開を見られるのは無名 impl だけ**。名前付き拡張（`#Ext`、自型・他型問わず）・非 impl コード・他型は pub のみ。理由：拡張から非公開が見えると誰でも extension 経由で内部に到達でき `pub` が無力化する。外部に隠す必要は普遍的（不変条件の保証・リファクタ自由度＝消費者は制御外）。Python の慣習 private 等「内部露出」は理想でなく弱点。

### `impl Type as Trait`
- `impl Trait for Struct`（Rust）は直後が trait か struct か文脈依存で気持ち悪い → **型主語**に統一。`as` は一度キャスト用途と衝突を懸念して `with` を検討したが、最終的に `impl Type as Trait` に回帰。
- ジェネリック実装は型引数を型側に付ける（`impl Struct[T: Display] as Trait[T]`）。「書く順が逆だから `for` 不要で破綻しない」が鍵。

### `assoc`（static の不採用）
- 「static メソッド/変数」という概念自体が無意味（インスタンス非依存ならグローバル関数でよい）。ただし `Struct.new()` のニーズはあるので `assoc`（associated）を採用。`static`（不変と誤読）/ `class` / `ass` は却下。

### `@[...]` ディレクティブとメタプログラミング（方針転換）
- **当初は閉じたメタプログラミング**: Rust の `derive` 相当の組み込みディレクティブのみで、ユーザーマクロは非公開（安全性・予測可能性・実装コストが理由だった）。
- **転換後**: ユーザー定義のメタプログラミングを可能にする。ビルドと独立した別コマンドで別ファイルへコード生成（go generate / build_runner 型）＋ マクロは `TokenStream` を入出力する構造体（`Derive` トレイト実装）として定義（Rust の手続きマクロ寄り）。詳細・未決は [spec/12-metaprogramming.md](../spec/12-metaprogramming.md)。
- 組み込みディレクティブは引き続き言語提供。AST ノードに属性リストを持たせ、対応するトランスフォーマをコンパイルフェーズで走らせる（型保証/補完を壊さない）。命名は型由来で **PascalCase**（`Eq`/`Hash`/`Clone`/`Encode`/`Decode`/`DefaultFactory`/`All`）。理想は組み込みも `Derive` 実装構造体として同じ仕組みで提供すること。
- enum の `All`（生成メソッドは `Enum.all()`）は `@enumerable`/`@all_cases`/`@variants` を比較し、`Enum.all` に直結する案を採用。

### その他
- **キャスト `as`** は `From[Source]` の糖衣（`x as T`⟺`T.from(x: x)`）。暗黙変換は持たず、幅変更も明示 `as`（例外は `try` の `From` と数値リテラル多相）。唯一 newtype と元型間の `as` は From でなくゼロコスト再タグ。
- **ローカル変数の再宣言（shadowing）は Rust 流に無制限（決定）**: 同名 `val`/`mut val` を再宣言/shadow 可（新束縛・型/可変性変更可・直近の宣言が有効）。**却下案**：(B) 再利用はパターン束縛（guard/match/if）のみ・プレーン val はフレッシュ必須＝「パターンだけ同名可」という線引き自体が分かりにくい、(C) 全面禁止＝guard が窮屈。Rust 流は規則が単一（`name` は直近の宣言を指す）で、guard/match の絞り込みも特別扱いなしに導ける。「同名で別物を指す」恐怖は未使用束縛の lint で緩和。代入 `x = e`（既存 `mut` を同型更新）とは別概念。
- **コレクション名 `Array`**: `Vec` は日本語話者に数学のベクトル連想で直感的でないとして却下。
- **辞書リテラル**: Swift 風 `[k: v]`、空辞書は型推論不能を避けるため明示トークン `[:]`。
- **JSX 属性に `{}` 不要**: 属性値は常に式として扱うため（JSX の `{}` は HTML 曖昧性回避という歴史的都合）。
- **`extern`**: 設計会話では `declare fn … from "libc"` 案を検討したが、最終文法は Rust 式の `extern "C" { … }` ブロックを採用。
- **`lazy`（遅延初期化）**: 専用構文は設けない。`<Lazy />` 構造体で表現する（言語仕様に載せなくても自然に実装できる単なる構造体）。
- **数値リテラル**: 16/8/2 進（`0x`/`0o`/`0b`）・`_` 桁区切り・e 表記・型サフィックスを採用。Rust とほぼ同様だが型サフィックスは型名（PascalCase）なので `10U32` / `3.14F64`（→ [spec/02-types.md](../spec/02-types.md)）。
- **force-unwrap 演算子は無し**: 後置 `!` のような強制取り出しは持たない（文法に残る `UNARY_POSTFIX_OP` は遺物で、再構築時に削除）。取り出しは `Optional`/`Result` の `unwrap` メソッドに留め、基本は非推奨（→ [spec/08-error-handling.md](../spec/08-error-handling.md)）。
- **冪乗演算子 `**` は導入しない**: `pow`（関数/メソッド）で代替。Rust/Go/Swift と同様、右結合・優先順位の事故（`-2**2`）、戻り型/コストの不透明さ、演算子経済の観点から。冪乗は単一 CPU 命令でなく実体は関数呼び出しのため、安価な演算子の見た目を与えない。

## 未決 / 今後決定すべき事項

実装を進める前に確認・確定が必要な点：

1. **チャネルの最終構文・型** — 方向（複数 Sender・`recv() -> Result[T, ChannelClosed]`・`Send`/`Clone` 境界不使用・`send` は immutable メソッド）は固まっているが、**所有権が無いため Receiver の単一所有は強制できない**（複数参照・複数 `receive` 可）。マルチコンシューマの意味論を含め **具体 API はコアライブラリ実装の課題**（言語コアの構文要素ではない）として stdlib 設計時に詰める。
2. **spawn/async の意味論実装** — モデルは確定（`spawn` はスレッド起動・ハンドル `join() -> Promise[T]`（`await` で join）・キャプチャ全 immutable・立てたスレッドも単一ループ・全スレッド完了までランタイム生存）。実装課題は「キャプチャ全 immutable」の型チェック（セマンティクス層）。文法には `block_modifier: ASYNC | SPAWN` のみ。
3. **Mutex/sync/atomic の扱い** — 標準で提供しない（or `@unsafe` 限定）。旧文法の修飾子は削除済み。
4. **（解決済み）extension の継承・ネスト** — **両方とも禁止**（呼び出し位置での由来一意性＝Single Dispatch Resolution を保つため。`value#B.foo()` の由来が不透明になるのを防ぐ）。再利用は `self#A.foo()`（明示修飾）、組み合わせは `value#A#B`（スタック）で代替。複数拡張を 1 名にまとめる別名（`alias Web = Json + Http`）は**将来の非破壊追加候補として保留**。再エクスポートは一般シンボルと同じく許可で決着済み。
5. **（解決済み）オーバーロード解決** — 暗黙変換は**無し**（完全一致＋リテラル多相のみ、例外は `as` 明示と `try` の `From`）、`via` 左辺は**常に完全シグネチャ**で要求を特定し target overload もそれで選ぶ、逆方向推論なし、モジュール閉包でローカル判定。骨子確定。旧「多重オペランド／多重変換」もオーバーロード許容＋`From` で解消。※残る検討は実装着手時の細部のみ。
6. **GC アルゴリズム** — GC 採用のみ決定、方式は未定。
7. **メタプログラミング / ディレクティブ詳細** — `Derive` トレイトのシグネチャ、`TokenStream` API、組み込みを `Derive` 実装で提供するか等（→ [spec/12-metaprogramming.md](../spec/12-metaprogramming.md)）。
8. **文法の細かい穴** — `@[...]` 内の空行・末尾カンマ、`match_case` 前の改行、`where_clauses` 末尾カンマなど（書き味レベル）。
9. **FFI の型マッピング** — `extern "c"` / `extern "javascript"` ブロックの構文は採用済みだが、Plew 型 ↔ C/JS 型の対応（数値・ポインタ/バッファ・文字列の境界変換、外部由来の `NaN` 流入の扱いなど）は未策定。実装フェーズで定める（→ [spec/11-modules.md](../spec/11-modules.md)）。

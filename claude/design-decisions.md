## 言語の目的（全制約の出発点）

### 設計の拠り所（最終的な判断基準）

> **唱えた通りに発現する。仕組みは問わない。** ── 意味（何をして・どこから来たか）は唱えた通りに発現し、仕組み（どう実現するか）は丸ごと引き受ける。観測挙動が唱えた意味から逸れない限り、裏では好きなだけ動いてよい。

- 求めるのは「簡単さ（言語が代わりにやる）」ではなく**掌握"感"・正直さ・一貫性**＝書いた通りに意味し動いて見えること（実際には CoW・イベントループ等の魔法が裏で動く＝**掌握"感"**であって実際の掌握ではない・Rust の no-hidden-cost は日常に重すぎるので採らない＝hidden cost は許容）。
- **二軸で運用**：(1) **意味は唱えた通り（透明）**＝意味を決める層（字句/名前/**型**/オーバーロード/トレイト/変換の解決）でコンパイラは勝手をしない＝**補完はする／忖度はしない／曖昧はエラー**。(2) **発現は隠蔽してよい（コストは裏）**＝最適化・codegen・ARC・CoW・スケジューリング・確保や「人間に難しすぎる魔法」（メモリ/所有/並行/浮動小数点）は自由に隠す。
- **hidden *cost* は可・hidden *meaning/behavior/provenance* は不可**：性能/コストのサプライズは許す（CoW の copy cliff 等）。意味・観測挙動・出どころのサプライズは許さない。境界は「コンパイラ vs ランタイム」ではなく「**意味の決定 vs 発現**」（コンパイラは両方にまたがり、前段＝透明・後段＝魔法）。魔法を唱えるのは人間で、コンパイラ/ランタイムは唱えられた呪文を発現させる側（意味を発明・読み替え・忖度しない）。
- 帰結の例＝`any`（トレイト配列を素直に）・暗黙変換なし・曖昧はエラー（リテラル/オーバーロード/specialization なし）・CoW/ARC/再帰型の自動箱化は隠す・**NaN/overflow は素朴な数値モデルで「答えの無い」演算で loud に落ちる**（overflow＝真の和が表現不可／NaN比較＝実数モデルで無意味＝両方とも honest abstention・NaN は隠すべき難しい概念ゆえ既定で見えず `isNan` で opt-in・整数 div は op で・NaN は比較で落とす＝嘘が起きる地点に panic を置く）。

### ターゲット

- **主軸＝複雑な状態を持つクライアントアプリ**。加えてモノレポでサーバ（Node 的・ステートレスで scale out 前提）も同一言語で書き、モデル層を共有する**フルスタックのアプリケーション言語**。**システムプログラミング言語ではない**（ARC・CoW・存在型・単一スレッド既定・spawn 境界 deep copy ＝**共有メモリ／ゼロコピーのデータ並列は不可**〔spawn は実スレッドで並列自体は在るが各スレッドは deep copy を持つ〕は、Rust/Zig 的システム言語ではなくアプリ言語のモデル。並行モデルは Node と同じ単一スレッドでこの狙いに合致）。
- **一次ビーチヘッド＝WASM ウェブ**：Plew の自前ランタイム（値意味論/ARC/native）を保ったまま、単一スレッド+イベントループ・JSX・値意味論+参照キャプチャが UI と噛み合い、クライアント(WASM)/サーバ(native)で**同一意味論**＝モノレポの一貫性が保てる。Flutter web の弱点（CanvasKit の重さ・DOM/a11y/SEO）を「軽量 WASM＋本物の DOM」で突く。
- **Flutter 相乗りは採らない**：Dart VM とランタイムを共有できず（FFI は C ABI 境界＝二ランタイム同居）、Kotlin/JVM の「ランタイム共有で侵入」類推が効かない。WASM↔DOM と FFI↔Dart は**同 genre（境界越しに外部 UI エンジンを駆動）だが相手の適性が真逆**で、DOM が理想・Dart が最悪。
- **コールドスタートが速い**ことが第一目的 → AOT ネイティブ / WASM、軽量ランタイム志向。性能は scale out で割り切る（二の次）。
- 「**Rust から所有権の*重さ*を引いた書き味**」が理想 ── 既定は値意味論で所有権を意識せず、資源など必要なときだけ opt-in の最小所有権（`unique`/`borrow`/`inout`/`move`）。全面的な所有権とライフタイムは不採用。
- この「**値意味論 + CoW + ARC + opt-in 所有権**」が、並行性・拡張・所有権周りの議論すべての根本にある。

## メモリ・所有権モデル（CoW + ARC + opt-in 所有権）

機構の正典は [spec/03 値・所有権](../spec/01-basics/03-values.md)・[spec/14 並行](../spec/04-execution/14-concurrency.md)。本節は**なぜこの地金か**の根拠。

### なぜこの地金か
- **信頼できる不変性**：値意味論なら `val` が型レベルで本当に不変（代入はコピー）＝エイリアスバグが消え、辞書キー・並行が footgun フリーになる。これを得る道は「値意味論／値コピー／全面不変」のいずれかで、Plew は **値意味論（CoW）**＝Swift 的書き味を採る。
- **CoW で安い**：「全代入コピー＝遅い」は誤解。CoW はコピーを遅延し共有中は無料、書き込み時にだけ実体化するので参照渡し並みに安い。
- **決定的破棄**：ARC なら `deinit` でファイル/ソケット等を確定的に解放できる（GC の非決定性が無い）。

### 主な帰結と根拠
- **ARC（参照カウント）を採る**：CoW は安価な一意性判定（refcount）を要し、ARC はコールドスタートが軽く**第一目標に合致**。代償＝**循環は refcount で回収できず `WeakRef[T]` が要る**（手動の弱参照を受け入れる＝意識的トレードオフ）。この手動 `WeakRef` の負担（Swift/iOS で実証済みの「書き忘れると静かにリーク」footgun）の緩和方針は下記「循環回収」を参照。
- **refcount は非アトミック（atomic 不要）**：`ARC` の "A" は **Automatic**（コンパイラ挿入）であって **Atomic** ではない。Swift の ARC がアトミック命令を要するのに対し Plew は**非アトミックな素の `++`/`--` で十分**。根拠＝並行モデル上、**同一 refcount バッファが2スレッドから同時に触られることが構造的に起きない**：`spawn` は move/copy のみ・`Ref`（唯一の共有可変）は spawn 不可・値型は **spawn 境界で実体化（deep copy）** されるので子スレッドは自前バッファ（rc=1）を持つ。join/チャネルは「同時共有」でなく「受け渡し＋同期点」、async は協調的シングルスレッド（プリエンプションなし）。よってバリア不要＝アトミック不要で、Atomic RC より大幅に安い（lock 付き命令の 10〜20 倍を回避）。**前提＝spawn 実装時に「境界で materialize」を必ず入れる**こと（これを破ると非アトミック前提が崩れる）。「跨ぐ変数だけ atomic」という hybrid すら不要＝materialize で跨いで共有しないので **atomic 対象はゼロ**。
- **循環回収＝ARC＋Ref グラフ限定サイクルコレクタ（方向確定・実装は additive）**：「GC が欲しい」の正体は **GC ではなく循環の回収**で、両者は分離できる。**鍵＝循環は `Ref` グラフにしか生じない**：CoW の値世界（`Array`/`String`/`Dictionary`・[自動箱化された再帰値型](#主要な判断と根拠)）は構造上つねに木／DAG で、親への貼り戻し＝共有可変エイリアスは `Ref` でしか得られない（→ spec/05「再帰的な値型」）。よって純粋 ARC は値世界を**取りこぼしゼロ**で回収し、残る穴は「`Ref` ボックス（＋`mut val` を参照キャプチャしたクロージャ＝同じ管理下の共有可変ボックス）から成る、小さく隔離された部分グラフの循環」だけ。これはヒープ全体の GC ではないので、**trace 対象が `Ref` グラフに限定**され劇的に安い。
  - **方式＝Bacon–Rajan の trial deletion**（"Concurrent Cycle Collection in Reference Counted Systems", 2001。CPython `gc`・PHP・Nim 旧 refc が実証）。循環は「refcount を減らしたが 0 にならなかった瞬間」にしか生まれないので、その候補ルートだけを集め、部分グラフ内で試行的に減算してゴミ循環を判定し、**メモリを回収する**（循環メンバの `deinit` は走らせない＝下記「循環検出時の挙動」）。**ARC の長所は残る**：CoW の一意性判定は不変、`unique`+`deinit` の決定的資源解放も**正常路では不変**、循環だけ自動回収。`WeakRef` は「正しさのために必須」から「決定性・性能のための opt-in」へ格下げされる。
  - **Plew はこれを安く・安全にできるが Swift はできなかった**：相違は環境にある。**(1) 非 atomic かつスレッドローカルな `Ref`**（spawn を越えない）→ `Ref` グラフはスレッドごとに完全分割＝**per-thread コレクタ・ロック不要・stop-the-world のスレッド間協調が不要**（実 GC の最難関＝並行コーディネーションが、既存制約だけで消える）。**(2) 単一スレッド＋イベントループ**→ ターンの合間が**天然のセーフポイント**（JS エンジンが常時 GC を回せるのと同じ理由）。**(3) フルマネージド＋レイアウトメタデータ**で `Ref` フィールドを列挙でき、**FFI はコピー**ゆえ生ポインタが `Ref` グラフに侵入しない。Swift が常時ランタイム検出を積まず**プロセス外スナップショット（memory graph debugger/Instruments）に逃がした**のは、trace 計算が重いからではなく（trace は O(候補＋内部辺)・per-frame 仕事に比して安い）、**atomic RC＋素のプリエンプティブスレッド＋セーフポイント無し＋半マネージドヒープ（C/ObjC interop・`Unmanaged`）**で「安全に・プロセス内で・常時」やるのが重く脆いから＋「決定的 deinit・ポーズ無し」を売りにした思想と自己矛盾するから。Plew はこの障害を設計上すべて排除済み。
  - **循環検出時の挙動（方針確定・deinit の有無で分けない）**：ゴミ循環を検出したら ①**loud に報告**（retain path・dedup・診断フック経由・全ビルド共通＝release 含む）②**メモリを回収**（GC 的）③**循環メンバの `deinit` は走らせない**。**deinit の決定的契約は正常路（スコープ離脱・`return`・`try`/`Result` 伝播）のみで保証し、契約外の脱出は 2 つ＝`panic` と「リークした循環」で、どちらも deinit を飛ばす**（[panic=abort で deinit 不走](#主要な判断と根拠)と対称）。
    - **uniform にする理由＝「deinit を足したら漏れ出す」崖を作らない**：もし「deinit 無し循環は回収・deinit 有り循環はリーク」と **deinit の有無で分けた**ら、ある構造体に `deinit` を 1 行足した瞬間にそれを含む循環が回収対象から外れ**リークし始める**＝許容できない footgun。だから**回収は deinit の有無に依存させず一律**にし、deinit は「契約外脱出では走らない」で揃える。多くのユーザーの「勝手に回収してくれ」も一律回収で満たす。
    - **驚きの deinit タイミングが原理的に消える**：循環メンバの deinit は「変な時刻に走る」のではなく**そもそも走らない**ので、非決定タイミングの驚きは生じない。非決定なのは**ログの発火時刻だけ**（診断であり資源操作でないので無害）。**循環内 deinit を一切走らせないので、PEP 442 の finalize 順序・復活問題も丸ごと不要**になる（前案で挙げていた循環内 deinit 順序規則は撤回）。
    - **正直な残コスト**：`Ref[File]` を意図せず循環に閉じ込めると、メモリは回収されるが **fd は閉じない**（deinit skip）。ただし①バグで②loud に報告され③`panic` で File が閉じないのと同じ＝契約外。直し方は **`WeakRef` で輪を切る**→正常路に戻り deinit が決定的に走る。「資源 deinit を変な時刻に走らせる」より「契約外では走らせず報告する」方が Plew の正直さに合う。
    - **重大度＝ログであって panic ではない**：overflow/NaN/0除算 が panic なのは**間違った値（嘘）**を返すから。リークは値の嘘ではなく**資源の無駄＋deinit skip**なので、走っているアプリを殺さず loud に報告するのが正しい較正。
    - **release で常時 ON が原則整合**：dev だけのレポータは「**意味論を変えるビルドを持たない**（assert/overflow panic は全ビルド ON・観測挙動不変）」ドクトリンに反する。検出・報告は assert と同じく**全ビルド ON**、フックは「どこに出すか」を変えるだけ（挙動は不変）。**安くする 3 条件**＝idle＋終了時スキャン（同期スキャンしない・長寿命プロセスは定期 idle）／循環サイト単位 dedup／診断フック経由。**コストは `Ref` グラフに比例**（値世界は 0 円）＝「軽量 ARC」と非矛盾（dead-simple な ARC に隔離コレクタが乗る点は最小ランタイムと多少緊張するが枯れたアルゴリズム）。
    - **段階導入は実装順の話**：reporter 先行（メモリ回収なし）→ 回収追加、は impl 順にすぎず、**回収は確定方針（任意の保留ではない）**。deinit 挙動は両段で同一（循環メンバは走らせない）なので、回収の追加は「漏れていたメモリが回収される＝hidden cost 解消」だけで観測される意味は不変＝非破壊。リークしていなかったプログラムは終始挙動不変。
  - **足がかり**：Bacon & Rajan 2001／CPython `gc`（世代別の候補管理）／PHP の GC。いずれも「ARC の上に載る循環コレクタ」の実装例（Plew は循環メンバを finalize しないので PEP 442 の順序・復活問題は回避する）。
- **資源は `unique`＋`deinit`**：値 struct に `deinit` は置けない（コピーで多重 deinit＝二重 close。Swift の struct に deinit が無いのと同理）。値意味論で言語内に資源を書くには **class かコピー不可型のどちらか必須**（Ref だけでは中身がコピー可能で漏れる）→ **class 種別を増やさず `unique`（コピー不可）採用**＝move 意味論の限定サブセット（borrow/inout/move・use-after-move・非 escape 借用でライフタイム不要）。
- **`Ref` は唯一の共有可変プリミティブ**：extern で再現不可（コピー時 retain／drop 時 release の自動挿入が要る・これは Array の CoW も同様＝両者とも祝福プリミティブ）。「同じ書き方で違う挙動」の懸念は **deref `->` を明示**して解消（`.`＝ハンドル操作・`->`＝中身）。
- **アクセス語＝`borrow`/`inout`/`move`**：`borrow`/`move` は「関係」を表すのに `modify` は「行為」を名指し不整合で却下。`&mut` は正確だが CoW には too much → **`inout`（＝CoW 版 `&mut`・Swift と同判断）**。`mut` は **`val`/`mut val`（記憶域）専用**（二義性回避）。`var` 却下＝「手抜き＝immutable」を守る。
- **並行性は実質 race-free**：**借用は async/spawn を越えない**（越えるのは move/copy/Ref）→ async 借用ライフタイム追跡が不要・`Promise.all([f(move a),f(move a)])` は use-after-move で弾ける。**spawn は move/copy のみ・Ref は spawn 不可**（推移的 Ref-free を要求）→ スレッド間に共有可変が無く競合フリー・Mutex 不要。**async は単一スレッドゆえ Ref 可**（メモリ安全・interleave は JS 同様の論理ハザード）。spawn を越えられない型は **`local struct`**（`Ref` を持つ型は必須・unique 同型のエラー強制）。
- **generics**：能力マーカーは **`[...]`**・trait 制約は `where`。既定 `[T]`＝`unique` でない＋`local` 許容＝common case が無注釈。`[noLocal T]`（narrow・spawn 用）／`[allowUnique T]`（widen・unique admit・実装は将来）。非対称は「既定＝common case」の帰結。v1 はコピー可能な型に限定（unique は `Ref` 包み）。
- **実装順**：spawn は後回し濃厚 → `noLocal`/`allowUnique` 検査も連動。最小コンパイラは 値＋CoW＋ARC＋`unique` 基本＋`Ref`/`WeakRef` から。

## 主要な判断と根拠

### アクセスモードと `inout`（→ [spec/03](../spec/01-basics/03-values.md)）
- 可変性・所有移動は構文で明示する（副作用がシグネチャから見える）。可変借用は **`inout`**（Swift と同じ・呼び出し元を書き換える意図が明確）。引数の `mut` は「関数内ローカルの再代入」と誤解されるため使わず、`mut` は記憶域可変性（`mut val`）専用にした。Ada / C++ `&` / Nim `var` / D `ref` も比較。
- **コピー可能型で `borrow`/`move` はエラー・`inout` は全型 OK（決定）**：モードがコピー可能型で「観測上の意味を持つか」で判定。**`borrow`** はコピー可能型では by-value と観測挙動が完全同一（読むだけ・元無傷・CoW でゼロコスト・コンパイラがコピー省略を自動実行）で**何も足さない冗長指定**、**`move`** はコピーで済むのに「以後使えない」制約だけ課す **footgun**（`f(x: move a)` 後に `a` 不可）。ゆえに**コピー可能型では `borrow`/`move` をコンパイルエラー**にする。**`inout` は書き戻しという観測可能な意味を持ちコピー可能性と独立なので全型で許可**。**対称性**：コピー可能型＝「コピーできるので borrow/move 不要＝エラー」／`unique` 型＝「コピーできないので by-value 不可＝モード必須」、`inout` だけ両方にまたがる。**根拠**：Plew は効果のない飾り構文を切る（`pub(crate)` を切ったのと同種）＋footgun を弾く（曖昧/無意味はエラーの精神）。**却下案**＝Rust 流「全型で borrow/move 可（コピー可能型では冗長だが書ける）」は move の footgun を許し冗長 borrow をノイズとして残すため。**含意**：v1 ジェネリクスはコピー可能限定ゆえ generic `[T]` は by-value/`inout` のみ（`allowUnique` 導入時に capability 依存で borrow/move 解禁＝additive）。メソッド self も同様＝コピー可能型は `fn`/`inout fn` のみ・`move fn` はエラー。警告でなくハードエラー。→ spec/03「アクセスモード」。
- **場所（place）越しの変更＝get-modify-set／重なる inout は禁止（決定）**: 可変参照・lvalue を返す添字を持たない（`IndexSet` はセッター）ので、`arr[i].field = x`・`arr[i].inoutMethod()`・`a.b[i].c = x` をどう実現するかが未定義だった（旧 spec は複合代入 `arr[f()] += x` だけ規定）。**決定＝意味モデルは get-modify-set**（添字段＝`Index`+`IndexSet`・フィールド段＝load/store の read-modify-write・場所は 1 回評価・複合代入の一般化）。機構は [spec/03](../spec/01-basics/03-values.md#場所place越しの変更)・[spec/12](../spec/03-expressions/12-operators.md#添字代入indexset)。**Swift との対比（実機で検証済み）**：Swift の `inout`/`_modify` は速度のため**生ポインタ（addressor）を任意区間貸し**、再入で再確保されると dangling するので **Law of Exclusivity（全アクセスに `swift_beginAccess` 計装＋静的/動的検査）** が要る（`accounts[0].moveTo(&accounts[0])` は**コンパイルエラー**・グローバル経由 `increment(&stepSize)` は**実行時トラップ**＝SIGABRT を確認）。**Plew はコピー意味論ゆえ生ポインタを貸さず、アクセス窓が 1 呼び出しに閉じる**（借用は境界を越えない）ので、dangling が原理的に起きず**全アクセス計装が要らない**＝重なり検査は「同一呼び出しの inout place を見比べるローカル検査」だけで足りる。**in-place 直接書きは「一意所有＋無効化なし＋非重なりを静的証明できる時だけの観測不能な最適化」**（実行時計装なし）。**重なる inout**（レシーバ＋引数等が同じ場所）は get-modify-set だと**書き戻し衝突で last-write-wins＝片方が静かに消えるバグ**（Swift 検証の 1 つ目の診断 "inout writeback through subscript … invalid aliasing" がまさにこれ）ゆえ**プログラムエラー**＝①構文同一→コンパイルエラー ②添字 distinct 証明不可→lint＋限定ランタイム panic ③証明可→OK。**`inout` の排他はスレッド安全でなく単一スレッドのメモリ安全の話**（再確保による無効化防止）で、spawn はそもそも共有可変を渡さないので無関係。**前方互換**：last-write-wins 挙動を*保証しない*ので、将来速度のため Swift 流 in-place+トラップへ実装変更しても、重なりの無い全プログラムは観測不変＝非破壊（重なりは両方式とも拒否）。**却下**：実メモリ in-place を意味モデルにする案＝排他則という重い装置（単一スレッドでも要る）を Plew が他で必要としないのに抱え込むため。

### 並行性: 値意味論で race-free（→ [spec/14](../spec/04-execution/14-concurrency.md)）
- 基盤は JS と同じ単一プロセス・単一スレッド + イベントループ。重い処理は `spawn`（「プロセス」ではなく**スレッド**・立てたスレッド自身も単一ループ）。
- **スレッド間は値の送信のみ**（"share memory by communicating"）：spawn は move/copy で値を渡し（`unique` は `spawn fn` の `move` 引数）、`Ref` は spawn を越えない。よって**スレッド間に共有可変が存在せず競合フリー**で、`Mutex`/`sync val` は不要（値意味論なので「参照経由で競合」も起きない）。借用も境界を越えない（→ async 借用ライフタイム追跡が不要）。
- **spawn の戻り＝ハンドル構造体（決定）**: `join() -> Promise[T]`。**footgun 回避**：detached でもブロックは完走／ハンドルはスレッドを所有しない／**ランタイムは全スレッド完了まで生存**（Go の「main 終了で goroutine kill」footgun を避ける・将来 daemon 指定の余地）。
- チャネル方針: **複数 Sender**。所有権で「Receiver は単一所有」を強制しない（`Receiver` も値で複数箇所が持て `receive()` 複数回可）。送る値は `local` でないこと（`Ref` は送れない）。マルチコンシューマ意味論・具体 API はコアライブラリ送り。
- **`Send` を別途設けない**: spawn 越え可否は「推移的に `Ref` を含まない（＝`local` でない）」で判定でき、専用マーカー不要。
- **CoW 値は spawn 境界で eager 実体化（決定）**: `Array`/`String`/`Dictionary` は CoW バッファを参照カウントで共有するが、その count は `Ref` と同じく**非 atomic**。`Ref` を含まないので `local` 判定は通る（spawn を越えられる）が、遅延コピーのまま越えると送信側・受信側が同一バッファの非 atomic count を同時に触り、**`Ref` を spawn 不可にしたのと同じ競合が CoW バッファで再発**する（旧 spec では未対処の穴）。**解決＝spawn 境界でコピー可能な値の CoW 遅延を打ち切り、バッファを実体化（ディープコピー）して各スレッドに独立 count を持たせる**（→ [spec/14](../spec/04-execution/14-concurrency.md#cow-値は-spawn-境界で実体化するeager-copy)）。**却下案**：(A) **Swift 流の全 atomic ARC**＝CoW バッファも `Ref` も atomic count にすれば共有越境が安全だが、単一スレッドコードまで全 retain/release が atomic コストを払い、Plew の「軽量 ARC・`Ref` は非 atomic」の地金を失う。(B) **バッファだけ atomic**（祝福プリミティブは atomic・ユーザー `Ref` は非 atomic 維持）＝中間解として一貫するが、CoW 操作全般に atomic コストが残る。**採用＝(C) 境界 eager copy**：spawn は**稀で重い操作**（実スレッド起動）なので越境時の実コピーは相対コスト小で、ARC を一切重くせず非 atomic を全面維持できる＝Plew の地金に最も一貫。**対価**：spawn へ大きな `Array`/`String` を渡すと読み取り共有のつもりでも実コピーが走る（大きな不変データの thread 間共有が要るなら、atomic 参照カウントの thread-safe 共有型を additive に足す → [spec/14](../spec/04-execution/14-concurrency.md#並行安全性--実質-race-free)）。**async（単一スレッド）では CoW は遅延のまま**＝この実体化は spawn 境界だけに効く。
- **トップレベル変数を持つ（決定）**: モジュールのトップレベルに `val`（定数）・`mut val`（可変）を置ける（`export val` で公開も）。**ユーザーはグローバル（ambient）な定義を作れない**が「グローバル変数/関数が無い」わけではない＝モジュールレベルには在る。正確には「**グローバル名前空間が無い**」ではなく「**ユーザーが ambient 定義を作れない**」（唯一の ambient＝言語提供 lang item は実在する）。
- **言語アイテム（lang item）は常にスコープ・それ以外は明示 import（決定）**: 機構は [spec/15](../spec/04-execution/15-modules.md)。**経緯**：毎ファイル `import Foundation with *`（#include 風）も暗黙 ambient（Swift 風・コア境界が曖昧で「Random は要 import？」が起きる）も嫌い、の板挟みを「ambient なのは"言語の語彙"＝固定小集合だけ、ライブラリは全部明示」で割って解消。**位置づけ＝唯一の ambient は言語提供 lang item でユーザーは足せない**（"グローバル名前空間なし" とは言い切らない＝lang item は実際 ambient）。**保留：マニフェスト既定 import（write-once で全ファイルに撒く）** ── ユーザーが「許せる」とした案だが当面不採用（additive で後付け可）。
- **ambient なのは型のみ・トレイトは含めない（決定）**: 「`import` 不要で常にスコープ」に入れるべきは**型だけ**で、トレイトは入れない。根拠は **use site と definition site の分離**：(1) `a+b`/`for`/`xs[i]`/`x?`/`xs.sort()` のように**トレイトに裏打ちされた機能を使う**とき、ディスパッチはレシーバ型＋有効な `#Ext` だけで決まり、演算子・構文→トレイトの対応（`+`↔`Add`・`for`↔`Iterator`/`Iterable`・`xs[i]`↔`Index`・`[k:v]` キー境界↔`Hash`）は**コンパイラ内部の脱糖表＝名前空間の住人でない**ので、use site では**トレイト名が一度も解決されない**＝import 不要。(2) トレイト名を書くのは `where T: Add`/`any Iterator[Item=I32]`/`impl Add for T` の**定義地点だけ**で、そこは他の名前同様 import（組み込み演算子トレイトも std から）。`xs.sort()` を呼ぶ側に `where T: Ord` が波及しないのは、束縛検査が型に対して起き呼び側はトレイトを名指さないから。**帰結**：ambient リストは**型のみ**に縮み sharp に閉じる（数値型・`Bool`・`String`・`Array`・`Dictionary`・`Optional`・`Result`・レンジ 2 型・`Promise`・スレッドハンドル `JoinHandle`）。`From`（脱糖表に在るが名指し時 import）と `TryFrom`（構文非参照ゆえ普通の import）の非対称は「**脱糖表に居るか**」と「**名前空間に居るか**」が独立、で一貫説明できる（trait を ambient に含めるか否かの論争はこれで決着）。**`Unit` 型は持たない**（`()` は空のラベル付き無名レコード＝構文そのもの）。スレッドハンドルの名は `JoinHandle`（「join するためのハンドル」＝役割で命名・Rust 同名／`Thread` はスレッド自体を騙るので却下・`Promise` が「未来の約束」を名指すのと対称）。

### 拡張システム（記法が最も二転三転した・→ [spec/09](../spec/02-type-system/09-extensions.md)）
- 解決したかった Rust の DX 課題: (1) 1 メソッドのために trait+impl は冗長、(2) 呼び出し側がファイル頭の `use` を見ないと由来が分からない。
- 核心アイデア: **拡張元を呼び出し位置で明示**する（import スコープに依存させない）。
- **外部型への実装は拡張に強制**: 無名 impl は「**型を所有**」が必須（Rust の「型 or トレイト」より厳格）。理由：外部型への無名トレイト impl は呼び出しで `#` 修飾が要り「実質拡張」になる上、明示拡張と並存すると経路が二重化するため、一律 `#Ext` に一本化。`#Ext` は型の一部でジェネリックにも決定論的に流れ、別実装は別型として区別（禁止でなく型で区別）。
- **記法変遷**: `[..].average#crate()` → 区切りを `@` に（メアド連想）→ 演算子・引数渡しで明示できない問題で `value@Ext.call()` を断念 → レシーバ後置 `value@Extension.call()` → スコープを `namespace { … }` で区切る → 広すぎるので **`extension`** キーワードに。**最終文法では区切りは `#`**（`@` は会話上の議論）。
- **Single Dispatch Resolution Rule**: `#Ext` を必須にすることで C++ 的ダイアモンド曖昧性は原理的に起きない。危険が出るのは `#Ext` 省略糖衣 / extension の継承・ネスト / 暗黙 trait dispatch を入れたとき → これらは禁止/制限する。**拡張の再エクスポートは安全で許可**（`#Ext` は各ファイルでスコープ内の一意名に解決＝一般シンボルと同じ扱い。当初 re-export を危険リストに入れていたのは誤りで撤回）。
- **拡張ビューは暗黙キャストなし・ビュー変更は明示（決定）**: 機構（`A#P`＝ゼロコストビュー・型検査では `A` の不変な型細別・コンテナ非伝播・拡張違いオーバーロード共存）は [spec/09](../spec/02-type-system/09-extensions.md)。**経緯**：一旦「双方向の暗黙キャスト（ターゲット指向）＋拡張違いオーバーロード禁止」を採ったが、(a) スカラは暗黙・コンテナは不可という**非対称が分かりにくい**、(b) Plew は他に暗黙変換を持たず**全ビュー変更を明示する方が一貫**（orphan の `f(x#Ext)` 必須と統一）、の 2 点で**暗黙キャスト全廃に再転換**。明示の冗長は `defaultExtension`（既定拡張はベア表面に載る）が大半を吸収。暗黙キャストを外した結果、オーバーロード禁止の特別規則も不要になった（exact 一致で曖昧消滅）。

### トレイトのフィールド + `via`、トレイト準拠モデル（→ [spec/08](../spec/02-type-system/08-traits.md)）
- computed property（getter 地獄）が嫌い、という動機でトレイトにフィールド定義を許す（構造的制約として機能）。Rust が避ける理由（メモリレイアウト/衝突）は理解の上で採用。
- 代償: フィールド要求トレイトは外部型に実装できない（Rust の orphan rule より強い制限）。妥協策が `via` フィールドエイリアス。`via`/`<-`/`=:` を比較し `via` 採用。
- **準拠モデル（方針確定）**: 準拠は `impl Type as Trait` を**明示宣言**し、全要求を `via` で実体メンバに束ねる（or メソッドは本体定義）。当初の「単一フラット名前空間」は後述のオーバーロード許容で緩和。
  - **却下**: ① Swift 方式（同名・同シグネチャの既存メソッドが暗黙に witness）→「うっかり準拠」が怖い。② Rust 方式（inherent と trait で別名前空間、`fn baz() { return self.baz() }` の自己委譲が意味不明）。`via` 束縛は両者の中間で、**ベアの呼び名を保ったまま明示**でき、自己委譲の奇習も消える。
  - **別名はベアでも可視**（決定）: 要求名と実体名が違う `via` は要求名をベアの呼び名として追加。トレイトとして呼べてベアで呼べないのは不合理、という理由。
  - **`via` 左辺は常に完全シグネチャ**（決定）: 本体定義形と対称で、トレイト未参照でも各行の意味が分かり、同名要求が複数（要求のオーバーロード）でも一意に witness できる。「名前だけ／稀にシグネチャ」の特例を避けた（ルールは 1 つ）。
- **提供メソッドはトレイトと同じモジュールのベア `impl Trait` に置く＋衝突は拡張 gating で解決（Fork B・最終決定）**: トレイト本体＝要求（本体なし）／**ベア `impl Trait`＝提供メソッド（本体あり）**＝型の `struct`↔`impl Type` と対称。準拠 `impl A as Trait` で提供メソッドが**自動でベアに載り**、境界 `where T: Trait` 越しにも使える（provenance は明示の準拠/境界＝ambient でない）。第三者追加は `extension { impl Trait }`＝`#Ext` opt-in。**衝突**＝P・Q が同名同シグの提供メソッドを持ち A が両方に準拠＝A のベアに同名が 2 つ。**併存は許し、曖昧なベア呼び `a.foo()` だけがエラー**（use site で曖昧はエラー＝`any P` 診断と同形）→ `a#P.foo()`／`a#Q.foo()` で源を選ぶ。ベア既定が要れば片方を拡張に閉じる／inherent で privileged にする（任意・強制でない）。**具体型と generic で同一規則**：generic `where T: P + Q` は両方に準拠する型（直接でも拡張経由でも）が満たし、本体 `t.foo()` は曖昧＝**`a#P.foo()` で曖昧化**（`#`＝メソッド源セレクタ＝トレイト | 拡張・トレイト形は呼び出し位置限定・`A#P` 型は作らない・トレイト相対なので `a#AWithQ`/`a#AWithP` どちらを渡しても同じ関数で動く）。機構は [spec/08](../spec/02-type-system/08-traits.md)・[spec/09](../spec/02-type-system/09-extensions.md)。
  - **経緯（長い再転換の連鎖・すべて撤回して Fork B へ）**：(i) 当初「派生メソッド＝名前付き拡張＋型が `defaultExtension` で opt-in」→ generic で `x#Ext`＋`where` の二重条件が毎回必要な摩擦。(ii) **Fork A'**＝トレイトが `defaultExtension` を宣言し準拠/境界に**自動随伴**＋既定拡張 strip を**トレイト側 `#!`**（`impl A as P#!Ext`／`where T: P#!Ext`）に統一 → だが「どの規定拡張がどこで宣言され推移閉包でどう侵入するか、人間が追えない」複雑さが致命的。(iii) 「**trait 実装のたびにほぼ同名の拡張を宣言するボイラープレートがひどい**」と気づき、**シンプルさを分離の美しさより優先**して Fork B（提供メソッドをトレイトと同じモジュールのベア impl へ）へ。**規定拡張・境界随伴・strip-on-trait は全廃**（`#!` は value/型レベルの拡張剥がし `a#!Ext`・super `self#!Bar` だけに戻る）。
  - **却下した代替**：(a) トレイト規定拡張/トレイトビュー＝人間が追えない暗黙侵入。(b) `Q#E` 型引数拡張＝`P + Q#E` と `P#E + Q` が別関数になり渡せる値が割れる馬鹿げた縛り（trait 相対の `a#P` が安定で正しい）。(c) `P.foo(self: a)`（trait 修飾呼び）＝正しいが `P.` のオートコンプリートに instance メソッドが混ざる・generics 外に裸 `P` が出る → 却下し**レシーバ起点の `a#P.foo()`** に（`a#P.` 側に instance メソッド・`P.` は assoc/factory のまま）。(d) generic 衝突を「書けない（restructure）」で割り切る案＝ユーザーが拒否、`a#P.foo()` で書けるように。
  - **`#` の意味拡張＋唯一の非一意例外**：`#X`＝「メソッド源 X（トレイト | 拡張）の選択」。`#Ext` は型レベルビューにもなるが `#P`（トレイト）は呼び出し位置限定。`a#X` の X が trait か拡張かは字面で決まらない（操作一様ゆえ無害・ツール判別）。これは「全呼び出しが一意解決」原則を**この曖昧化に限って**緩めた唯一の例外（`a#AWithQ.foo()` と `a#AWithP.foo()` は別メソッドだが両方 `f` に渡せる必要があるため）。
  - **残る細目**：ブランケット（`impl B as Q`）経由でのみ Q に準拠し明示 impl が無い型は、Q 提供メソッド衝突の局所解決地点を持たない（直接実装した側を拡張に閉じる・inherent shadow で回避）。継承はこの形にならない（`impl A as Sub` には `impl A as Super` 必須）。
- **トレイト継承 `trait Sub: Super`（決定）**: Sub 準拠に Super 準拠を要求（`:` は `where` 制約と同記法）。**複数指定は `+`**（`,` から変更＝`where T: A + B` と区切り統一。`+` は同一主語 `Self` への制約重ね、`,` は別主語の並びで supertrait では使わない）。**制約であって自動実装ではない** — `impl T as Sub` には別途 `impl T as Super` が要る（暗黙準拠を持たない方針の一貫）。**提供メソッドの帰結**：トレイト由来の同名・同シグネチャ提供メソッド衝突は「型が両トレイトに準拠したとき」併存可で、曖昧なベア呼びだけがエラー（`a#P.foo()` で解決・旧「継承強制 (1)／偶発 (2) の検出時点分岐」は撤回）。
- **オーバーロード許容（決定・旧「演算子の多重実装は拡張で」「型引数廃止」を撤回）**: 同名メソッドを引数型で区別して複数定義可（inherent でも trait witness でも）。**根拠＝無名 impl が型のモジュールに閉じる**ので、衝突検出はモジュール単体ビルドでローカルに完結（Rust のグローバルコヒーレンス不要）。重なり得るジェネリック impl は保守的拒否（specialization 無し）。**却下案（演算子だけを特別カテゴリにして暗黙の構文トレイトを持たせる）** — 「演算子は本来メソッドの糖衣なのに特別扱いする根拠が無い／特別 trait が暗黙」。Rust が trait 必須なのは Rust の trait スコープ解決＋コヒーレンスゆえで、モジュール閉包の Plew には当てはまらない（cargo-cult 回避）→ Swift 流の inherent オーバーロードを採用。「うっかり準拠」は `impl as`＋`via` の明示準拠で別途防止（オーバーロードとは直交）。
- **関連型 associated type（決定）**: `type Name` で要求宣言、impl は `type Name = ConcreteType` で束ねる（`via` 不使用＝関連型はメソッド/フィールドのフラット名前空間とは別の**型の名前空間**）。外部射影は `T.Item`（`.`＝値メンバアクセスと同区切り）、制約束縛は `Trait[Item = Foo]`。Rust 実証済みモデルに合わせ、記号だけ Plew 流（`<>`→`[]`、`::`→`.`）。
- **トレイト型引数は維持（決定・一時「廃止」と判断したが撤回）**: オーバーロード許容＋モジュール閉包で多重 impl が安全に書けるので `Add[Rhs]` 等の型引数を残す。**入力（複数 conformance）＝型引数、出力（impl が一意に決める）＝関連型、両方持てる**。演算子はトレイト経由継続。
  - **変換は `As`→`From[Source]` に置換（決定）**: `as()`（引数なし・戻り型だけ違う）は引数オーバーロード規則に乗らないため、ターゲット側 `From[Source]` にする。`x as T`⟺`<T from=x />`（無名 factory）、`try` のエラー変換も `From`。これで多変換先・多 source・`try` が自然に解決（旧「多重オペランド／多重変換」未決を解消）。（旧 `Coalesce` トレイトは後に廃止＝`??` 演算子ごと撤回。）
  - **`as` は infallible 固定・縮小は `TryFrom`・生成は fallible factory（決定）**: 旧 spec は縮小／可謬変換の経路を欠いていた（`From` は infallible しかなく、`as` で `I64→I8` をどう扱うか未定義）。**Rust のおさらい**：`as`＝unchecked な lossy/飽和キャスト（Plew Source)`＋`as` 糖衣**（`x as T`⟺`<T from=x />`）、TryFrom は稀ゆえ名前付き ── この非対称で、同じ Source から失敗しない版（From）と失敗し得る版（TryFrom）を**両方書いても衝突しない**（無名 vs 名前付き factory）。③**`as` を `Result` にする案・`try_as`／`as?`   - **集約エラー enum の boilerplate はメタプログラミングで消す（決定）**: variant ラップの `From` は**コンパイラ特例の自動ラップにはせず、`Derive` 系メタプログラミングで生成**（Rust の `thiserror` 相当）。`try` の暗黙 `From` 機構は 1 つに保ち、手書き boilerplate だけ生成で消す（→ [spec/16](../spec/04-execution/16-metaprogramming.md)）。
- **数値リテラルは多相・文脈で確定・既定型なし（決定）**: 型は文脈（注釈・引数型・戻り型・被演算子型）で一意に定まったもの。**一意でなければエラー**（`val x = 42` も文脈ゼロ＝エラー）。Rust 的既定型は持たない（明示優先・幅安全）。**型付けは双方向（期待型を式に下ろす）のみで、変数の後続使用から宣言型を逆算する推論はしない**（コンパイラ負荷と可読性のため）。
    - **却下した代替（既定型・comptime_int・符号付き添字の探索／すべて却下し現行維持）**：出発点は「文脈ゼロのリテラル（特に `for val i in 0..<10`）に suffix が要る摩擦を、既定型で緩められないか」。追った末、現行の「既定なし・U64 添字」が原則に最も忠実と再確認した。
      - 却下①**`U64` 既定**＝**型の嘘**。一般の数は負になり得るのに、頼んでもいない非負性を被せると `val a = 5 - 10` のような無害な式が実行時 panic する。U64 既定は**永久に不可**。フォールバック既定を将来 additive に足すなら**符号付き（`I32`/`I64`）限定**（符号付きは一般値に嘘をつかないので可・→ [spec/02](../spec/01-basics/02-basic-types.md)）。
      - 却下②**符号別既定（正→`U64`／負→`I64`）**＝1 式内で符号が割れ、暗黙変換なしの Plew では `5 + -5` や `5 - 10` が型不一致/panic になり破綻。既定を置くなら**単一の符号付き型**でしかあり得ない。
      - 却下③**comptime_int（Zig 流の任意精度コンパイル時整数）**。`val x = 1; arr[x]` を救えるが、**no-widening の Plew では唯一の暗黙コアース**になり浮く。Zig で自然なのは Zig が一般に**無損失の暗黙 widening を持つ**（`i32→i64` も暗黙・comptime_int→具体型はその一ケース）から。Plew は widening を持たない（`I32→I64` も明示 `as`・Rust 同様）ので、comptime_int だけ入れると「明示>暗黙・暗黙変換なし」の中で孤立する。値型にして `val a: ComptimeInt = 1; val b: I64 = a` を許せば**それ自体が暗黙変換**＝禁じたもの。しかも**本命の痛み（ランタイム for ループの添字）は救えない**（反復は具体型必須）ので利得も小。→ 不採用。
      - 却下④**添字・`count` を `I64`（符号付き）に変更**＝既定 `I64`＋添字 `I64` で摩擦は綺麗に消え、Swift/Go/Java（符号付き添字）とも揃う。**だが型の嘘**：非負しか入らない場所に負を渡せる型を置き、エラーが「添字した地点」へ遅延する。**正しい原則＝正の値しか入らない場所の型は U64、実行時エラーは「負を非負の場所に入れようとした地点」で起きるべき**。Plew は `as`＝無損失限定／縮小・可謬は `TryFrom` なので、符号付き→U64 は明示の `TryFrom` を要し、**負は変換境界で loud に落ちる**＝この原則は既存の `as`/`TryFrom` 分割で既に強制済み。→ 添字は **U64 維持**。
      - **維持した結論**：U64 添字＋符号付き一般値＋`TryFrom` 境界。`for` の添字は `0..<arr.count`（無印・最頻）か `0..<10U64`（「これは添字だ」という意図の明示＝摩擦でなく宣言）。一般算術の文脈ゼロは `: I64` 等で明示。既定型は当面なし（将来の escape hatch は符号付き限定）。
  - **等価・順序・論理の演算子設計を確定（決定）**: 当初の `Eq[Rhs]`/`Ne`/`Lt..Ge`（型引数つき比較）案を見直し、**等価＝`Eq`／順序＝`Ord: Eq` に統合し型引数を持たせない**。理由：等価/順序は同一型上の同値関係/全順序で、`impl A as Eq[B]`（異種）は対称律・反射律を型で守れず不健全。型引数を残すのは**両辺が別型になり得る**演算（`Add..[Rhs]`・`Index[Key]`・`From[Source]`）だけ、と境界を整理。
  - **浮動小数の NaN は比較時 panic（決定）**: `F32`/`F64` を全順序 `Ord`・全等価 `Eq` に準拠させ、NaN を比較した瞬間に **panic**。算術は IEEE 据え置き。**却下案**：(a) IEEE 忠実に黙って `false`（Swift 寄り・静かな footgun）、(b) `compare -> Optional[Ordering]` の部分順序（普通の型にまで `Optional` の儀式を強いる）、(c) 生成時 panic（**WASM に FP トラップが無く**全演算へソフトチェックが必要＋FFI で NaN 注入され不変条件が漏れる）。比較時 panic は移植可・低コストで、バグの瞬間にだけ大きく落ちる＝「隠れた footgun を嫌う」方針に最も合致。inf は全順序を壊さないので通常値。
  - **整数オーバーフローは常に panic・wrap は明示・意味論を変えるリリースビルドは持たない（決定）**: 桁あふれは**全ビルドで panic**（Swift のトラップに合わせる）。ラップは明示メソッド `wrappingAdd`/`sub`/`mul`/`neg`（**専用演算子 `&+` は持たない**・Rust std も無し・稀用途＝決定）。整数 0 除算も panic（剰余符号は被除数＝truncated・→ [spec/12](../spec/03-expressions/12-operators.md)）。**却下：Go の silent wrap**（「静かな嘘を返さない」＝ NaN/暗黙変換と同方針に反する）。**却下：Rust の debug=panic/release=wrap**＝**意味論を変えるビルドモードを持たない**（`debug`/`release` は最適化レベル＝速度だけ・観測挙動は不変＝リリース限定バグを作らない＝観測挙動は唱えた意味から逸れない）。Go にそもそも debug/release 区別が無い（常に最適化・overflow は常に wrap）ことも確認、Plew は「1 意味論＋最適化レベルのみ」を採る。**別腹（決定）**：`assert` は**常時 ON 一本**（Rust `assert!`／Swift `precondition` 相当・全ビルド同意味論・通常関数で import 要）。`debugAssert`（最適化ビルドで除去する段）は唯一「観測挙動が唱えた意味から逸れない」と緊張するため**別名で additive 保留**（→ 下の「数値トレイトの分解原理＋assert/ラップの確定」と spec/11「assert」）。
  - **`&&` / `||` は短絡する制御フロー（決定・トレイト化しない）**: `a && b ≡ if a { give b } else { give false }` の **`if` 糖衣**（Bool 専用・オーバーロード不可）。`And`/`Or` トレイトは廃止。**却下案**：(a) eager トレイト＝範囲チェック後の添字などガード idiom が壊れる/panic、(b) Swift の `@autoclosure` で lazy トレイト＝暗黙ラップ機構が要り「明示>暗黙」に反する。根拠：`&&`/`||` は右辺を評価するか左で決める＝`+` と評価戦略が違う**別カテゴリ（制御フロー）**なので特別扱いに筋が通る。`!`（`Not`）は eager なのでトレイトのまま。
  - **`panic` はキーワード（決定）**: `panic "メッセージ"` は発散する**文**（式ではないので `x ?? panic` は不可→`guard`/`match`）。メッセージは診断用 String のみ。回復不能用で catch 不可。**「`Never` を返す普通の関数を魔法で発散扱い」を却下**（見た目が関数なのに特別扱い＝暗黙を嫌う）。ユーザー可視の `Never` 型も導入せず、発散はフロー解析で扱う。**`spawn` 内 panic はプロセス全体を停止**。
  - **match アームのベア式形（決定）**: アーム右辺は ①ベア式 `=> expr` ②ブロック ③発散ブロックの 3 形式。`give` を毎回書かせず軽量にする。
  - **match の網羅性は Rust 流（決定）**: 非網羅は**コンパイルエラー**（機構→ [spec/11](../spec/03-expressions/11-control-flow.md)）。**根拠**：match は値を生む式なので、どのアームにも当たらない経路があると結果値が無く型健全性が壊れる＝網羅必須は型システムからの要請（C の switch fall-through とも無縁＝最初の一致のみ・到達不能アームは警告）。整数/`String` 等の開いた型は `_`（or 捕捉束縛）必須、enum は全バリアント。**Plew は match アームにガードを持たない**（文法 `match_case: expression | enum_assign_left | '_'`）ので、網羅判定は純粋に構造的＝Rust の「ガード付きアームは網羅に数えない」例外規則が不要（絞り込みは束縛→ネスト match か前段の `if`/`guard` 条件チェーンで行う）。**additive 保留：`non_exhaustive` 相当**（ライブラリが将来のバリアント追加に備え下流に `_` を強制する Rust `#[non_exhaustive]`）は `export` 境界と絡むので、需要が出たら非破壊で後付け。
  - **`_` は一般ワイルドカード・分解は全フィールド明示・`..` なし（決定）**: `_` を match 専用の特殊構文でなく**パターン文法の葉（ワイルドカード）**にする＝束縛を作らない破棄・パターン位置ならどこでも（`Some(value: _)`・`(val x, _)`）・**書き込み専用シンクで値式としては読めない**（`val x = _` 不可）。**残り無視 `..` は持たない**（ユーザーも Rust で使わずに済んできた／大構造体以外は `_` で足り、安全側に倒す）。**構造体/レコード/バリアントを開くパターンは全フィールド明示必須**（束縛 or `_`）。**根拠**：フィールド追加時に既存の分解/match がコンパイルエラーになり新フィールドの扱いを強制＝静かな取りこぼし防止（match 網羅性と同じ「静かな嘘を返さない」精神）。**Rust も既定では黙って無視せず `..` を要求する**（`E0027`）ことを確認＝本決定は「Rust の全フィールド明示」から `..` の逃げ道を外しただけで新規ルールではない。**対価**：やや冗長（`_` で吸収）。名前位置の葉は 3 種（`val x`＝新規／bare `x`＝既存マッチ／`_`＝破棄）。
  - **`elif` 廃止 → `else if`（決定）**：`elif` 専用キーワードを持たず、`else` の本体が単一 `if` のときの連鎖として書く。近接言語 Swift/Rust/C 系がすべて `else if` で、`elif`（Python/Bash 系）は Plew の語彙の中で予想外＋キーワードを 1 つ増やすため不採用（「単純 > 紛らわしい」）。spec/01 キーワード表・spec/11 から除去済。
  - **条件チェーン：if-let/while-let も束縛可・連結は `&&`（Rust let-chains 流／決定）**: `if`/`while`/`guard` の条件を**条件チェーン**に統一。**却下案**：Swift の `,` 区切り＝`&&` を値レベル Bool 専用に保てるが新しい区切り意味を増やす＋既存 guard 例の書き換えコスト。**`&&` 採用の根拠**：(1) spec の guard が既に `&&` で一貫、(2) Plew は構造体生成が JSX 限定なので Rust 流の「条件位置で構造体リテラル禁止」制限が不要、(3) 値レベル `&&` はこの条件チェーンの〈全節 Bool〉特殊形と説明でき概念は一つ。**`&&`/`||` を制御フローにした判断との整合**：trait メソッドは引数が正格評価済みで届くので短絡は表現不能、ゆえに短絡は制御フロー側に置くのが必然。**by-name 引数（Scala `=> T`）も同根拠で却下**：呼び出し側に痕跡が残らない暗黙の非評価で「明示>暗黙」に反する（遅延が要ればクロージャか `<Lazy />` で明示）。

### トレイトを値型にする存在型（`any`・決定・→ [spec/08](../spec/02-type-system/08-traits.md)）
- **`any P` を導入**：トレイトを値の型として使える（型消去・動的ディスパッチ・異種混在）。動機は **Plew = Programming Language for Everyday Wizard**＝トレイトの配列を Swift のように素直に書けるべき、という根幹思想。`children: Array[any Component]` のような React 風ツリーが第一の用途（ジェネリック `[T]` は同種しか持てず不適、手書き型消去ラッパは構築側 boilerplate が重い）。**実装順は最後でよいが必ず実装する**。
- **マーカーは `any` のみ・`some`（opaque）は持たない**：`dyn`（Rust）でなく `any`（Swift）採用＝「動的ディスパッチ」という実装語でなく「準拠する任意の型」という概念を指し everyday wizard に自然。`some`/opaque を入れないのは、ユーザーが「`any`/`some` の使い分けはややこしい」と評したため＝マーカーは 1 つに絞る。**marker 必須の実利**：ジェネリック `where T: P` と存在型 `any P` が見た目で別物になり「横着して `n: P`」問題が解け、object-safety 違反の診断が `any` に紐づく。
- **形成は全型引数・全関連型を束縛必須**（決定）：**理由＝この縛りで `any P` 内に残る消去が `Self` ただ一つ**になり、呼び出し規則が単純化（関連型の共変再消去のような曖昧さを排除）。Rust の `dyn Trait<Assoc = …>` と同趣旨。
- **object-safety は型レベルの一律禁止でなくメンバ単位・使用箇所診断**（決定・modern Swift SE-0309 と同方向）：**却下＝旧 Swift 流の型レベル一律禁止**（「Eq は Self 要求があるので型にできない」は抽象的で分かりにくい、とユーザー評）。エラーを使用箇所に局所化し「2 つの `any Eq` は別型かもしれず比較不可」と具体的に出せる。
- **`any` で呼べる範囲の正確化**：「Add/関係系は存在型にできない」は雑な括りで、**全型引数/関連型を束縛すれば呼べる**（`any Add[I32, Output=I32]` で `+` 可）。本当に詰まるのは `Self` 入力と関連関数だけ。
- **ダウンキャストは無い（v1 不採用・additive 保留）**：`any P` から具体型/別トレイトを取り出す機構を提供しない（Rust と同姿勢・Swift `as?`/Go type assertion 相当なし）。**却下理由**＝(1) 開いた存在型は網羅不能で型分岐が必ず `_` 付き可謬チェックになり「match は網羅必須」と噛み合わない、(2) `as` は infallible 固定で可謬ダウンキャストを載せられず `TryFrom` は値変換で別カテゴリ＝既存の綴りに乗らない、(3) 定番動機のエラー検査は Plew では値型 enum＋集約 From で既に具体 `match`＝最大の使い所が存在型側に無い。**閉集合は列挙型＋網羅 match、開集合のインターフェース限定が `any P` という役割分担**で代替十分。**気概**＝欲しくなったら設計の誤りを疑う（ユーザーも「Rust で困ったことがない」）。将来入れるなら `Any` 風 opt-in 定型でなく `match` の型パターン（`_` 強制・具体型のみ・`any P → any Q` のグローバル準拠探索は ambient マジックゆえ却下）。→ spec/08。

### 文字列とコレクション（String / Array / Slice・→ [spec/02](../spec/01-basics/02-basic-types.md)）
- **`String` は不変・UTF-8 常に妥当・`==` はバイト等価（決定）**: Swift/Rust/Go を比較した結論。**不変にした根拠**：値意味論なら「参照＋可変＋共有」のエイリアス footgun は無いが、不変だと UTF-8 妥当性の不変条件を保ちやすく `==` がバイト等価で済む（CoW 値型として安全に共有でき、将来 Swift 流の可変 CoW String を足すのも非破壊）。**却下：Swift の `==` 正準等価**（正規化コストが隠れる）＝明示原則に反する（要れば明示正規化、API 未決）。**却下：Go の「妥当性不変条件なし」**（保証が緩すぎ）＝「静かな嘘を返さない」方針。
- **`String = struct { pub(get) bytes: Array[U8] }`**: 内部表現がそのままバイト配列なので getter を生やさず**フィールドで公開**（方針：**stored は `pub(get)` フィールド、computed だけメソッド**）。不変条件は `pub(get)`（write 内部）＋任意バイトの公開 factory を持たない（生成はリテラルと検証 factory `fromBytes -> Result` のみ）で守る。
- **要素ビューは明示選択・型がコストを語る（決定）**: `bytes`（`Array[U8]`・`count` O(1)）／`scalars()`／`graphemes()`（イテレータ・`count()` O(n)）。`*_count()` を生やさず「配列 count=O(1)／イテレータ count()=O(n)」で自明にする（ユーザー発案）。**整数添字 `s[i]` は持たない**（可変長 UTF-8 で O(1) 添字は嘘。Swift/Rust も拒否）。Rust の `char`/Go の `rune` は**スカラ＝書記素でない**ので絵文字・結合列を割る罠があり、書記素を第一級で出せる Swift の長所だけ取り込む。
- **`Array[T]` 一本・`[E; N]`（const generics）は持たない（決定）**: 日常配列は動的・伸長・連続・プリミティブ unboxed（Java `int[]`／C# 配列モデル＝WASM ゼロコピーの前提）。**根拠**：`[E; N]` を実用にする＝const generics 必須で**型システムが一段重く紛らわしい**大物、しかも CoW＋ARC の Plew では「インライン格納でスタック確保」という Rust の主動機が弱い。需要が固まれば**非破壊で後付け**できる（C#・Swift も後から InlineArray を足した前例）。
- **C 固定長配列はタプルでなく同型 `Array` に写す（決定）**: **C 配列は定義上ホモジニアス**なので、Swift が異種タプルに落としたのは「固定同型型が無かった」苦肉策。Plew は**同型は `Array[T]` へ（境界でコピー）**写す。
- **Array は「生メモリ床の上の Plew struct」に寄せる（決定・Swift/Rust モデル・実装は段階的）**: 現状 Array は generics 導入前に作られた**コンパイラ 1-off**（専用ランタイム `PlewArray_<E>`＋`.append`/`[i]`/`.count` 決め打ち）。メソッドを Plew 化するのに「Array 専用の mono 経路」を足すのは **workaround＝Array が特別なまま残る**ので採らない。**あるべき姿＝小さな生メモリ床（`RawBuffer[T]`＋数本の intrinsic）を還元不能の床として置き、Array を Core の `struct Array[T] { data: RawBuffer[T]; len }`＋Plew メソッドにする**。これで Dictionary/Set/String 内部/独自コレクションが全部同じ床に乗る（**前例＝Swift の `Array` は `ManagedBuffer`/`Builtin` の上のライブラリ型・Rust の `Vec` は `RawVec`/`ptr` の上**＝どちらもコンパイラ内に Array 実体を持たない）。**CoW の肝＝`RawBuffer` を `Ref` と同じ「値意味論機構が自動 retain/release する参照」として足す**＝コピーでバッファ共有・破棄で解放が既存機構でタダで正しくなり、変更系メソッドが `rawIsUnique` を見て複製する＝copy-on-write が Plew で書ける（**新 Clone/Drop プロトコルは作らない**＝値意味論の哲学を保つ）。**還元不能な床はなぜ残るか**：可変長・連続・unboxed・CoW・ARC を「魔法を隠す（hidden cost 可）」で実現するには生メモリ確保/生ポインタ読み書き/refcount が要り、これは型システムでは表現しきれない＝Swift `Builtin`・Rust `intrinsics`/`ptr` に当たる最下層。生ポインタは**先送りした `extern "C"`（FFI）とも地続き**。設計詳細・段階分けは [worklog](worklog.md)。
- **位置タプル廃止 → ラベル付きタプル（無名・構造的レコード）（決定）**: **動機**＝「位置指向のタプルが、全部名前付きの言語で唯一の例外だった」を解消（構造体・enum バリアントは既に名前付きのみ＝`Some(T)` 不可）。**経緯（却下案）**：①無名 struct を JSX `<x=1/>` で生成する案は、分解パターンが bare `{…}` でブロックと衝突（JS の `({a,b}=o)` 問題）。②`${}` 記号は Perl 臭く型/生成/分解の 3 面がバラバラ。→ **タプル廃止で空いた `()` に置く**のが新記号ゼロ・`{}`（ブロック）と非衝突・「全部名前付き」と地続きで最良。
- **変数束縛は `val`＝新規・bare＝既存（決定。分解・for へ拡張）**: スカラの「`val x` 宣言／`x =` 代入」を分解・`for` にも一般化（→ [spec/03](../spec/01-basics/03-values.md)）。**未初期化宣言は持たない**（Swift の `let x: T` 後分岐代入は `val x = if c { give 1 } else { give 2 }` で代替＝確定代入解析を持ち込まない）。文頭 bare `{` はブロックのまま（無名レコードが `()` なので衝突せずスコープ用独立ブロック文を温存）。
- **Slice / Substring は当面持たない（保留・additive）**: ゼロコピーのビュー型 `Slice[T]` と String の substring API は**入れない**。**手詰まりにならない根拠**：いずれも純粋に additive（Array 意味論も既存シグネチャも壊さず後付け可）。**マネージド言語の前例**：性能の答えは `[E; N]` でなく「連続バッファ＋ビュー」＝.NET `Span`／Java Panama `MemorySegment`／JS `TypedArray`／Python `memoryview`。スライス取得は（入れるなら）`[]` でなく**メソッド `arr.slice(...)`**（`[]` は要素値専用、view は名前付き操作で可視化）。**スライスを入れるなら 2 型**（所有伸長 `Array` ＋固定ビュー `Slice`＝C#/.NET 流）で Go の append-aliasing footgun を避ける案を本命とする。
- **文字列構築はビルダ（不変＋ビルダがワンセット）**: 逐次連結の O(n²) を避けるため、伸長可能ビルダで溜め確定時に不変 String へ封じる（Java `StringBuilder`／Go `strings.Builder`／Python join 型）。型名・API は未決。
- **文字リテラル `'…'`＝1 書記素・単一スカラ時はコードポイント整数に縮退（決定・→ [spec/02](../spec/01-basics/02-basic-types.md#文字リテラル)）**: `'…'` は概念上「1 書記素クラスタ」で、中身の構成で多相に行き先が決まる ── **単一スカラなら値＝コードポイントの多相整数**（`'/'`→47・`'あ'`→12354）、**複数スカラ 1 書記素（`'🇯🇵'`）は将来の `Grapheme` 型のみ**、**2 書記素以上／空はエラー**。**根拠**：Plew の数値リテラルが既に「多相・既定型なし・収まらなければエラー」なので、char を「コードポイント値の数値リテラル」とすれば新機構ゼロで乗る（**Zig 流**＝`'a'` は codepoint の `comptime_int`）。コードポイントは Unicode 固定でエンコーディング非依存（バイト列だけが UTF-8/Shift-JIS で変わる）。**却下：Rust 流 `'a'`(char 32bit)＋`b'a'`(u8) の 2 系統**＝独立した `char`/Scalar 型がある時に初めて元を取る。Plew は今その型が無く、`"…"`(String) と `'…'`(1 書記素) で役割が割れていれば「どちらでも書ける」も起きないので 1 系統で十分（Scalar 型を将来入れるなら `b''` を additive 追加可）。**先例**：複数スカラ書記素を値にできる `Grapheme`＝**Swift の `Character`**（`let c: Character = "🇯🇵"`）。
- **`Grapheme` 型と内部表現は Substring/Slice 実装とセットで未決（保留）**: `'🇯🇵'` のような複数スカラ書記素を第一級の値にするには `Grapheme` 型が要るが、その**内部表現が悩ましい**＝(a) 所有する CoW `String`（リテラルから直接作れる・Swift Character 流）か、(b) 親文字列へのビュー `Substring`（リテラルからは作れない＝指す元が無い）か。**CoW なら所有でもビュー共有が安く両立し得る**が、これは [Slice / Substring を当面持たない](#)（上）の決定と一体で、**文字列の部分文字列・`Slice` を本格実装する段でまとめて決める**。それまで `'…'` は単一スカラの整数形のみ実装し、`Grapheme` 形は未実装（spec valid だが reject）。**実装コストの留保**：「ちょうど 1 書記素か」の判定は UAX #29 の書記素分割が要り、妥当性が**コンパイラの Unicode バージョンに依存**する（整数の「収まるか」より曖昧さが一段入る）。

### モジュールと無名 impl の配置（`part`・→ [spec/15](../spec/04-execution/15-modules.md)）
- **無名 impl の配置単位＝モジュール**と決定（impl 権はモジュールに紐づく）。無名 `impl T as Tr` は **T を定義したモジュール内にのみ**置ける（Rust の「型 or トレイト所有」より厳格な型所有版）。
- **却下した代替**: ① file = module（明示的だが impl を型と同一ファイルに強制＝窮屈）② directory = module（楽だが境界が暗黙）。「明示・非窮屈・新機構なしは2つまで」というトリレンマと認識し、明示最優先の方針に従って「新機構（`part`）を足して明示＋非窮屈」を選択。「impl は trait か struct を定義したモジュール内のみ」を厳格にすると単一ディレクトリでは狭すぎる、というのが directory 却下の決め手。
- **モジュール内はスコープ共有、外部 import はファイル単位**。暗黙の可視性を「明示的に綴じた part ツリー」の内側に限定することで、拒否したディレクトリ境界の暗黙性と区別する。
- **ディレクトリパスの解決＝`_.pw`**: 固定英単語（`Mod`/`Index`）や同名重複（`Foo/Foo.pw`）を避け、`_` は「ディレクトリ名をそのまま継ぐ代表ファイル」の意。**`_.pw` はディレクトリを集約せず単なる単一ファイルモジュール**。検索性低下は軽微（エディタで吸収）と判断して許容。
- **再エクスポート**: `export <path> with {...}`（`import` を付けず・ローカル非束縛＝JS の `export...from` 相当）。全取り込みは `with *`（`all` は camelCase メンバ名と衝突しうるため `*` を採用）。1ファイル1モジュールゆえ再エクスポートは必須で、公開 API の「バレル」構築に使う。

### メンバ可視性＝impl ブロック単位（`pub impl`・決定・→ [spec/05](../spec/02-type-system/05-structs-enums.md#メンバの可視性)）
- **メソッド・関連関数・factory の可視性は `impl` ブロック単位**＝`pub impl Type { … }` でブロック内全公開、修飾なし `impl Type { … }` で全非公開（無名 impl 内のみ）。**メソッド個別の `pub fn` は廃止＝エラー**。混在は `pub impl`/`impl` の **2 ブロックに分割**。**フィールドだけは per-field**（`pub`/`pub(get)`）＝`pub(get)` の「読み公開・書き内部」という読み書き非対称はブロックに畳めないため。
- **根拠**：①**conformance は単位**＝トレイトの全要求を満たすので「一部公開・一部非公開」は中途半端で不整合。②**`via` と相性**＝`impl A as P { via existingMethod }` で witness が既存メソッド（自前可視性持ち）のとき per-method `pub` は曖昧、ブロック単位なら「この準拠が公開か」だけで決まる。③**明示 > 暗黙の方針**＝可視性の指定点が 1 箇所に集約。④**Swift と同型**（conformance/extension にアクセスレベル）。**却下案＝per-method `pub fn`**（Rust/Swift 流）は ①②に反し、conformance で半公開の不整合を許す。
- **トレイト準拠の可視性も同形**：`pub impl Type as Trait`＝公開準拠／修飾なし＝内部準拠（事実はモジュール内成立で `where`/`any` に使えるが外部メソッド呼びは可視性エラー）。**`export impl` は無し**（外部到達は型の `export`＋`pub impl` の組）。
- **Plew 固有の核心＝resolve-by-type ゆえメンバ可視性が trait メソッドを隠す唯一の軸**：Plew はトレイトメソッドを**レシーバ型だけで解決**し呼び出し側に trait を import させない（[lang item 方針](../spec/04-execution/15-modules.md#言語アイテムは常にスコープにあるimport-不要)）。よって **Rust の「trait がスコープに無ければ trait メソッドも見えない」自然ゲートが効かない**。Rust は trait 可視性がメソッド可視性を兼ねるが、Plew は分離するので「export していない内部実装も（暗黙 public だと）外から呼べてしまう」問題が出る。これを `pub impl` か否か（メンバ可視性）で塞ぐ＝**「暗黙 public」を却下**し witness にもブロック可視性を適用。**Swift の確認**：public 型×public protocol の準拠は witness を明示 public にせよとエラー強制（自動 public でない）＝Plew の「private witness で内部準拠」は Rust 的「内部は内部に閉じる」を member 軸で実現。
- **直交 2 軸**：`export`＝モジュール境界（その型/関数/トレイトに到達できるか）／`pub impl`・`pub`＝型カプセル化（到達した型のどのメンバを使えるか）。spec/15 のモジュール可視性と spec/05 のメンバ可視性は独立。
- **実装**（worklog の I2）：Phase B＝モジュール可視性（export/import 強制）→ Phase A＝メンバ可視性。**コンパイラは自由関数が struct のフィールド/メソッドを直接触る様式**で spec の private＝「無名 impl 内のみ」と衝突するので、`Comp`/`Lexer`/`TypeRef` 等の impl を `pub impl`・触るフィールドを `pub` にする**機械的大掃除**が要る（コンパイラ struct 全 pub 化＝spec 準拠で実害なし・enforcement の実価値は stdlib の pub(get)/内部準拠を将来含め守ること）。[[visibility-before-stdlib-grows]]。

### パッケージ（分散・TOML マニフェスト・→ [spec/15](../spec/04-execution/15-modules.md)）
- **中央レジストリ無し**（Go modules / SwiftPM 思想）。各パッケージは **TOML マニフェスト**（暫定名 `Plew.toml`）を持ち、依存を **git / ローカルパス**で指定。
- **依存はローカル名に束縛**し `import @Name` で使う。上流のパッケージ名衝突は**消費側のローカル名**で解決（Cargo の rename / Go の replace 相当）。
- **import のルートは 3 つ＝`@…`（自分の外）／`/…`（自前・ルート起点絶対）／`./`・`../`（自前・相対）。bare 名は不可（決定）**。`import Foo` を禁じる既存方針（相対/外部/std が記号で判らなくなる）を std にも貫く。**経緯**：std を bare（`import Io`・多数の予約 bare 名）にする案、`@Std`（外部と同じ `@`・名前で判別）にする案を比較。bare＝std は「`@` を外部依存専用に純化」できて provenance が鋭い一方、**「bare 禁止」という既存の根本決定を std だけ特例で破る**＋bare 名カテゴリ全体を予約する。`@Std` は「bare 禁止」を維持し記法を増やさず、`Std` は周知の予約名で provenance も保たれる ── **後者を採用**（`@` の意味は「外部依存だけ」→「自分の外＝std か他人・名前で判別」に少し広がるが、既存方針の一貫性を優先）。**他言語**：区別する Dart（`dart:`/`package:`/相対）/Node（`node:`）/Deno（`jsr:@std`/`npm:`）/Go（短名 vs ドメインパス）は「std に専用マーカー」、区別しない Rust/Python/Java/C#/Swift は「同記法・名前判別」── Plew は後者型（`@` 共有・名前判別）。
- **自前ルートにルート起点の絶対パス `/` を追加（決定）**＝`import /Models/User` は `src/Models/User.pw`（`/` 単体は `src/_.pw`）。**動機**：深いネストで自前参照が `../../../` に膨れる（Node でも顕在化する）問題。**根拠**：相対パスは *import する側*の位置をエンコードするので import 側を動かすと壊れ、`/` は *ターゲットの同一性*（ルートからの位置）をエンコードするので import 側の移動に強い＝**リファクタ安定**かつ provenance も `../../` より正直に固定（ターゲット側を動かせばパスは変わる＝`public` の path=file と同じ Go 流の正直さ）。**到達範囲**：`/` は自パッケージ内ゆえ外部公開を絞る `public` ゲートを通らず、`./`／`../` と同じく自パッケージのどのモジュールにも届く（違いはルート絶対かファイル相対かだけ）。Rust の `crate::`（`super::` と二系統）に相当し、運用は「近接は相対・遠隔/深いネストは `/`」。**却下案**：(a) **マニフェストでファイル別名宣言**（webpack の `@app/*` 流）＝任意の深さに任意の別名 ── 先頭記号を見ても実パスが分からず **provenance 隠蔽**（bare 名を禁じた理由と同じ穴）ゆえ却下。(b) **自己 `@` 名**（`@Self/Foo` 等で自パッケージを `@` 機構で参照）＝`@`＝「自分の外」という不変条件を濁す（`/` で足りるので不要・`@` は外部専用に保つ）。**他言語**：Rust=`crate::` あり／Go=相対 import 無しで全部ルート絶対（深い相対問題が原理的に出ない）／**Zig=ルート絶対は無く、深い参照の逃げ道は build.zig の名前付きモジュール登録**（= 粗い粒度のエイリアス＝案 (a) を*モジュール単位*に限定した形・webpack のようなファイル別名は誰もやらない）── Plew は `/` で Zig が build.zig の間接で払うコストを払わず provenance も明確。**ワークスペース（複数パッケージ分割）は直交する別軸の将来機能**（「深すぎる」でなく「分割したい」への解）。
- **`@Std` は標準ライブラリの予約名（決定）**。マニフェスト束縛不要・常に `import @Std/…`（唯一マニフェスト不要の `@`・ローカル名に `Std` 不可）。**std は分割する**（フラットにしない）＝`@Std/Http`・`@Std/Testing` 等。**根拠はサイズでなく名前空間**：フラットだと全名が大域一意必須で `Json.parse`/`Toml.parse` の領域跨ぎ衝突が書けない・修飾アクセス不可・プラットフォーム条件付き能力をモジュール有無で表せない（ツリーシェイクはサイズ問題だけ解く＝分割理由ではない）。全 std が分割されている（Rust モジュール/Go/Python/Java/Node/Dart パッケージ）。領域の正確な一覧は core-lib 送り。
- **パッケージは複数モジュールを公開可・公開面はマニフェストの `public` で宣言・公開パスは実ファイル（決定）**。`@Dep/Foo/Bar`・`@Std/Http/Server` の**任意深さサブパス**を許可（Go/Rust/Node/Dart/Python と同じ）。`public` は実パス列挙（**既定 `["_"]`＝ルート `src/_.pw` のみ**・`_`＝ルート・`[]` で封印・ディレクトリ糖衣可）、**列挙外は内部実装で到達不可**（カプセル化）。単一モジュールは `public` 不要で `import @Dep`（`_.pw` 規約でルートが裸＝Dart の `package:foo/foo.dart` 重複を回避）。**path=file（rename しない）＝Go 流の正直さ**（公開ファイル移動＝公開 API 変更）を採り、**rename 公開（Node の `exports` 流）は却下**（公開名が実体と乖離＝「実態と異なる名前」をユーザーが嫌った）。リファクタ安定のための別名公開は将来 additive。所有境界の encapsulation が `part`→`export`→`public` で 1 段ずつ増える形に揃う。**旧「公開エントリ＝`src/_.pw` 固定・サブ到達不可」は撤回**（複数公開モジュールを許す形に拡張）。
- **実行エントリ＝`fn main`（決定）**。開始点は `fn main`／`async fn main`（async は任意・同期は無税）。**選択は 2 段＝ビルドでファイルを明示 ＋ その中の `main` がエントリ**（プロジェクト全体から探索せず・`bin/` 等の特別ディレクトリも無し）＝`plew build ./src/client.pw` と `./src/server.pw` でモノレポ複数エントリが同一モデルを共有。**トップレベル文は持たない**（命令的開始点を `main` に分離＝force-on-read 初期化順との衝突回避）。実行は **①全トップレベル/`assoc val` 初期化 → ②`main`** の 2 段。**戻りは `()` か `Result[(), E]`**（後者で `main` 内 `try` 可・`Err` は表示して非ゼロ終了＝`Termination` 相当 lang トレイト）。**引数/環境は仮引数でなく stdlib**（`import @Std/Process`→`Process.args()`/`Process.env`・`print`/`Random` と同じ「ambient 能力を import で明示取得」・`Process` は非 lang item）。**終了は main 返却 ＋ イベントループ drain**（保留タスク/タイマ/リスナ/未 join spawn が無い・Node/ブラウザ流＝UI は mount して return でループ生存）。**`main` は実行可能ビルドのみ必須**（ライブラリ＝JS から呼ぶ WASM 等は不要・export 面のみ）。→ spec/15「実行エントリ（main）」「ビルド」。
- **同一パッケージの複数バージョンは共存を許す方針**（依存解決ツールの詳細は実装時に別途）。

### コアライブラリの境界＝intrinsic ブロック＋名前ベース lang item（決定・→ [spec/15](../spec/04-execution/15-modules.md)）
- **方針（3前提）**：①Plew で書けるものは Plew で書く ②プログラマが呼べるものは **Plew コードで明示宣言**（不可視ビルトインを無くす） ③専用構文は最小限。
- **コンパイラ↔ライブラリのグルーを 2 機構だけに集約**（Rust/Zig が収束する形・matklad「privileged stdlib が本体なし intrinsic を宣言する／ad-hoc 演算子を足す」）：
  - **(1) intrinsic ブロック `extern(<abi>) { fn …（本体なし） }`**＝Rust の `extern "rust-intrinsic"` / Zig の `@builtin`。当面の ABI は **`plewIntrinsic`**（bareword・旧 `"plew-intrinsic"`・下記「外部コード統合」で ABI 選択子を文字列→bareword に統一）（自前ランタイム束縛・引数/戻りは **Plew 型**・コンパイラが lowering＝`String`→`PlewString` 等は層αのまま隠蔽・C シンボルは規約 `plew_<name>`〔ランタイム側を camelCase に統一〕）。本物の外部 C は **`extern(c)`** を**同じ構文に additive**（下記「外部コード統合」で確定方向）。
  - **(2) lang item＝名前ベース**（`Optional`/`Result`/`Ordering`/`String`/`Array`… を型名でコンパイラが役割解決）。型自体は std `.pw` に明示（前提②満足）。std 単一ゆえ Rust が `#[lang]` を要した事情（no_std/多 crate 再束縛）が無く名前ベースで足る。将来不便なら std 側マニフェスト表へ（属性は使わない）。
- **層**：α コンパイラ核（リテラル構文→lang item 型・`String`/`Array`/`Promise`/`Ref` の表現と ABI・演算子脱糖表・intrinsic 本体 codegen＝不可避）／β 薄い intrinsic 床（`extern "plew-intrinsic"` 宣言＝`write`/`readStdin`/`sleep`… ＋将来の Array/String 原始操作）／γ 純 Plew（Optional/Result/assert・高位メソッド・`print` 整形…＝最大化）。
- **メソッド由来の intrinsic は free 宣言＋Plew ラッパ**（`extern { fn arrayPush(a~: inout Array[U8], byte~: U8) }` ＋ `impl Array { inout fn push(...) { arrayPush(...) } }`）。Rust の `core::intrinsics` も全部 free function でメソッドは library 側。**却下**：impl 内 extern／extern 内 impl（入れ子規則が増える・前提③違反）。
- **lang item 型の宣言も同じ extern ブロックに（決定・Swift モデル）**：`extern "plew-intrinsic" { struct I32 … struct String }`（**本体なし＝不透明 intrinsic 型**）。ブロックの意味が「Plew の外が中身を供給する宣言」に自然拡張＝`fn`＝**本体**を runtime 供給／`struct`＝**表現**をコンパイラ供給。**動機＝コヒーレンス**：Plew は**型所有版**コヒーレンス（spec/09・Rust の「型 or トレイト」より厳格）なので、`impl I32 as Format`/`Eq`/`Ord`/`Add` を**純 Plew で書くには Core が I32 を所有＝定義する必要**がある。**他言語**：Rust=プリミティブは組み込みのまま std だけ orphan 例外で impl（"the only library that does so"）／Zig=struct も trait も無く comptime リフレクションで整形／**Swift=`struct Int { _value: Builtin.Int64 }`＝stdlib の struct が intrinsic 表現を包む**。Plew の型所有コヒーレンスは **Swift 型（型を宣言して所有）と噛み合い**、Rust 型（特権例外）は浮く（フラットモデルで Core を識別できず例外を強制できない）ので Swift を採る。**`builtin` 等の新キーワードは足さない**（premise 3）。実装＝`StructDef.isExtern`・codegen は全 struct ループでスキップ（C の `struct I32 {}` を出さず表現は既存の名前→C 型写像＝`int32_t`/`PlewString` のまま）・`checkImplOnBuiltin` を「extern struct 宣言のある型は所有→bare impl 可」に是正（inherent/準拠とも所有則で一貫）。**完全な orphan 強制（ユーザも `extern struct I32` を書ける穴）は module identity（I2）待ちの provisional**。`String` は spec の `struct String { bytes: Array[U8] }` 実フィールド化＝表現移行ゆえ別段（当面 no-body で所有だけ確立）。これで `print[T] where T: Format`（`Format`＝`fn format(format: String) -> String`・補間 `{x}`＝`x.format(format: "")` と同一トレイト・spec/02）が純 Plew で書ける（要 `extern { fn stringFromBytes(b~: Array[U8]) -> String }` で整数→String 整形）。
- **演算子/数値トレイトタワーも最終的に全て純 Plew・可視（決定・コンパイラ埋め込みゼロが目標）**。`impl I32 as Add[I32] { type Output = Self  assoc fn add(lhs: Self, rhs: Rhs) -> Output { return addI32(lhs: lhs, rhs: rhs) } }` の形で **Core に plain Plew で書く**（derive 合成や演算子のコンパイラ直 lower に**頼り切らない**＝premise 2 を算術まで貫く）。**還元不能な floor は「名前付き intrinsic」だけ**＝`extern "plew-intrinsic" { fn addI32(...) }`（Swift の `Builtin.add` / Rust の `intrinsics` 相当だが **`extern` 宣言として可視**・ロジックでない）。**パフォーマンスは最適化器任せ**：`plew_addI32` を runtime に **`static inline`**（overflow チェック込み）で置けば -O2/LLVM が**単一の checked-add 命令に畳む**（Rust の `i32::add` が実関数なのにゼロコストなのと同じ）＝「`+` ごとに関数呼び」は最適化ビルドでは起きない。ゆえに **`addI32` は `write` と同じ一様 runtime-call intrinsic で十分**（「inline intrinsic 専用カテゴリ」も `extern { impl }`〔impl を extern で包む〕も**不要**）。`+`→`Add.add`→`+` の再帰は **`add` の本体が `+` でなく `addI32` を呼ぶ**ことで断つ（最終的に `+` は全型一様に `Add.add` へ脱糖）。**線引き＝関連型の有無**：`Add`/`Sub`/`Mul`…（`Output` 関連型あり）は**関連型実装が唯一の本物のブロッカー**で待ち／`Eq`/`Ord`/`Format`（関連型なし）は**今すぐ plain Plew 可**（ただし `Eq`/`Ord` は全比較を `Eq.eq`/`Ord.compare` 経由へ再配線する波及があり順次）。**`@[Eq]` derive 合成も最終的にこの floor＋Plew impl へ寄せて埋め込みを消す**（将来整理）。当面の print は `Format`（関連型なし・本体の `/`・`%` はコンパイラ lower のままで可・要 `stringFromBytes`）だけで進む。
- **却下案**：(a) `@[builtin("…")]` 属性＝derive/メタプロ表面（spec/16・後回し）を開く＋属性機構拡張が要る。(b) インライン `extern "…" fn`＝ブロックと二重構文（前提③違反）。(c) ランタイム関数を `extern "C"` で宣言＝`String↔PlewString` の内部表現を userland に晒す/依存＝表現リーク（自前ランタイムを foreign 扱いする provenance 倒錯）。(d) intrinsic 本体（C）の外部ファイル切り出し＝Rust/Zig も本体はコンパイラに残す＝理想条件ではない（コード整理として任意）。
- **本本でも `print` だけ当面ビルトイン残置**（型に応じた符号付き/なし整形＝`%lld`/`%llu` 選択が要る＝Display/整形 std が無いと純 Plew 化できない）。整形 std 整備後に γ へ移す。

### 外部コード統合（FFI・`extern(c)`/`repr(c)`/`CPtr`・設計叩き台・→ [spec/15](../spec/04-execution/15-modules.md#外部コード統合externc-ffi)）
- **動機＝LLVM バックエンド**。意味論が出揃ったので LLVM 化に着手する前提で FFI を設計。**LLVM は libLLVM-**C** API（安定 C API）を叩く**＝C++ interop は不要（C++ には安定 ABI が無く、どの言語も C++ には直接 FFI せず、rustc も `llvm-wrapper/*.cpp` で `extern "C"` シムを書いて C++ API を露出する＝Plew 側の言語機能は最後まで `extern(c)` だけで足りる）。**LLVM-IR テキスト出力は飛ばす**（終着が C-API で確定なら使い捨ての足場・C-API なら `LLVMPrintModuleToString` で IR ダンプも得られる）。**パッケージ管理は LLVM の前提でない**（バックエンドは in-tree・M3 は別トラック）。
- **FFI はメタプロでなくコア言語＝キーワードで表す（決定）**。レイアウト/ABI 制御は**ソース生成で表現不能**（C レイアウトを意味する Plew ソースが無く必ずコンパイラ原始要素に底打ち＝どの言語の FFI も公理）。ゆえに `@[Repr(c)]` のような**属性は使わない**（`@[...]` は「純粋 codegen マクロ」専用の不変条件を破る）。Plew は既に `extern(plewIntrinsic)`/`unique`/`Ref` 等**キーワードでコンパイラ指示**を出しており、FFI はその閉じた語彙を数語増やすだけ＝ポリシー（メタプロ＝純粋 codegen）はむしろ純化。**避けるのは「codegen を変える一般属性機構」**で、閉じた FFI キーワード追加はそれと別物。
- **役割 × ABI の 2 軸（決定）**。`extern` は「**外部に実体がある（本体なし）**」だけを意味し、ローカル定義に使わない（キーワードが定義場所を正直に告げる）。`extern(c) { fn/type }`＝import・`repr(c) struct`＝C 共有レイアウト（向きを持たない値型）。**却下＝`extern struct`（Rust/Zig）**：Zig 定義なのに C レイアウト＝定義場所と ABI の畳み込みで「C 側で定義」に誤読される（両先例の wart を Plew は踏まない）。**スコープ＝使う側（C を呼ぶ）のみ。使わせる側（export＝Plew→C 公開）は未定**＝既存 `export` キーワードと紛らわしく要設計・現状の LLVM 利用に不要ゆえ仕様から外す（将来 additive・`repr(c) struct` は方向非依存なので export を定めればそのまま乗る）。
- **`repr` の引数 `c` ＝ C *ABI*（C 言語でない）（決定）**。各ターゲットで唯一の標準データレイアウト ABI＝万能相互運用規約。**却下＝`repr(stable)`/`repr(fixed)`**：相互運用に要るのは property（決定的）でなく contract（どの規約か）で、`stable` は「どの固定か」を言わず**under-specify**・かつ将来 `packed`（これも決定的）と衝突＝**規約で名付け**スケールさせる。
- **ABI 選択子は bareword・パレン括り `extern(c)`（決定）**。ABI はコンパイラ定義の**閉じた集合**（ユーザー定義不可・intrinsic 床と同じ原始要素）。**却下＝文字列 `extern "c"`**：「何でも入る」と閉集合を偽装＝import パス直書きと同じ「本質的に文字列でない箇所はクォートなし」方針に反する。**決定的証拠＝Rust も文字列だが集合は閉じる**（`extern "florble"` はエラー）＝文字列の利点はハイフン名と予約語回避だけで、Plew は camelCase（`cUnwind`/`plewIntrinsic`）で両方解決＝bareword で失うものなし。「LLVM が未想定 ABI を吸収」は**誤り**（LLVM の cc も closed enum・C ABI の集合体分類はフロントエンド自前＝どこも閉じている）。素通し設計だけが「開いて見える」が `全ターゲット同一意味論`/`曖昧はエラー` を破るので不採用。**却下＝`extern(system)` を C ライブラリに**：`system` は OS API 規約（Win32 で stdcall）で `c` と別物・C ライブラリ（libLLVM）には `c` が正解（非 Windows で偶然一致するだけ）。
- **不透明ハンドル＝`extern(c) { type Name }`（決定）**。C の `typedef struct …Opaque *Ref` に 1:1・名前ごとに別の名義型（暗黙変換なしゆえ取り違えコンパイルエラー＝`void*` 素通りを塞ぐ）・コピー可能 1 語・**deinit 自走しない**（外部寿命を知らない＝生のままリーク/二重解放可）。安全化は **`unique` struct＋`deinit`** で包む（`Array`→`RawBuffer` と同じ「生床＋安全な皮」分離）。
- **C ポインタは const/mut を分ける（決定・Swift 流）**。`CPtr[T]`（無印＝`const T*`・読み取り）／`CMutPtr[T]`（可変は明示＝`T*`）／`COpaque`（`void*`）。**却下＝単一 `CPtr`**：`.h` は const を区別＝畳むと bindgen が lossy・かつ const/mut は Plew の borrow/inout・shared/unique と同じ「読む権利/書く権利」軸で意味がある・無印を安全側にして可変を長名で明示（`mut val` と同流儀）。`RawBuffer`/`Ref` 同格の組み込みプリミティブ（属性でなく型語彙）＝「生ポインタ無し」は**表層**の約束で床には在ってよい。`&opts` 渡しは `inout` 再利用で表に出さない。
- **NULL は境界で `Optional` に写す（決定）**。署名に `Optional[T]` 明示時のみ NULL→None・非 NULL→Some（黙って None 化しない・null を言語内へ入れない＝Zig の `?*T` と同思想）。**却下＝`isNull()`**（null ハンドルを内部に持ち込む向き）。
- **理想＝`.h` から 1:1 bindgen（auto-gen）**。ただし「自動生成」と「型語彙」は別レイヤ＝**bindgen は誰が `extern` を書くか（人 vs ツール）を変えるだけで、必要な型語彙は同じ**。型語彙（不透明 `type`・`CPtr`/`CMutPtr`/`COpaque`・`repr(c)`）を先に確定し、bindgen（Clang AST を食う別ツール＝Zig `@cImport` 相当）は後続。**段取り（手書き先行 vs bindgen 先行・C/LLVM 並行 vs 置換）は spec 確定後に決める**。
- **残る未決**：使わせる側（export＝Plew→C 公開・既存 `export` と要整合）・ハンドルの `Eq`（ポインタ同一性・当面非提供）・spawn/local（生ハンドルを `local` で spawn 不可にするか正直に危険で許すか）・`repr(packed)`/`callconv` 軸・型エイリアス・点2 数値対応/点3 文字列境界/点4 所有権規約。

### テスト（`test` ブロック・→ [spec/15](../spec/04-execution/15-modules.md)）
- **宣言形＝`test` ブロック（関数でない・決定）**。テストはプログラムとしての意味（戻り値・レシーバ）を持たず「走らせて検査する」だけなので `fn` でなく専用ブロック（Zig/D 流）。`test` は実行時意味ゼロの宣言修飾的な語＝`export`/`pub` と同類。**経緯**：`@[Test]` ディレクティブ案を一度推したが撤回 ── ディレクティブは「TokenStream→TokenStream の純粋関数（ユーザー定義 derive）」に限る方針なのに、テスト標示は**横断的収集＋production リンク除外**で局所トークン書き換えに表せず、`@[...]` に混ぜると「`@[...]`＝純粋マクロ」の心象を裏切る。命名規約（Go/Python）/ライブラリ DSL（JS/RSpec）は Plew の「忖度しない・ambient 可変レジストリ無し」と衝突し却下。残る言語ネイティブ構文（Zig `test "…" {}`・D `unittest {}`）を採用＝modern 言語の実証あり・「意味論を変えるビルドモード無し」と整合。
- **配置＝モジュール直下／無名 impl 内（決定）**。テストに特権可視性を与えず、通常コードと同じ規則で「見たいものが見える位置」に置く。非 `export` は同一モジュール直下で、**型の非 `pub` は無名 impl 内**で試験（`part` で別ファイル化も同一モジュールゆえ可）。Zig の配置（ファイル直下／型の中）と同型。`fn` 本体内不可。**「公開 API 以外のテストは設計ミス」説は否定**（複雑ロジックの内部切り出しを直接突くのは正当）。
- **発見＝無条件全収集（決定）**。コンパイル対象に含まれる `test` を全部走らせる。**Zig の参照ベース（`refAllDecls`）trap を回避**＝`refAllDecls` が `pub` のみ辿り private struct 内テストが静かにスキップされる footgun（issue #12838/#18032）を踏まない＝「書いたテストは必ず走る」。
- **production リンク除外（決定）**。`test` ブロックごと本番ビルドから外すだけで通常コードは不変。Rust の `cfg(test)`（通常コードを test 時に差し替え可）は「意味論を変えるビルドモード無し」に反するので不採用＝変えるのはエントリ/リンク対象だけ。テスト失敗は panic（プロセス停止）でなく**ランナー続行の別チャネル**（正確な機構はランナー設計＝未決）。
- **アサーション＝`@Std/Testing` の小族 `expect`/`expectEq`/`expectNe`/`expectApprox`（決定）**。実行時 `assert`（本番不変条件・panic・常時 ON）とは別物（`expect*`＝テスト検査・ランナー続行）＝Zig も `std.debug.assert` と `std.testing.expect*` を分ける。**`expected:`/`actual:` ラベル必須**で `assertEquals` の引数逆転 footgun を防ぐ（ラベル必須＋宣言順固定だから取り違えが目に見える）。**power-assert は却下**（pytest/Spock/Swift Testing の式内省＝診断無料だが「どの式まで分解されるか」が暗黙＝対応範囲が不明瞭）。Plew はコンパイラが AST を持つので power-assert を hack 無く実装できる利点はあるが、**明示性（関数リスト＝対応範囲）を優先**。族が Zig より小さいのは `String`/`Array` に `==`/`Ord` があり `expectEqualStrings` 等が畳まれるから。**`expectError` 不要**（特定エラー値は `expectEq(expected: <Result.Error…/>, …)`・「エラーか」は `expect(r.isError)`・中身は `match`）＝Plew の値型エラーが Zig の `expectError` を畳む。**バリアントの「ケースのみ判定」は関数化不能**（第一級バリアントタグ無し＝`match` の領域）・`is*` で bool 化／`expectMatches`（パターン引数）は additive 保留。
- **依存（core-lib 未決）**：Result/Optional の `isOk`/`isError`/`isSome`/`isNone`、診断表示の `Debug` 相当トレイト、`assert`（実行時）の置き場モジュール名（`@Std/Diagnostics` 等・Testing でない＝本番でも使う）、ランナー詳細（失敗チャネル・async テスト・doc テスト）。

### メンバの可視性（型スコープ・2 段・→ [spec/05](../spec/02-type-system/05-structs-enums.md)）
- `pub` は**型のカプセル化のみ**を制御し、モジュール/パッケージ境界（`export`）とは直交する別軸。非公開（修飾なし）＝**その型の無名 impl からのみ**可視。
- **段階は 2 つだけ**（`pub(crate)` / `pub(super)` は「正しく使えた試しがない」として不採用）。兄弟モジュールが触りたいメンバは `pub` にする（＝外部にも見える）か、密結合コードを型のモジュールに `part` で同居させ無名 impl から触る。
- **非公開を見られるのは無名 impl だけ**。理由：拡張から非公開が見えると誰でも extension 経由で内部に到達でき `pub` が無力化する。外部に隠す必要は普遍的（不変条件の保証・リファクタ自由度）。Python の慣習 private 等「内部露出」は理想でなく弱点。

### 列挙型バリアントのフィールドは修飾子なし `name: Type`（決定・→ [spec/05](../spec/02-type-system/05-structs-enums.md)）
- 当初は「フィールドの統一原則」で struct とバリアントの宣言を同一構文（`{ val f: T }`）にしていたが、**バリアントのフィールドでは `val`/`mut val`/`pub` がどれも意味を持たない**ので落とし、`{ f: T }` だけにする。**根拠**：(1) 可変性 — バリアントのフィールドは `match` で取り出すしかなく `e.V.f = …` のような場所がない（変更はバリアント再構築）ので `mut val` を行使できず、`val`/`mut val` の区別が存在しない。(2) 可視性 — 可視性は列挙型単位（バリアントが見えれば `match` で全フィールド可視）でフィールド個別には効かない。意味を持たない修飾子を文法に残すのは冗長（「明示は good だが意味のない冗長は嫌う」）。**生成・分解は struct と同形のまま**（差は宣言だけ）。分解時の束縛 `{ val binding }` の `val` は新変数束縛で別物＝不変。ラベル付きレコード `(f: T)` と同形になり一貫。**経緯**：パーサ素描（`selfhost/calc.pw`）で `Num { value: I64 }` と書いて「`val` が要る」とエラーになり、`mut val value` が成立する/意味を持つかを検証した結果「成立はするが意味ゼロ」と判明して撤廃。
- **バリアントペイロードを record 形式 `V(x: I32, y: I32)` に移行（採用・決定 2026-06-04・→ spec/05）**：↑で `val`/`mut val`/`pub` を落とした結果バリアントフィールドは**ラベル付きレコード `(field: Type)` と同形**になったので、宣言・分解も `{ }` でなく `( )` で書く（生成は JSX のまま）。**根拠**：(1) レコードは `(x: I32, y: I32)` ＝括弧なので `( )` が一貫（`{ }` は記憶域＋可変性を持つ struct 本体＝宣言ブロック用）。(2) struct/variant の `{ }` 混同（上の「val 意味なし」注を要した混乱）を構文で解消＝「これはレコード」が見える。(3) **Swift と一致**（stored property は改行 `{ }`・enum は `case v(x:y:)` 括弧）＝Plew は Swift 寄り。**当初 `val` 必須だった頃はレコード形式が不自然だった**（`(val x: T)` は変）が、`val` 撤廃で `(x: T)` が自然になり移行可能に。**分解もドットで判別**＝`Enum.Variant(…)`（括弧）vs `Struct { … }`（ブレース）。**移行＝ADD（両構文受理）→USE（全ソース機械置換・両形は同一 AST ゆえ生成 C 不変＝fixpoint 無変化で挙動不変を実証）→REMOVE（`{ }` を loud-reject）**。struct は `{ }`・`val`/`mut val` のまま不変（記憶域ブロック）。

### `impl Type as Trait`（→ [spec/07](../spec/02-type-system/07-methods-impl.md)）
- `impl Trait for Struct`（Rust）は直後が trait か struct か文脈依存で気持ち悪い → **型主語**に統一。`as` は一度キャスト用途と衝突を懸念して `with` を検討したが、最終的に `impl Type as Trait` に回帰。
- ジェネリック実装は **`impl[...]` で型パラメータを前置宣言**。`impl[T]`（束縛）と `Struct[T]`（使用）を分けるので `impl Struct[I32]`（具体型への実装）と曖昧にならず、トレイト引数だけに現れる型変数（`impl[T] Vector as Mul[T]`）の置き場にもなる。当初案「型側ブラケットで暗黙束縛」は、トレイト引数限定の変数を書けず・具体型と曖昧で却下。

### ジェネリクスの記法（型パラメータ・制約・impl・→ [spec/06](../spec/02-type-system/06-generics.md)）
- **型パラメータの `[...]` は名前のみ**。**インライン制約 `[T: Trait]` は廃止**し、制約はすべて `where` に集約。理由：`[...]` が全宣言箇所で「名前だけ」に揃い `impl[T]` バインダと一貫、制約の置き場が一意（単純・明示）。代償＝単一制約が冗長（明示税）。supertrait `trait Sub: Super` と関連型宣言 `type Item: Format` の `:` は別構文なので残す。
- **`where` の述語は `型: 制約` のみ。型等価述語 `where T = I32` は持たない**。特定具体型への実装は型の位置に直接書く（`impl MyStruct[I32] as Trait`）。
- **「トレイト境界」→「トレイト制約」と呼ぶ**（`境界` は boundary の語に温存：モジュール／パッケージ境界・区間の境界条件 `i<b`・FFI 境界変換/境界コピー）。
- **デフォルト型引数（`[T = …]` / `Add[Rhs = Self]`）は持たない**（後付け additive）。Rust の実需は①演算子 `Rhs = Self`②末尾 policy 引数に集約されるが、Plew は①を明示 `Add[Self]` で書き、②は ARC でアロケータ引数が surface せずハッシャ型も出ないため不要。Rust の既定型引数は推論に参加しない狭い糖衣でもある。
- **型変数が返り値だけに出る generic は「返り値文脈推論」で型を決める（決定・Swift/Rust/Haskell 流・実装は段階的）**: `makeZero[T]() -> T` や `Array.new[T]()`・`Set[T]()`・空コレクション・各種 factory のように **T が引数に現れず返り値型にだけ出る**呼び出しは、**期待型（束縛の型注釈・引数位置の期待型・戻り値型）から T を推論**する＝`val b: RawBuffer[I64] = rawAlloc(cap: 4)` で T=I64。**根拠**：`new()`/空コレクションで普遍的に再発する必要・標準的で驚きが少ない・**「型注釈に書いた意味がそのまま発現する」**＝拠り所（意味は唱えた通り）と整合。**却下：明示型引数 `rawAlloc[I64](...)`**（新呼び出し構文・`new[I64]()` が随所に出て実用上うるさい・(A) があれば不要／将来 additive で足すのは可）。**現況**：引数からの推論は実装済（`wrap(x: 42I64)`・配列 intrinsic）だが**返り値文脈推論は未実装**（`val b: I64 = makeZero()` は素の `makeZero()` を出し monomorphize されない）。コレクション一般化の段で実装。それまで生メモリ床の `rawAlloc` は intrinsic 専用に束縛型から要素型を読む narrow 対応で通す。→ [worklog](worklog.md)。

### `assoc`（static 相当・→ [spec/07](../spec/02-type-system/07-methods-impl.md)）
- Plew の static メソッド/変数は **`assoc fn` / `assoc val`**（名前が違うだけで static と同等機能）。命名は `static`（不変と誤読）/ `class` / `ass` を却下し `assoc`（associated）に。
- **経緯（翻意）**：当初は「static は概念ごと不要（インスタンス非依存ならグローバル関数で足りる）」としたが、`Struct.new()` 等のニーズから `assoc` を採用＝**実質 static を持つ**方向に翻意。型に属さないトップレベル関数も別途存在するが、それは static の代替ではない（両方ある）。なお「グローバル**名前空間**」は無い（全定義はモジュールスコープ）。

### `@[...]` ディレクティブとメタプログラミング（方針転換・→ [spec/16](../spec/04-execution/16-metaprogramming.md)）
- **当初は閉じたメタプログラミング**: Rust の `derive` 相当の組み込みディレクティブのみで、ユーザーマクロは非公開（安全性・予測可能性・実装コストが理由だった）。
- **転換後**: ユーザー定義のメタプログラミングを可能にする。ビルドと独立した別コマンド（`plew gen`）で別ファイル `<Foo>.gen.pw` へコード生成（go generate 型・原本不変・add-only）＋ マクロは `Derive` トレイト実装構造体（要求 `derive(input: AST) -> String`）。
- **入力は `TokenStream` から `AST` へ確定（却下＝TokenStream）**: 当初 TokenStream 入力を選んだ動機は (a) 安定境界 と (b) 汎用性。だが**最終形＝lexer+parser+AST の外部共有パッケージ**（コンパイラもマクロも同一版に依存・AST 版違い問題を回避）を据えると **(a) は消える**（AST も真実の源 1 つで安定・derive は結局 AST へ parse するのでトークン段の安定性も享受しない）。残る (b) は **Plew が宣言への derive 専用**（関数形 `macro!()`/DSL マクロを持たない）ゆえ稀＝Rust でも生 TokenStream 必須は `json!`/`html!`/`quote!` 等の関数形/DSL だけで derive は常に AST へ parse する。よって入力＝AST、生トークンは将来 escape hatch。**String→AST 変換は `Derive` の提供メソッド `deriveFromSource` が担い**（中間 dispatcher 層不要）、**ランナーは String↔String の版非依存な機械**（ハーネス合成→compile→run→`.gen.pw`・AST 型に触れない・版固定はハーネスの固定 `@Std/Syntax` で成立）。構文ライブラリ＝当面 `@Std/Syntax`（in-tree）・最終形は外部共有パッケージ。実行系の段取り＝[metaprogramming-architecture.md](metaprogramming-architecture.md)。
- 組み込みディレクティブは引き続き言語提供。命名は型由来で **PascalCase**（`Eq`/`Hash`/`Encode`/`Decode`/`All`。`Clone` は値意味論ゆえ無し）。理想は組み込みも derive 実装として同じ仕組みで提供すること。enum の `All`（生成メソッドは `Enum.all()`）は `@enumerable`/`@allCases`/`@variants` を比較し `Enum.all` 直結案を採用。**ディレクティブは「コードを合成する derive 専用」**＝旧 `DefaultFactory(pub)` は derive ではなく可視性制御なので**ディレクティブから外し素の構文 `pub factory` に移した**（祝福ディレクティブを `@[...]` 名前空間に置かない＝ユーザー定義可能な derive だけが残る）。
- **trait と derive の同名（決定・方向確定／綴りは dogfood 時）**: `@[Hash]` の derive と `trait Hash` が同名になる問題。Plew は **型とトレイトが同一名前空間**なので、Rust 流の「`trait Hash` ＋ derive 用 `struct Hash` を別名前空間で共存」が**できない**（`struct Hash {} ; trait Hash {}` は衝突）。**解＝derive を必ず構造体にする前提を外す**：derive 可能性を「**derive インターフェースの実装**」と定義し、その実装主体は**トレイトでも struct でもよい**とする。derive の本質的な軸は**設定（引数）の有無**だけで、それを 2 インターフェースに対応させる——**設定なし＝`Derive`（要求 `assoc fn derive(input: TopItemAst) -> String`・`Self` 非依存ゆえトレイトも no-field struct も実装可・bare `@[X]`）／設定あり＝`ParameterizedDerive`（要求 `fn derive`・`self`=設定 struct・`@[X(args)]`）**。`()` 規約で構文が機構を示す（bare=assoc・括弧=インスタンス構築＝`@[A()]` も括弧必須）。これで `Hash` はトレイト 1 エンティティのまま（`impl Hash as Derive` で deriver を後付け・`struct Hash` 不要）＝**衝突が原理的に消える**。`All`/`Builder` 等トレイトを持たない derive だけが struct（対応トレイトが無く衝突もしない）。**却下案**：(A) Rust 流の別名前空間＝Plew に無く、Core 内でモジュールを割って名前空間で逃がすのは不自然。(C) trait/derive を別名（`@[DeriveEq]` 等）＝同名前空間なら筋は通るが、共通ケース（設定なし derive が大半＝Eq/Ord/Hash/All）に恒久的な命名負担が乗り「`Eq` の derive は何という名か」が毎回問われ混乱。**採用の決め手**＝設定なしを**無印 `Derive`** に置けば共通ケースに修飾子が要らず、命名問題そのものが消える（`@[Hash]`⟺`impl Hash as Derive` が 1 本道）。**実装前提**＝`Self` を含まないトレイト提供 `assoc fn` を trait 名で実体なしに一意呼び出しする機構（`Hash.derive(input)`・唯一の提供 deriver ゆえディスパッチ不要・当面メタ機構限定で可）。**現状は組み込みが特権合成（`trait Hash` のみ・`struct Hash` 無し）なので未着手で無害＝効くのは dogfood 段**。→ [spec/16](../spec/04-execution/16-metaprogramming.md)。

### その他
- **キャスト `as`** は `From[Source]` の無名 factory の糖衣（`x as T`⟺`<T from=x />`）で **infallible 固定**（全域変換のみ）。暗黙変換は持たず、幅変更も明示 `as`（例外は `try` の `From` と数値リテラル多相）。**可謬変換は `TryFrom`／`<T.convert from=… />`**（上記「`as` は infallible 固定…」の決定参照）。唯一 newtype と元型間の `as` は From でなくゼロコスト再タグ（→ [spec/10](../spec/02-type-system/10-newtype.md)）。
- **ローカル変数の再宣言（shadowing）は Rust 流に無制限（決定）**: **却下案**：(B) 再利用はパターン束縛のみ・プレーン val はフレッシュ必須＝「パターンだけ同名可」という線引き自体が分かりにくい、(C) 全面禁止＝guard が窮屈。Rust 流は規則が単一（`name` は直近の宣言を指す）で、guard/match の絞り込みも特別扱いなしに導ける。「同名で別物を指す」恐怖は未使用束縛の lint で緩和。
- **コレクション名 `Array`**: `Vec` は日本語話者に数学のベクトル連想で直感的でないとして却下。
- **辞書 `Dictionary[K, V]`／集合 `Set[E]`（決定）**: 名前は Swift 系の**実装隠蔽名**（`HashMap`/`HashSet` でなく `Dictionary`/`Set`）。**リテラル**は Swift 風 `[k: v]`、空辞書は型推論不能を避けるため明示トークン `[:]`（可変アリティゆえ配列と並ぶ「構築は JSX」の**本物の例外**）。**`Dictionary` はリテラルが参照する型なので lang item**（`Array` と同じく import 不要）、**`Set` はリテラル無し＝通常ライブラリ型で import 必須**（→ [spec/15](../spec/04-execution/15-modules.md)）。**キー境界は `K: Hash`・`Hash: Eq`**（衝突解決に等価が要る・`Ord: Eq` と同じ形・Rust の `Eq + Hash` 2 本を 1 本に）。**`dict[key] -> V`（欠落 panic）＝Rust 流**で `Array` 範囲外と同挙動。**却下**＝Swift の `Optional[V]`：理由は「添字アクセスの挙動を型で変えたくない」（`Array` は `T`、辞書だけ `Optional` は非一貫）。安全引きは `get(key:) -> Optional[V]`、代入 `dict[k]=v` は挿入/更新（`IndexSet`・`V`）、削除 `remove(key:)`、反復順は未規定（ハッシュ表）。**`Hash` の算法は Rust 流 `Hasher` ストリーミングに倒す（方向は確定）**。**トレイト形＝(B) generic Hasher**（`fn hash[H](hasher: inout H) where H: Hasher`・マップが算法を選べる Rust 厳密形・generics 前提工事は実装済）。**算法＝SipHash-1-3（Rust と同じ・rotl＋wrappingAdd＋xor の U64 のみ）**。**シードは当面固定（決定的）**＝Plew にまだ RNG が無いため。**🔴 RNG（`Random`）着手後にマップごとのランダムシード（Rust の RandomState 相当・DoS 耐性）へ差し替える＝必須 additive**（アルゴリズム/トレイト形は不変・シード源のみ差す・忘れない／→ [worklog.md](worklog.md) の 🔴 TODO）。`F64` をキーにできるか（NaN）も `Hash` 準拠判断として core-lib。
- **添字・`count`・レンジ要素は固定 `U64`（決定）**: `arr[i]` は `Index[U64] -> T`、`count: U64`、`0..<arr.count` のレンジ要素も `U64` ── **添字・長さ・反復を同一型に揃える**（暗黙変換が無いので揃えないと `for val i in 0..<arr.count { arr[i] }` ですら `as` が要る）。`String.bytes`（`Array[U8]`）も同じ。`Dictionary` の `Index[K]` はキー型なので無関係（`dict.count` は `U64`）。**却下案**と理由：(A) **`I32`（現行）**＝64bit で 2³¹ 要素超を指せず・`count` も表せず・符号付きで負添字が実行時 panic 送り（コンパイル時に弾けない）。(B) **ポインタ幅 `USize`/`ISize`（Rust `usize`・C `size_t` 流）**＝「サイズは addressable memory で頭打ち＝最もタイトで正直な型」という核は本物だが、**幅がターゲット依存→オーバーフロー panic 点がターゲットで変わり、Plew の「意味論を変えるビルドは作らない／オーバーフローは常に決定的に panic」と衝突**。可変幅が systems 言語で普遍なのは添字が GEP/ポインタ算術そのものになるからで、ARC＋境界チェック＋codegen 仲介の Plew ではその動機が消える（実際 GC の Java/C# は固定 32bit 添字を採用）。(C) **符号付きワード `ISize`／Swift `Int` 流**＝単一整数の楽さはあるが Plew は幅明示の `I8…U64` で単一整数を持たず一貫性に欠け、負添字の嘘も残る。**採用＝固定 `U64`**：Java/C# の決定性（固定幅・全ターゲット同一意味論）から 2³¹ 上限だけ外した形＝両者の良いとこ取り。WASM32 でのコスト（メモリ境界での `i32.wrap_i64` 1 命令／count が 8byte）は GC 言語では実害ほぼ無し（i64 算術は 64bit ホストで実質無料・in-bounds なら wrap は lossless）。**`USize`/`ISize` は生ポインタ FFI が要るとき additive に足す**（今 `U64` にしても閉ざさない）。**経緯**：当初の私の推奨は「正しさ＋正直さ＋codegen」で `USize` 寄りだったが、ユーザの指摘で再評価 ── 正しさの論点は対 `I32` であって `USize` を `U64` と分けず、`USize` 固有の利点は定数倍/見た目に留まり、ターゲット非依存意味論という Plew の価値が決め手で `U64` に倒した。
- **デフォルト引数の意味論（決定）**: 構文 `arg: T = 式` は既存（→ [spec/04](../spec/01-basics/04-functions.md)）だが評価意味論が未定義だったので確定。**(1) 評価タイミング＝呼び出しごと**：引数省略のたびにデフォルト式を再評価。**却下＝Python の定義時 1 回共有**（`def f(x=[])` で `[]` が全呼び出し共有される悪名高い罠）。値意味論の Plew でも定義時 1 回共有は危険（`= []` の破壊的変更が次の呼び出しに漏れる＝「静かな嘘」）。毎回評価なら `[]`/`now()` が毎回フレッシュで直感どおり＝Swift/Kotlin/JS/C# と同じ。**(2) 評価スコープ＝定義側モジュール**（呼び出し側ではない）：デフォルトはシグネチャの一部なので、呼び出し側から見えない private も参照可。「省略＝呼び出し側へテキスト挿入」ではない（全言語一致＝事実上一択）。**(3) 任意の実行時式を許す**（const 限定にしない）：C# は定数限定だが、それだと `= []`/`= now()` が書けず `Optional`+`??` に追いやられる。毎回評価なら任意式でも安全＝Swift 流のほうが開発しやすい。**(4) 他引数・`self` は参照不可**（**唯一の本物のトレードオフ**）：`fn f(a, b = a+1)` や method の `= self.count` を禁止。利点＝デフォルトがシグネチャ単体で評価できる自己完結な値になり引数の評価順問題が消える（単純＞強力／Swift も同じ制約）。代償＝`substring(end = self.count)` 的なものはオーバーロードに回す（Slice/substring 自体まだ無く、**許可方向は後から additive で非破壊**なので初手は禁止が安全）。**(5) 末尾限定なし**（Swift と同じく任意位置に既定可）：**却下＝末尾のみ**。ラベル必須の Plew では位置がラベルで一意に指せるので `f(name:, loud:)` のように途中だけ省く呼び出しも曖昧にならず、末尾限定は不要な制約。**(6) オーバーロード干渉**：デフォルトは「省略の組み合わせごとに呼び出しセレクタ（名前＋ラベル列）を増やす」（`fn f(a=0, b)` は `f(a:b:)`＋`f(b:)`）。派生セレクタは通常のオーバーロード集合に合流し、既存の解決規則（同一セレクタは具体位置の型で区別）に従う＝別宣言と型で区別できなければコンパイルエラー（「一意に定まらなければエラー」と整合）。**(7) `inout` 引数は不可**（書き戻し先の場所が要る＝値であるデフォルトと相容れない）。
- **レンジ構文 `a..<b`／`a..=b`（決定）**: 半開／閉を**両端とも記号で明示**し素の `..` を持たない（機構→ [spec/02](../spec/01-basics/02-basic-types.md)）。**却下**：Rust の bare `..`=半開（どちらが開かを覚える要）／Swift の `...`=閉（一目で分からない）／Kotlin の `..`=閉デフォルト（後から `..<` を足す羽目）。採用根拠＝`<`/`=` が境界条件 `i<b`/`i<=b` に対応する mnemonic で「開区間の記憶」footgun が消える（代償：`..`=半開の世界標準から外れる＝黙って半開より良い、半開ループが 1 文字長い＝明示税）。
- **JSX 属性に `{}` 不要**: 属性値は常に式として扱うため（JSX の `{}` は HTML 曖昧性回避という歴史的都合）。
- **leading-dot 構築 `<.…/>`（採用・決定・→ [spec/05](../spec/02-type-system/05-structs-enums.md#型を文脈から省くleading-dot-構築)）**: 構築型が文脈から一意に定まるとき `<Type.Member …/>` の **`.` の前の型だけを落として** `<.Member …/>`/`<.member …/>`（バリアント・名前付き factory）と書ける。**leading-dot は「既存の `.` の前の型を省く」操作で `.` を発明しない**＝memberwise `<Type field=…/>` には元々 `.` が無いので `<. field=…/>` は省略でなく `.` の捏造ゆえ不可（読みづらさは結果・根拠は「省略ではない」＝ユーザー判断）。Swift `let e: Enum = .foo`／Zig の enum literal `.foo` と同系だが、**Plew は JSX 構築という単一の場所に閉じ込め `<.` 一記号に統一**（Zig は enum literal `.foo` と匿名構造体 `.{}` が別記号）。**「他言語で稀」な理由＝裸 `.foo` の名前解決が期待型に依存→名前解決を型推論へ畳み込む双方向化が要る**（Rust はパス解決を独立パスで早期確定する主義ゆえ持たない）。**Plew が容易な核心＝`.` が常に `<.` の形でしか現れない不変条件**で、浮いた `.foo` が無く構文的に「型省略構築」と一意確定（パース層の曖昧さが消える）。**ambient ではない**：型名は左辺注釈・受けシグネチャにローカル明記＝provenance 回収可能（Swift 嫌いの「どこからでも見える」とは別物）＝忖度でなく補完。**使えるのは期待型が一意に定まる位置のみ**（明示注釈・宣言済み戻り型・型が単一に決まる引数）で **leading-dot 式自身では期待型を決めない**（鶏卵回避）。**型オーバーロードでは不可**（期待型が割れる→`<A.foo/>` 明示）・**ラベルオーバーロードは可**（型は一意・ラベルが候補を絞る）。**パターンには波及させない**：`Enum.Variant(…)` は JSX でないので型名を省かず、`.` が `<.` 以外で始まらない不変条件を保つ。
- **`extern`**: 設計会話では `declare fn … from "libc"` 案を検討したが、最終文法は Rust 式の `extern "C" { … }` ブロックを採用。
- **`lazy`（遅延初期化）**: 専用構文は設けない。`<Lazy />` 構造体で表現する（言語仕様に載せなくても自然に実装できる単なる構造体）。
- **識別子は camelCase（型は PascalCase・決定）**: 変数・関数・メソッド・フィールド・**引数ラベル・stdlib メソッド名・定数**（`val`/`export val`/`assoc val`）は **camelCase**（`isNan`/`wrappingAdd`/`stepForward`/`expectEq`/`firstName`/`maxRetry`）。型名・enum バリアントは **PascalCase** 据え置き。**定数も camelCase**＝SCREAMING_SNAKE_CASE は使わない（Swift 流・`let maxRetry`／束縛は一律 camelCase で casing 軸を 1 本に保ち、不変 `val` と可変 `mut val` で見た目を割らない）。**動機**：JSX 生成 `<User firstName=… />` の prop が snake_case だと React/TSX 直感とズレて書き味が悪い。**根拠**：識別子に触れる表面機能 ── 必須引数ラベル・メソッド・値意味論/CoW/ARC・JSX・クライアント/フルスタック志向 ── はすべて **Swift 族**で、Swift は camelCase（型システムの中身は trait/generics で Rust 流だが、casing を決めるのは「ラベル・呼び出し・フィールド」側＝Swift が最も近い親戚）。加えて Plew は既に**先頭の大小を load-bearing** にしている（関数型の裸位置で「ラベル＝先頭小／型＝先頭大」で曖昧性回避）ので、camelCase なら値 vs 型を**先頭ケース一本**で分けられ、snake_case は冗長なアンダースコア信号を重ねる形になる（単純 > 強力）。**スコープ**：stdlib API 名も規約に従い camelCase（`isNan`/`countOnes`/`fromBytes`…）。能力マーカー/文脈キーワード（`defaultExtension`/`allowUnique`/`noLocal`）も camelCase ── snake キーワードが camel 言語で浮くため。**据え置き**：(1) import/part のパスコンポーネント（ファイル/ディレクトリ名）は **PascalCase**（命名の別軸・`_.pw` のみ例外）。(2) ANTLR 文法ルール名（`type_use`/`match_case` 等）は `.g4` の別名前空間ゆえ不変（Plew.g4 不可侵とも整合）。(3) 外部名はそのまま（C `size_t`・WASM `i32.wrap_i64`・Swift `swift_beginAccess`・Rust `#[non_exhaustive]`）。**却下＝snake_case 継続**：Rust 整合・語境界の明示は本物の利点だが、casing が効くのは表面であり、そこは Swift 族が勝つ。**非干渉**：camelCase＝先頭小・PascalCase＝先頭大なので、関数型裸位置や `f[I32]` vs `arr[i]` の曖昧性回避（先頭ケース判定）は無傷。**経緯**：当初の既定 snake_case（Rust メンタルモデル由来）を、JSX prop の違和感を引き金に表面親戚（Swift）優先へ巻き戻した。
- **数値リテラルの基数・サフィックス**: 16/8/2 進（`0x`/`0o`/`0b`）・`_` 桁区切り・e 表記・型サフィックスを採用。Rust とほぼ同様だが型サフィックスは型名（PascalCase）なので `10U32` / `3.14F64`。
- **force-unwrap 演算子は無し**: 後置 `!` のような強制取り出しは持たない（文法に残る `UNARY_POSTFIX_OP` は遺物で再構築時に削除）。取り出しは `Optional`/`Result` の `unwrap` メソッドに留め、基本は非推奨。
- **冪乗演算子 `**` は導入しない**: `pow` で代替。Rust/Go/Swift と同様、右結合・優先順位の事故（`-2**2`）、戻り型/コストの不透明さ、演算子経済の観点から。冪乗は単一 CPU 命令でなく実体は関数呼び出しのため、安価な演算子の見た目を与えない。
- **演算子の優先順位・結合性（決定）**: 14 段ラダーを規定（機構→ [spec/12](../spec/03-expressions/12-operators.md)）。**`as`・算術・ビット・比較・`&&`/`||` の相対順は Rust と一致**（一次資料 The Rust Reference で照合）。Plew 固有の判断：
  - **`??` 演算子は廃止（決定・当初案を撤回）**：当初は Swift 位置（算術・ビット・`as` より弱く比較・`&&`・`||` より強い・右結合）で入れる予定だったが、**演算子としては持たないことに最終決定**（Rust と同じくあえて入れない）。**理由**＝`??` の短絡（左辺が `Some` なら右辺を評価しない）は**右辺というユーザー提供の値の暗黙遅延評価**で、Plew が却下した `@autoclosure`（暗黙遅延）と本質的に同じ隠れた挙動。「明示 > 暗黙」「autoclosure 不採用」と座りが悪い。**代替**＝`Optional.unwrapOr(fallback:)` を**引数型でオーバーロード**：`unwrapOr(fallback: T)`（eager）と `unwrapOr(fallback: fn() -> T)`（lazy・クロージャが目に見える）。eager/lazy の選択がコードに現れる。**`&&`/`||` は残す**（遅延されるのが安価な Bool 節＝普遍イディオムで、任意値を遅延する `??` とは別格）／`?.`（Chain トレイト）も残す（短絡は受け手側でコンパイラ match 脱糖が制御・トレイトメソッド自体は eager）。**廃案の precedence 議論（経緯）**：「算術より上 vs 下」「比較との上下」を検討したが演算子自体を持たないので moot。実装も lexer/parser/AST/codegen から `??` 機構を削除済（reject `coalesce_removed`）。→ spec/12「Nil 合体演算子は持たない」。
  - **レンジは Rust 位置（最下位・非結合）**。Swift はレンジを `??` より強く置くが、Plew は最下位にした（`a ?? b ..< c`＝`(a??b)..<c`）。実用上レンジは限定文脈（`for … in`・`[]`・括弧内）にしか現れず端点に算術が先に結合するので害なし。
  - **ビット演算子を採用（spec は確定・実装順は実装時に判断）**。「能力は不要では？」を再検討した結論：Lua(5.3 前)・OCaml・Scheme 等シンボル無しの前例はあるが、Plew は systems 言語かつ**自前 stdlib（UTF-8 の `scalars`/`graphemes`・ハッシュ・FFI）がビット演算を要求**するので能力は必須、論点は演算子 vs メソッドで演算子採用。C の罠（`x & 1 == 0`）回避のため Rust 同様「シフト>&>^>|・全部比較より上」。**`!`（論理 Not・`Bool` 専用）と `~`（`BitNot`・整数）を分離**（Rust の `!` は両用で紛らわしい）。**残る意味論の小決定**（右シフトの符号拡張＝符号付き算術/符号なし論理か、オーバーシフトを overflow-panic に乗せるか、`Shl`/`Shr` の RHS 型・`Output`）は additive で後決め。
  - **`as` は算術より強い**＝暗黙数値変換が無く `a as I64 + b as I64` を多用するため。当初「Rust と違い Plew は `as` を書く頻度が高い」と差別化したが、**Rust も暗黙拡幅が無い点で同じ**と判明し差別化は撤回（位置の結論は Rust と同一）。
  - **前置 `try`/`await` の帰結**：後置チェーン全体に掛かる（`try a.b()`＝`try (a.b())`）。Rust の後置 `?` と逆で途中取り出しは `(try a).b()`。前置 `try` 採用（既決）の必然。
  - **比較・等価は非結合**（`a==b==c` が `Bool` の `Eq` で静かに通る誤読を防ぐ・Rust の "Require parentheses" と同じ）。
- **`Display` 廃止・`Format` 一本化（決定）**: 表示も文字列補間も `Format`（`fn format(format: String) -> String`）に統一。`{x}`⟺`x.format(format: "")`、`{x:.2}`⟺`x.format(format: ".2")`。役割重複を解消。
- **文字列補間は任意の値式・`:` 境界は括弧深さ 0（決定）**: `{ 式 }` の中身は**任意の値式**（Rust のインライン捕捉が識別子限定なのと異なる）。**フォーマット境界の `:` 規則**＝補間内で**括弧入れ子深さ 0 のコロンだけ**が spec 開始（ラベル引数・レコードの `:` は必ず `()`/`[]` 内なので衝突せず、Plew は型注釈を式位置に持たない）。**却下した区切り**：`;`/`@`（規約性・可読性で劣る）・`|`（将来 `BitOr` と深さ 0 で衝突）。**補間内はブロック式・`match` 式を禁止**（閉じ `}` 対応を単純に保つ）。**波括弧リテラルは `{{`/`}}` 二重化**（Rust 同）。**複数行**：生改行はそのまま含み、**行末 `\` は改行＋次行先頭空白を除去**して折り返し（Rust 同）。
- **添字代入トレイト `IndexSet`（決定）**: `a[i] = x` ⟺ `inout fn indexSet(key:, value:)`。Rust の `IndexMut` 相当だが、参照/借用が無く可変な場所を返せないので**可変参照ではなくセッター**。複合代入 `a[i] += x` は `Index`＋演算＋`IndexSet`。
- **複合代入は純粋脱糖・専用トレイトなし・Rust の Assign 系統を全網羅（決定）**: `a OP= b` ⟺ `a = a OP b` の純粋糖衣で、Rust の `AddAssign` 等の専用トレイトは**持たない**（機構→ [spec/12](../spec/03-expressions/12-operators.md)）。**根拠＝Rust が `AddAssign` を分ける第一動機は所有権**：`Add::add(self,…)` が `self` を move 消費するため借用越しの `self.x += 1` を `a = a + b` 脱糖で書けない、という対処であり、Plew は（CoW で）借用越し move 消費の問題が無く、`mut val` 再代入もフィールド/添字 store も単なる書き込みなので当てはまらない。残る純粋な in-place 性能も Plew では弱い（String 不変・伸長は専用メソッド・ARC＋最適化器・性能より拠り所＝意味の透明性／掌握感を優先）。純粋脱糖の利得＝追加トレイトゼロ・`a += b` と `a = a + b` が原理的に食い違わない（静かな嘘なし）・`IndexSet`（可変参照でなくセッター）と同方針。**対象は Rust の 10 個を全網羅**＝算術 `+= -= *= /= %=`（現行・`%=` は `Rem` が整数のみ）＋ビット系 `&= ^= |= <<= >>=`（対応二項演算子の糖衣）。**`&&=`/`||=` は無し**（短絡する制御フローでトレイト非）。**`??=` は当面入れない**（Rust に複合 nil 合体が無い。Swift/JS/Kotlin にはある＝additive 候補として保留）。成立条件＝(1) 代入可能な場所、(2) `a OP b` が成立（演算子トレイト実装あり）、(3) `Output` が左辺型と一致（暗黙変換なしゆえ型不変）。**場所は 1 回評価**（`arr[f()] += x` の `f()` を二重評価しない＝レシーバ・添字を一時束縛してから `Index`→演算→`IndexSet`）。
- **`inout` の呼び出し側は `&`（決定）**: `f(param: &x)`。`mut` 束縛にのみ付けられ、「この呼び出しで変更され得る」ことを明示。
- **`async fn` は TypeScript 流（決定）**: 戻り型は `-> Promise[T]` と明示し、本体の `return e`（`e: T`）はコンパイラが `Promise[T]` に自動 wrap。`await` が開く。
- **async fn のローワリング＝B（stackless ステートマシン・決定・段階 1-3 実装済〔native-C・`Codegen/Async.pw`〕）**: `async fn` を**状態機械**にコンパイルする（`await` をまたぐ live local だけヒープのフレーム構造体へ昇格・`await` で `state=N`／退避／PENDING return・resume は `switch(state)`・`async fn` はフレーム確保して `Promise[T]` を返す）。**却下＝A（スタックフルコルーチン・ucontext/Asyncify）**＝タスクごとにスタックを確保し既存のスタック変数 codegen をほぼ無改修で使える。**なぜ B**：(1) **Plew の async は spec で colored（`await` は `async fn` 内のみ・JS と同じ）＝意味論レベルで既に stackless を選んでいる**ので、A/B は**ユーザーから見た観測挙動が同一**（hidden cost のみの差＝「発現は隠蔽してよい」に合致）。(2) **Node/V8 が B**＝async/await を generator ベースの stackless（中断時にフレームをヒープ退避・専用ネイティブスタックを持たない）で実装し、これが (a) colored=赤青関数問題の正体、(b) サーバが 1 万本のアイドル接続をタスクごとのスタック無しで抱える軽量大量並行、(c) エンジンにスタックスイッチ機構が不要、を生む。Node を範とするなら**終着点は B**。(3) **A は中継ぎにならない**＝A/B で再利用できるのはループ/Promise/timer ランタイムだけで、async fn ローワリング（この仕事の難所）は B 化で丸ごと作り直しになる。(4) **WASM 直行**＝B は素の WASM に落ち、A は Asyncify/JSPI が要る。**他言語**：Rust の `async fn`・C# async・Python async も B／Go goroutine・Java Loom・Lua coroutine は A で**色無し**（coloring の有無が stackful/stackless の見える署名）。**実装順＝native-C 先行**（suspend/resume・drain 順・ARC across await の意味論を固める）→ WASM。**最小サブセットから additive**（単一中断点→loop/branch/match 内 await→複数中断点）。→ architecture.md「async/await ローワリング」・spec/14。
- **Iterator / Iterable 分離（決定）**: `Iterator`＝`inout fn next() -> Optional[Item]` の消費カーソル、`Iterable`＝`iterator()` で毎回新カーソルを産む。`for` は Iterable を回し（`Array`/辞書/レンジが準拠）、`Iterator` 自身も Iterable。**却下**：単一 Iterator（コレクション自身が `next`）＝値意味論で「自分のカーソル」を持てず多重走査不可。正確なシグネチャは未決。
- **ユニット型＝`()`（決定）**: 名目 `Void` も `Void` エイリアスも作らず、ユニットは 0 要素ラベル付きタプル `()`。**根拠**：Java の「void は型でない」失敗（総称に乗らない）を避ける／0 フィールドなのでフィールドを畳むメタプログラミングで「0 個の基底ケース」として一様に扱え、別名・別型を設けない方が書き方が一通りで済む。

## 個別論点の決定と根拠

`SPEC.md` 全章を見直して洗い出し、決着させた設計判断。各根拠・却下案・経緯を保存する。

- **再帰的な値型の扱い** — 自己参照する `struct`/`enum`（`List`・木・AST 等）は素朴にはサイズ無限。**結論：コンパイラが再帰を検出し、必要なフィールドを CoW ヒープセルで自動箱化**してレイアウトを有限化する（Array/String と同じ機構の再利用）。`indirect` 等の修飾語は持たない／フィールド型・値意味論は書いた通り（ラッパー型は表面に出ない）／間接箇所はコンパイラが選ぶ（正しさは選び方に依らない）。**当初の仮結論（`Ref` 包み必須）は棄却**：`Ref` は共有可変で値意味論を壊し、`local` 化で spawn も阻むため。住み分け＝素の再帰＝値の木（自動箱化・spawn 可）／`Ref` 明示＝共有可変グラフ（循環可・`WeakRef`）。値意味論の再帰型は循環を作れない（親への貼り戻しは `Ref` 必須）ので `WeakRef`/リーク問題なし。終端ケースなしの再帰（`struct Node { val child: Node }`）は型としては合法のまま（構築不能なだけ・不要なチェックを課さない）。**根拠**：ヒープ/スタックの別はランタイム実装の詳細＝CoW と同じ「気にしなくていい暗黙」であり、Plew が嫌う暗黙（「書いた通りに動かない／想定と違う型」）ではない。Everyday Wizard 基準では露出させる理由がない。→ spec/05「再帰的な値型」・spec/03 Ref 節に索引。
- **トップレベル変数・`assoc val` の初期化** — **結論：起動時 eager（`main` 前に全完了・Swift/Rust の遅延初期化は採らない＝非直感を避ける）＋ force-on-read で依存順を自動算出（静的依存解析を持たない）＋トップレベル await 可（イベントループ上の async コンテキスト）**。各トップレベル値は memoize サンク（未初期化/初期化中/初期化済み）。初期化子が他値を読むと相手を再帰 force するので、関数越しの推移依存も実行が辿って正しい順になる。**循環はコンパイル時でなく起動時の panic**（ユーザーがこの緩和を選択＝静的解析が不要になり最小コンパイラが単純化。同期は「初期化中」再入で検出、async は待ち合わせの輪＝デッドロック検出）。**トップレベル await**：初期化子で `await`／内部 `spawn`+`join()` 可。起動は全値の force を**並行起動してから await all**（`Promise.all` 相当）＝独立な非同期初期化子は待ち（I/O）が重なる（真の並列は spawn）。依存があるものは force-on-read の await で直列化。初期化子は const 限定でなく任意の実行時式（life-before-main あり）。**同期プログラム（await 皆無）は無税**＝従来の同期 before-main と同挙動・同性能。**順序保証の範囲**：①メモリ安全（半初期化を観測しない）②依存順③一回性は常に保証。独立初期化子どうしの副作用順は **unspecified であって UB ではない**（各実行は妥当・メモリ安全。JS の Promise スケジューリングや辞書反復順と同性質。I/O 無しなら FIFO で事実上 kickoff＝宣言/import 順・I/O 絡みで前後し得る）。特定順が要るなら明示依存を作る。モジュール跨ぎも force-on-read で自動順序化＋跨ぎ循環も起動時 panic（`import` 循環の可否は初期化と独立）。**隣接論点（`main` エントリ規約）は別途決着**＝`fn main`／2 段選択（ファイル明示＋`main`）／戻り `()`|`Result`／args は stdlib／イベントループ drain で終了（上の「実行エントリ＝`fn main`」バレット・spec/15）。**残る隣接**：ジェネリック型 `assoc val` の per-instantiation（単相化）。→ spec/15「トップレベル初期化と実行順序」「実行エントリ（main）」・spec/07 assoc val に索引。
- **`panic` 時に `deinit` が走るか** — **結論：abort。巻き戻さず `deinit` も走らせない**。`panic` は catch 不可ゆえ unwind しても回復はなく「死ぬまでの掃除」にしかならない上、不変条件が壊れた状態で `deinit`（ユーザーコード）を走らせると二次災害（壊れたデータ書き込み・二重 panic）。資源は OS が回収（メモリ/fd/ソケット）。`deinit` の「決定的資源解放」契約は**正常終了パス**（スコープ離脱・`return`・`try`/`Result` 伝播）のみで保証＝panic はその外の明示的脱出口。実装は trap 一発（unwind テーブル/landing pad 不要＝最小コンパイラに優しい）。**Swift 調査**：`throws`/`try` は実体が「エラーを return で伝播させる通常制御フロー」ゆえ deinit/`defer` が走るが、trap（`fatalError`/`precondition`/強制アンラップ nil/範囲外/オーバーフロー）は巻き戻さず即死＝deinit 走らない。Plew の panic に対応するのは後者で Swift も走らせない。Rust は `panic="unwind"`（Drop 実行）/`"abort"` を選べるが Plew は意味論を変えるビルド差を持たない方針ゆえ常時 abort。死ぬ前のログ flush 等が要れば将来 atexit 風フック（unwind ではない）を additive に。→ spec/11「panic と発散」・spec/14 ARC 節に明記。
- **関数型ラベルの型同一性** — **結論：ラベルは関数型の同一性の一部のまま（spec/04 既定を維持）。ただしサブタイプも暗黙変換も持たない＝ラベル違いは別型で代入不可。クロージャリテラルの引数名＝ラベルで期待型と順序込み完全一致必須・ラベル多相なし。ラベル違いの適応は明示クロージャラッパー**。**経緯**：当初は SE-0111 流の「型からラベル消去」（案 X）を推奨したが、ユーザーが「混乱の主因は (a) 引数並べ替え (b) ラベル違いの暗黙サブタイプ変換であって、ラベルを型に持つこと自体ではない」と指摘。Plew は (a) 引数順固定・(b) 暗黙変換なし、を両方満たすので**ラベルを型に残したまま健全**にできる（SE-0111 詳細を一次資料で調査して裏取り：Lattner "inherently broken"、原則「ラベルは宣言のメタデータで型の一部でない」、受理時に装飾ラベル `_` のみ許容＝クロージャ値呼び出しは常に位置）。**ラベル多相（リテラル/参照が文脈ラベルを採用）は却下**：`f(handler: fn(y:,x:){…})` を `fn(x:,y:)` 期待に渡すと位置束縛で silent swap し、ラベルが型に書いてある分 Swift より誤解が強い。かつオーバーロード下では多相を後付けすると既存の一意解決が曖昧化＝破壊的（逆に relabel キャストの後付けは非破壊）。**relabel キャストは v1 では持たない**（案 1＝クロージャラッパー）：頻度が稀で、`as`⟺`From`（`x as T`⟺`<T from=x/>`・From ベース）の等式を崩してまで入れる価値が薄い。relabel は値を作らない純粋な型再解釈で From では表せず、欲しくなれば `as` 組み込みコアーションとして additive に足せる（案 2）。→ spec/04「ラベルは型の一部」節。**未策定の隣接**：関数型引数のラベル違いがオーバーロードを生む点（`foo(cb: fn(x:)->())` vs `foo(cb: fn(y:)->())` が別物）は原理的帰結として許容。
    - **ラベル抑制マーカー `name~: Type`（派生決定）**：`print(text:)`/`swap(a:,b:)` のラベルが冗長・無意味な引数を無ラベル化（位置渡し）したい需要に対し、Swift 流 `_ x`（外名 `_`・内名 `x`）を導入する。**ただし記法は `_ x` ではなく `name~:`**。**経緯**：(1) Swift 以外でラベル強制できる言語を調査＝Smalltalk/ObjC（セレクタにラベル織込み・無ラベルは二項演算子のみ・自由関数を持たずレシーバが天然の無ラベル第一引数）・OCaml（`~label` で opt-in＝無ラベルが既定）・Ruby（`def f(x:)` 必須キーワード）・Python（`*` で keyword-only）・Dart（`required` named）。「既定ラベル＋`_` で opt-out」は ObjC/Smalltalk 系譜で Swift に固有寄り。(2) **リネーム（外名≠内名）は不採用**＝命名が難しくなる・「オシャレに書ける余地」を断つ。ラベルは「引数名そのもの」か「無し」の 2 状態のみ。(3) 1 引数自動省略は**却下**（`delay(seconds: 3)` のようにラベルが本質の 1 引数を壊す＝抑制は作者の明示 opt-in）。(4) 混在は**許可**（`insert(value~:, index:)`＝Swift の `insert(_:at:)` 相当・「ラベル付きの後に無ラベル禁止」等の順序制約は主観的美しさの押し付けゆえ入れない）。(5) **記法選定**：`_ x` は空白入り二トークンが rename 形に見えてユーザーが嫌悪 → 候補比較（`x::`＝コロン装飾だが Rust/C++ の `::` 連想で却下／`x T` コロン落としは不在シグナルで typo に弱く却下／`(x):` は record/分解引数 `(label: expr)` と衝突／`-x:`/`x-:`/`x*:` は二項演算子チラつき）の末、**`x~:` を採用**＝`~` は Plew で単項 BitNot 専用で二項に使わないため **name 直後 `~` は postfix として式に絶対現れず衝突ゼロ・曖昧ゼロ**、`~`＝「ラベルを消す」の意味付けも乗る・追加マークなので typo に強い。(6) **関数型の無ラベル位置は裸の型**（`fn(String, terminator: String)->()`・ラベル camelCase/型 PascalCase で曖昧なし）でクロージャ側も `~:` で厳密一致（関数型ラベルの no-polymorphism と整合）。(7) **`factory` では `~:` 不可**＝生成は JSX `<Type label=…/>` でラベル付きであることが Plew の生成可視性の根幹ゆえ、ファクトリ引数のラベルは抑制できない（通常の関数・メソッドのみ対象）。→ spec/04「ラベルの抑制（`~:`）」・spec/05 factory 節。
- **構造体フィールドの既定値＋既定 factory の可視性** — **(A) フィールド既定値を許可**＝`val x: I32 = 0` は**既定（memberwise）factory のデフォルト引数の糖衣**で、意味論は #04 のデフォルト引数と同一（呼び出しごと再評価・定義側モジュールで評価・任意の実行時式・**他フィールド/self 参照不可**）。既定値持ちフィールドは生成時に省略可、省略組合せごとに生成セレクタが増える。**(B) 既定 factory の既定可視性＝not pub**（非公開メンバと同じ＝型の無名 impl からのみ呼べる）。理由＝memberwise factory は**非公開フィールドも構築引数に晒す**ため無制限公開は `pub`/`pub(get)` のカプセル化を構築時に破る。**公開は無名 impl 内に裸の `pub factory` を 1 行**（`@[...]` ディレクティブではなく素の構文）。**公開できる条件＝既定値を持たないフィールドが全 `pub`**（≡非公開フィールドは全て既定値持ち）、満たさねばエラー。**公開版の引数は `pub` フィールドのみ**・非公開フィールドは外から設定不可で常に既定値固定。**(C) `@[DefaultFactory(pub)]` ディレクティブは廃止**（祝福物を作らない＝可視性制御は derive でなく構文・ユーザー指摘）。→ spec/05「既定 factory（memberwise）とフィールドの既定値」・spec/10・spec/16。
- **`mut val` フィールド と `mut val` 束縛の合成規則** — **結論：Swift と同じ＝フィールド変更・`inout fn` 呼び出しには「束縛が `mut val`」かつ「フィールド自身が `mut val`」の両方が要る**。値型は束縛単位で凍結されるので、`val c = <Counter n=0 />` の `c.n += 1` は**フィールドが `mut val` でも**エラー（束縛 `c` が `val`）。逆に `mut val c` でもフィールドが `val n` なら `c.n` 変更不可（`c` 全体の再代入は可）。Ref はこの合成の例外（`val` 束縛越しでも referent 変更可・共有可変が本分）。→ spec/03「変数宣言（val / mut val）」に明記。
- **`try` は `Optional` に効くか** — **結論：`Result` 専用。`Optional` には効かない**（Rust の `?` が `Option` でも効くのとは異なる）。`Optional` は `??`/`?.`/`match`/`guard` で扱い、エラー伝播したいなら `opt ?? <Result.Err …/>` 等で明示 `Result` 化してから `try`。**根拠**：`try` の経路をエラー型 1 本（`Result` の `From` 変換）に絞り、「欠落（`None`）」と「失敗（`Err`）」を構文レベルで混同しない（`Optional` でも効かせると 2 つの早期離脱意味が `try` に同居する）。→ spec/13「try 式」に明記。
- **その他の小さな未明記** — 3 点を確定。**(a) newtype×unique**：包める＝**自動で `unique`（再宣言不要）・`deinit` 継承・最後の所有者で一度だけ実行**。コピー可能化は唯一所有の回避＝資源安全破壊なので伝播必須。`unique` だけ手で再宣言させないのは「underlying からすべて継承」原則どおり（underlying が `= File` と単一可視ゆえ構造体の見落とし罠が無い）。→ spec/10「unique 型を包む」。**(b) 複数 unique フィールドの deinit 順**：**型自身の `deinit` 本体が先（全フィールド有効）→ フィールドは宣言順（上から下）**・入れ子は再帰同規則。Plew はフィールド既定値が他フィールド非参照（spec/04 デフォルト引数）＝**構築依存が無い**ので C++ の逆順動機が無く最も単純な宣言順。→ spec/03 deinit。**(c) オーバーロードメソッドの関数値化**：**メソッドは値に代入不可＝`val f = obj.method` は禁止、クロージャで包む**（`fn(value:){ obj.method(value:) }`）。理由＝(1) どのオーバーロードかが一意でない、(2) `self` のアクセスモード（borrow は脱出不可・inout/move/unique-self も持ち回れない）。クロージャ内呼び出しがオーバーロードを一意化し、self はクロージャの参照キャプチャ規則がそのまま効く（専用規則ゼロ・関数型ラベルの方針と一貫＝暗黙の魔法を足さない）。セレクタ糖衣 `obj.method(value:)` は additive 保留。→ spec/07「メソッドは値に取り出せない」。
- **クロージャのキャプチャの可変性** — 経緯：spec/04 が「閉包内の変更も外へ漏れない」と書きつつ `makeCounter` 例は `Ref` を使い矛盾していた。**結論：通常のクロージャは参照キャプチャ（Swift と同じ）＝`mut val` キャプチャは可変・外と共有・呼び出しをまたいで永続**（`mut val x=1; val h=fn(){x+=1}; h() ⇒ x==2`）。脱出（escaping）しても変数は閉包の生存中存続するので**状態を持つ閉包に `Ref` は不要**（`makeCounter` は `mut val n` の参照キャプチャだけで書ける）。`val` キャプチャは読み取り専用。**`spawn` のキャプチャだけが不変**（境界越えは copy/move のみ・`mut val` 参照キャプチャした閉包は spawn 不可＝`Ref` 含む値と同じ `local`）。`Ref` の動機は閉包ではなく **unique 値の共有・意図した循環参照**（ユーザー明言）。**整合（「共有可変は `Ref` のみ」との関係）**：それはヒープ上の第一級の共有可変*値*の話で、レキシカルな `mut val` のクロージャ参照キャプチャも共有可変だが単一スレッド限定・spawn 不可の別機構（イベントループゆえ同時アクセスなし・論理 interleave のみ）。→ spec/04「環境のキャプチャ」。
- **素の数値リテラルの曖昧さが日常コードに波及（帰結の明記）** — 「数値リテラルは既定型なし・文脈で一意」は決定済み。**結論：当面フォールバックを入れず現状維持**（厳しい側＝明示要求から始める）。**推論の到達範囲は局所（前方・双方向）**＝注釈・引数型・戻り型・直接の被演算子型からその場で一意確定を要求し、**大域型推論（単一化／Hindley–Milner）で後の使用から逆算はしない**（アドホックなオーバーロードと衝突して曖昧化＋コンパイル時間爆発＝Swift の `ExpressibleByIntegerLiteral` × オーバーロードと同型の問題。最小コンパイラ・予測可能性を優先）。**許容する帰結**：`for val i in 0..<10`・`val x = 1 + 1` 等は**サフィックス必須**（`0..<10U64`／`1I32 + 1`）。`0..<arr.count`（`count`=U64 確定）や注釈・引数型がある場面は不要。暗黙数値変換なし＋添字/`count`=`U64` 固定ゆえ「単一の既定型」では添字（U64）と一般算術（I32）を両立できないのが既定型を置けない核心。**additive な緩和余地（後から非破壊）**：(a) 文脈ゼロ時限定の既定型フォールバック（**符号付きのみ＝`I32`/`I64`・`U64` は型の嘘ゆえ不可**）、(b) 推論到達範囲の局所→大域拡張。どちらも「今エラーの箇所が通る」だけで既存意味不変なので初手は厳しい側から。**コスト感（記録）**：大域単一化は実装中〜大（型変数・union-find・occurs-check＋オーバーロード/トレイト解決との衝突）・コンパイル時間は Swift 型の爆発リスク・生成物の実行コストはゼロ（型は消える）。**comptime_int・符号付き添字（I64 index）も探索の上いずれも却下**（上の「却下した代替」参照）。→ spec/02「リテラルの型付け」。
- **数値トレイトの分解原理（決定）＋ assert / ラップの確定** — **policy：struct 固有でない共有能力は trait にまとめる**（「整数」「数値」をまとめて扱う関数を書けるように＝`pow` を持つ値を一括処理 等）。難しさは**粒度**で、2 軸が交差する：**軸 A＝型の分類学**（符号付き/無し/小数で共通・固有が決まる→`Integer`/`SignedInteger`/`UnsignedInteger`/`Float`）と**軸 B＝ユーザ拡張性**（`pow` 等は自作型 BigInt/Matrix/Complex が独立実装しそう→`Add` 同様の単機能トレイトにしたい）。**解＝原子トレイト＋分類トレイト（supertrait 合成）**：ユーザ型が独立実装しうる能力は小さく原子化（演算子トレイトは既にこれ。`pow` も `Pow[Exp]`＝`Add[Rhs]` と同形・型引数で多重 conformance〔`impl I32 as Pow[U32]`／`impl F64 as Pow[F64]`〕＝他言語が pow を独立トレイトにしない理由＝指数型のバラつき、を型引数で解消）、**分類トレイトは原子の supertrait 束＋その表現に固有の要求**として定義（`trait Integer: Add + … + Pow { fn countOnes()…; wrapping…() }`）。これで BigInt は `Add`/`Pow` だけ実装して `f[T: Pow]` に渡せ（軸 B）、`where T: Integer` で束ごと取れる（軸 A）。**粒度の決定ルール**：あるメソッドを**独立原子トレイトに切り出す ⟺ 数値分類の外の型が同じ意味で独立実装しうるか**。Yes（`pow`・`abs`/`signum`）→原子。No（`countOnes`/`leadingZeros`/**`wrapping*`**＝固定幅 2 の補数固有で外部実装者なし）→分類トレイト内の要求。**帰結：`Wrapping` を単独トレイトにはしない**（ラップは固有ゆえ整数分類トレイト内のメソッド）。**他言語**：Swift の数値タワー（`AdditiveArithmetic`→`Numeric`→`BinaryInteger`→`FixedWidthInteger`/`Signed`/`Unsigned`・`FloatingPoint`）が軸 A に最も近い／Rust は std=演算子原子＋inherent・分類は num-traits crate（`Pow` 等）／Haskell は `Num`/`Integral`/`Fractional`/`Floating`（`**` は Floating・整数冪は自由関数）。**ラップ確定**：メソッド `wrappingAdd`/`sub`/`mul`/`neg` のみ・**専用演算子 `&+` なし**・`div`/`rem`/`shl`/`shr`/`abs`/`pow` は additive。**assert 確定**：常時 ON 一本（全ビルド同意味論・通常関数で非 lang item＝import 要）・`debugAssert` 除去段は additive 保留（「観測挙動が唱えた意味から逸れない」と唯一緊張＝別名で後付け）。**スコープ判断**：原理と上記具体配置のみ今ロック・`Integer`/`Float`/`Pow[Exp]` 等の**正確なメンバ表と署名は core-library 送り**（Hash/イテレータ署名と同枠＝実装着手時の方が情報が揃う）。→ spec/02「整数の実行時セマンティクス」・spec/11「assert」。
- **演算子・比較・step トレイトの要求は `assoc fn`（メソッドでない・決定）** — 命名規約：操作が**値を変えるか**で形が決まる。**破壊**＝`inout fn`（命令形・`next`/`sort`）／**非破壊で値を産む対称操作**＝`assoc fn`（操作名・`add`/`compare`/`stepForward`）／**名詞アクセサ**＝`fn` メソッド（`iterator`/`count`）。**経緯**：従来 `fn add(rhs:) -> Output`（`a.add(rhs: b)`）だったが、ユーザー指摘「非破壊なのに命令形メソッド＝`add` したら lhs が変わると誤読（Swift の `sort`/`sorted` 規約違反）」。修正案は (1) `assoc fn add(lhs:, rhs:)` か (2) 過去分詞メソッド `added(other:)`。**(1) を採用**：過去分詞は `bitAnded`/`remaindered`/`coalesced` が破綻／対称二項にレシーバを演じさせない方が正直／Swift の演算子 `static func +`・Rust の `Step` と同形。**対象**＝`Add/Sub/Mul/Div/Rem`・`BitAnd/BitOr/BitXor/Shl/Shr`・`Neg/Not/BitNot`・`Eq`・`Ord`・`Pow`（脱糖は `a+b ⟺ T.add(lhs: a, rhs: b)` 等）。**非対象**＝`Index`/`IndexSet`（コンテナアクセサ・レシーバが主語のメソッド）・`Chain.chain()`（分解アクセサ）・`From`（factory）・`Iterator.next`（`inout`＝破壊で命令形メソッドが正）。`+=` 等は演算子レベル純粋脱糖なので不変。→ spec/12（全演算子トレイト＋脱糖表）・spec/09/10（impl 例）。
- **イテレータ・プロトコル＋`Step` の確定** — **2 層**：`Iterator { type Item; inout fn next() -> Optional[Item] }`（消費カーソル）／`Iterable { type Item; type Iter: Iterator[Item = Item]; fn iterator() -> Iter }`（毎回新カーソル）。`Iterator` を `Iterable` にする blanket（`impl B as A` 形・`iterator(){ self }`＝値コピー返し）で iterator を直接 `for` 可。**`for` 脱糖**＝`mut val it = e.iterator(); loop { match it.next() { Some(val x)=>…, None=>break } }`。**横断批准**：`type Iter: Iterator[Item = Item]`＝**境界内の関連型束縛**を存在型に限らず一般に許可（`any Iterator[Item=I32]` と同形）。`Iter` は具象関連型で露出（単相化・boxing なし）。提供メソッド（map/filter…）はベア `impl Iterator`・署名は core-lib。**`Step: Ord`**（assoc fn 3 本）＝`stepsBetween(start, end) -> (lower: U64, exact: Optional[U64])`・`stepForward(start, count: U64) -> Optional[Self]`・`stepBackward(…)`。レンジは `where T: Step` 条件付き準拠で `Iterable`。**`stepForward` の `None` は正常終端**（`0..=U64.MAX` の MAX 溢れを panic でなく None で扱う・算術 overflow panic とは別物）。**Step の型を U64+tuple にした根拠（Rust 調査）**：Rust の `stepsBetween -> (usize, Option<usize>)` は **sizeHint と同形（飽和下界＋任意の正確上界）**で、`None` は「歩数が usize 超過/無限」。**associated `Distance` 型は採らず U64 固定（Rust に倣う）**＝(1) 本当の消費者（Array collect の事前確保）は Array 容量＝U64 上限ゆえ U64 で頭打ちが正しい、(2) associated 化は「どのコンテナにも入らない広範囲の正確カウント」という誰も使えない値のため機構を増やすだけ、(3) Swift の signed `Stride` は `UInt(0).distance(to:.max)` が trap する wart・Rust は usize 固定で回避＝Plew も U64 中核（添字）で Rust 側が正。Plew 改善は**ラベル付きタプル `(lower:, exact:)`** で自己説明的（Rust の位置タプルより読める）。`stepForward`/`backward` は Rust の all-assoc に合わせ（上の命名規約とも一致）。**Rust の `(usize, Option<usize>)` は wart でなく正当**（カウント型 vs 値幅のミスマッチが本質）と結論。→ spec/11「イテレータ・プロトコル」・spec/02「Step トレイト」。
- **文の区切り＝改行（自動文終端・確定）** — spec は当初明記していなかったが、サンプル（`examples/`）と旧 ANTLR 文法（`req_newline`）が**改行終端・セミコロン不要**で一貫するため、これを正とした（ユーザー追認済）。**規則**：改行が「文を終えられるトークン」（識別子・リテラル・`)`・`]`・`}`・`return`/`break`/`continue`）の直後に来たとき**文終端トークンを挿入**。行末が演算子・`,`・開き括弧のとき、および **`(...)`/`[...]` の内側**では改行を無効化＝暗黙の行継続（Swift 流）。**`{...}` ブロック内は改行有意**（文の区切りに使う）。**却下案＝Go 純トークン式**（括弧内も終端挿入＝複数行呼び出しに末尾カンマ必須）は Swift 系の書き味に劣るため不採用。**実装**：lexer が `Newline` トークンを Go 流の last-token 判定＋括弧深さ追跡で生成（`bootstrap/src/lexer.rs`）。→ spec/01「文の区切り」に反映済。

言語コアの設計は概ね決着し、残るは**実装／コアライブラリ寄り**が中心：

1. **チャネルの最終構文・型** — 方向（複数 Sender・`receive() -> Result[T, ChannelClosed]`・`Send`/`Clone` 境界不使用・`send` は immutable メソッド）は固まっているが、**所有権が無いため Receiver の単一所有は強制できない**（複数参照・複数 `receive` 可）。マルチコンシューマの意味論を含め **具体 API はコアライブラリ実装の課題**（言語コアの構文要素ではない）として stdlib 設計時に詰める。
2. **spawn/async の意味論実装** — モデルは確定（`spawn` はスレッド起動・ハンドル `join() -> Promise[T]`・キャプチャ全 immutable・立てたスレッドも単一ループ・全スレッド完了までランタイム生存）。実装課題は「キャプチャ全 immutable」の型チェック（セマンティクス層）。文法には `block_modifier: ASYNC | SPAWN` のみ。
3. **Mutex/sync/atomic の扱い** — 標準で提供しない（or `@unsafe` 限定）。旧文法の修飾子は削除済み。
4. **ARC/refcount の方式** — ARC 採用。**循環回収は方針確定**＝**Ref グラフ限定の Bacon–Rajan サイクルコレクタ**（per-thread・event-loop idle）。検出時は loud 報告（全ビルド ON）＋メモリ回収＋**循環メンバの deinit は走らせない**（deinit の有無で挙動を分けない＝「deinit を足したら漏れ出す」崖を作らない・panic と対称の契約外脱出。詳細・根拠は上記メモリ節「循環回収／循環検出時の挙動」）。実装順は reporter 先行→回収追加（どちらも非破壊）。残る実装課題は (a) スキャンの頻度/トリガ（idle/確保圧/終了時）の調整、(b) 非 atomic refcount と候補バッファの具体表現（side table 等）、(c) 診断フックの API。
   <!-- 循環内 deinit の順序問題（PEP 442）は「循環メンバを finalize しない」決定により消滅。回収を deinit 有無に依存させないのは footgun 回避が理由。 -->
5. **メタプログラミング詳細（骨子は確定・上記「メタプログラミング」節）** — 入力＝AST・`Derive`＝要求 `derive(input: AST)`＋提供 `deriveFromSource`・ランナー＝String↔String・構文ライブラリ＝当面 `@Std/Syntax`、までは決定。**残るは `@Std/Syntax` の `DeclAst` 具体形**（struct/enum・関数シグネチャ・型式の表現と span）・`plew gen` のコマンド設定・組み込み Eq/Ord/Hash を `Derive` 実装へ dogfood する段取り（→ [spec/16](../spec/04-execution/16-metaprogramming.md)・[metaprogramming-architecture.md](metaprogramming-architecture.md)）。
6. **文法の細かい穴** — `@[...]` 内の空行・末尾カンマ、`match_case` 前の改行、`where_clauses` 末尾カンマなど（書き味レベル）。
7. **FFI の型マッピング** — `extern "c"` / `extern "javascript"` ブロックの構文は採用済みだが、Plew 型 ↔ C/JS 型の対応（数値・ポインタ/バッファ・文字列の境界変換、外部由来の `NaN` 流入の扱いなど）は未策定。C 固定長配列は当面**境界コピーで `Array[T]`** に写す方針（→ [spec/15](../spec/04-execution/15-modules.md)）。
8. **文字列・配列の保留 API（すべて additive）** — 骨子（不変 String・`bytes` 公開・`Array[T]` 一本・`==` バイト等価・`scalars`/`graphemes` イテレータ・FFI はコピー）は確定。以下は後から非破壊で足す：(a) **文字列ビルダ**の型名・API、(b) **正規化 API**、(c) **`Slice[T]`（ビュー型）とゼロコピー部分文字列／FFI**（入れるなら所有 `Array`＋固定ビュー `Slice` の 2 型・取得は `arr.slice(...)`）、(d) **String の substring API**（まずはコピー版）、(e) **片側レンジ**（`a..`/`..<b`）・`step`（`.stepBy`）・逆順反復（`.reversed()`＝`stepBackward` を使う sub-trait）・**レンジパターン**・スライス糖衣 `arr[..<n]`（**`Iterator`/`Iterable`/`Step` の署名と `for` 脱糖は決定済み**＝上記「イテレータ・プロトコル＋Step の確定」。残るは提供メソッド群 map/filter/zip… の署名＝core-lib）、(f) **固定長配列 `[E; N]` / const generics**。
9. **ambient 型の正確な一覧 ＋ 脱糖表スロットの対応付け** — 「ambient なのは型のみ・トレイトは非 ambient（脱糖表＋名指し時 import）」は決定（上記）。**import 体系も決定**（3 ルート `@…`/`/`/`./`・`@Std` 予約＋分割・任意深さサブパス・`/`＝ルート起点絶対・`public`/path=file ── 上記「パッケージ」）。残るは (a) **ambient 型一覧の最終確定**（数値型の幅セット・`Promise`/`JoinHandle` で確定の他に漏れがないか）と (b) コンパイラの**脱糖表スロット**（`+`↔`Add` 等）と**コアライブラリのトレイト/型定義**の対応付け（実装フェーズ）・std 領域分割の正確な一覧。マニフェスト既定 import は当面不採用＝additive で後付け可。
10. **数値トレイトタワーの正確なメンバ・署名（core-lib）** — 分解原理（原子＝外部実装可能な能力／分類＝supertrait 束＋固有要求・決定ルール）は決定（上記「数値トレイトの分解原理」）。**assert＝常時 ON 一本**・**ラップ＝メソッド `wrappingAdd/sub/mul/neg` のみ（専用演算子 `&+` なし）・整数分類トレイト内**・**`pow`＝原子 `Pow[Exp]`** も決定。残るは (a) `Integer`/`SignedInteger`/`UnsignedInteger`/`Float`/`Pow[Exp]` 等の**正確なメンバ表と各署名**（Hash/イテレータ署名と同じ実装フェーズ送り）、(b) `debugAssert` の除去段＋ビルドプロファイル定義（additive）、(c) `wrappingDiv`/`rem`/`shl`/`shr`/`abs`/`pow` 等の追加（additive）。
11. **テスト機構（骨子決定・残りは実装/ランナー）** — 言語表面は決定済み（上記「テスト」＝`test` ブロック・配置＝モジュール直下/無名 impl 内・発見＝無条件全収集・production リンク除外・アサーション族 `expect`/`expectEq`/`expectNe`/`expectApprox`・power-assert 不採用・`@Std/Testing`）。**残るは実装/ランナー/core-lib**：(a) **失敗チャネルの機構**＝テスト失敗を panic（プロセス停止）なしにランナーへ伝える具体（テストコンテキストへの記録 or `test` ブロックからのエラー脱出）。(b) **`@Std/Testing` の正確な署名**＋診断表示が依存する `Debug` 相当トレイト。(c) **`assert`（実行時）の置き場モジュール名**（`@Std/Diagnostics` 等・Testing でない＝本番でも使う）。(d) **Result/Optional の `is*`**（テストの bool 化に使う core-lib API）。(e) **async テスト**＝`async fn`／イベントループ上のテストの扱い。(f) **doc テスト**は当面保留（additive）。(g) **`expectMatches`**（パターン引数）は additive 保留。**位置づけ**：すべて実装/ツール/core-lib フェーズで、言語コアの構文・意味論は確定。

> 残る論点はいずれも実装／コアライブラリ／ツール着手時に詰めるもので、言語コアの構文・意味論は確定済み（import 体系・テスト機構の言語表面も決着）。**拡張の別名束ね（`alias Web = Json + Http`）は「既定で持たない」で確定**（決定）：純粋なエルゴ糖衣で新意味ゼロな一方、`#Web` はどの拡張が効くか使用位置から見えなくなり「出どころが常に分かる」を侵すため。「将来やる」ではなく「具体的苦痛が出たときだけ非破壊で再検討・入れるなら `#Web`→`#Json#Http` の 1:1 逆展開可を条件」と格下げ。継承・ネスト自体は禁止で決着（本文「拡張システム」節）。→ spec/09。
